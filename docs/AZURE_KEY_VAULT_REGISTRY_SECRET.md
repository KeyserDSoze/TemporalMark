# Azure Container Apps — versioned external Key Vault DB secret (#127)

**Scope:** reference infrastructure only, **NOT a proven Azure deployment, production-ready secrets architecture, or qualified legal custody**. See [ADR 0094](../adr/0094-azure-api-keyvault-bootstrap-secret-reference.md), [#127](https://github.com/KeyserDSoze/TemporalMark/issues/127), Azure parent [#18](https://github.com/KeyserDSoze/TemporalMark/issues/18), [#115](https://github.com/KeyserDSoze/TemporalMark/issues/115) and [#17](https://github.com/KeyserDSoze/TemporalMark/issues/17).

## Security delta and threat

The prior Azure reference placed `var.registry_connection_string` directly in `azurerm_container_app.api.secret.value` and exposed its database credential in Terraform state even though the variable was marked `sensitive=true`. The new reference **removes that Terraform input entirely** and configures the API Container App with `secret.key_vault_secret_id` (non-secret reference to an externally provisioned, specifically versioned secret) and `secret.identity` (a newly created **user-assigned managed identity**).

The API identity block contains both `SystemAssigned` (unchanged: existing evidence Storage Blob Data Contributor) and one `UserAssigned` (new: secret lookup only). The user identity is created before the Container App and receives `Key Vault Secrets User` at the **supplied Key Vault resource scope**, with explicit Terraform ordering. No Terraform resource or data source reads, stores, generates, exports or creates the DB secret value itself. The ordinary application variable `ConnectionStrings__Registry` still refers to the Container Apps secret name `registry-connection`.

**Important least-privilege boundary:** the role assignment is at vault scope, not per-secret scope. The externally approved Key Vault should be **dedicated solely to this application's registry connection secret**; do not co-locate tenant credentials or unrelated secrets. The reference does not create/configure the Key Vault, private endpoints, DNS/firewall, vault policies, monitoring or secret versions.

## Manual authorized setup and change control (Azure real, NOT executed by CI)

1. Obtain independent approval for a **dedicated, RBAC-enabled Key Vault**, correct identity tenant/subscription, private access topology and an application database principal with **only** required privileges. Create and approve the value of a named secret **outside Terraform** using protected secret provisioning. Do not place the connection string in the repository, issue comments, CI environment, terraform CLI `-var` values, `.tfvars`, log/console, or any Terraform-managed Key Vault `secret.value`.
2. Provide the exact **versioned** secret URI (`https://<vault>.vault.azure.net/secrets/<name>/<32-lowercase-hex-version>`) as `registry_connection_secret_uri` and the full ARM ID of the *same* approved vault as `registry_connection_key_vault_id`. The two are validated and checked against each other during Terraform plan. The values are identifiers **not the connection string**. The checked-in sample contains fictitious placeholders. A change to a secret version requires its own explicit reviewed Terraform plan; no automatic unversioned latest-secret rollout is enabled.
3. Review `terraform plan` from an authorized runner, including the new user-assigned managed identity, vault-scoped `Key Vault Secrets User` and both Container Apps API identities. Confirm Blob identity remains system-assigned and web/API ingress remains internal by default. **Do not apply** until Key Vault DNS/networking/egress and grant propagation are independently checked. Terraform graph `depends_on` orders the RBAC resource but does not guarantee Entra or Key Vault RBAC propagation, enabled secret version, Key Vault secret expiry, firewall access or a healthy deployed revision.
4. **Existing deployments are not automatically migrated safely.** Prior state files and backups may retain the original `registry_connection_string`/API `secret.value`. Never assume removing an HCL variable removes state history or logs. Treat old credentials as potentially exposed, agree on protected state snapshots/backend ACLs, secret scanning and retention/deletion under GDPR/legal policy, database credential rotation (including replicas, jobs and break-glass accounts), controlled traffic cutover and rollback. Do not destroy/replace a protected database or evidence container to cleanse state. Coordinate migration-job credentials separately.
5. For real Azure acceptance, verify the effective Key Vault secret reference (without printing the secret value), managed identity attachment and resource-scoped RBAC, private DNS/connectivity, read permission and controlled rotation on a disposable staging app. Inspect Container Apps revision health, private PostgreSQL connectivity, safe failure on missing/disabled/expired secret, API data integrity, zero logged connection strings and security telemetry. Check Key Vault logs and role grants for least-privilege drift. CAB release, Data Protection Impact Assessment, production cutover and rollback evidence remain #18/#115.

Microsoft guidance: [Azure Container Apps Key Vault secret references](https://learn.microsoft.com/en-us/azure/container-apps/manage-secrets) notes that a user-assigned identity can bootstrap creation before a system-assigned identity exists and that Key Vault Secrets User is required; [deployment troubleshooting](https://learn.microsoft.com/en-us/azure/container-apps/troubleshoot-deployment-errors) documents RBAC propagation, secret availability and firewall errors; [AzureRM Container App resource schema](https://registry.terraform.io/providers/hashicorp/azurerm/4.46.0/docs/resources/container_app) defines `secret.key_vault_secret_id` and `identity`.

## CI and non-goals

The mandatory Terraform job runs `terraform -chdir=infra/azure test -no-color -filter=tests/api_key_vault_reference.tftest.hcl` with **mocked AzureRM plans**. The ten cases cover URI-only/no direct value, user/system identity intent, RBAC vault scope/role, malformed HTTP/unversioned/credential/query/foreign-host/nonhex URLs, invalid vault ARM ID and cross-vault URI/role mismatch. The existing OCI 11, OIDC 17, ingress 3, environment 3 and private Blob 2 plan tests remain. `fmt` and `validate` remain mandatory; mocked plans **do not create an identity, prove live Key Vault resolution or test secret retrieval**.

**Explicit remaining Terraform state secret:** `azurerm_postgresql_flexible_server.registry.administrator_password = var.postgres_password` is still present, so **the Terraform state is NOT secret-free**. Separate design required for PostgreSQL Entra-only administration, migration execution and credential removal; no force migration or claim of immediate state cleansing. The Blob immutability policy remains unlocked and preexisting AzureRM 4.x `storage_container.evidence.resource_manager_id` deprecation remains to be reviewed before provider 5.0. Neither this change nor the previous Blob private network tooling satisfies independent WORM custody, eIDAS/QTSP qualification, WAF, GDPR/DPIA, production HA/DR, signing, Key Vault network isolation or access-review governance.
