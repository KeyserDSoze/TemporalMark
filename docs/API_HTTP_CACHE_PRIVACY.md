# TemporalMark v1 API — HTTP no-store privacy contract (ADR 0144 / #186)

**Scope:** current unqualified pilot ASP.NET Core API, identical on OSS on-prem and Azure reference image; **not** a proof of what third-party CDNs, clients, enterprise proxies or browser disk caches actually retained. [ADR 0144](../adr/0144-api-v1-uniform-no-store-http-cache-policy.md), security parent [#115](https://github.com/KeyserDSoze/TemporalMark/issues/115), privacy [#113](https://github.com/KeyserDSoze/TemporalMark/issues/113), PWA delivery [#20](https://github.com/KeyserDSoze/TemporalMark/issues/20).

## Policy and priority

A single early ASP.NET Core middleware matching **only the `/api/v1` path segment** (case-insensitive) registers a final `Response.OnStarting` callback that sets **`Cache-Control: no-store`** on **every outgoing v1 response**. This includes private `200` tenant administrator identity, original registry metadata list, UTC daily/summary counts, audit actor events, search match/no-match, raw timestamp reply and ZIP; issuance success when externally possible; and **401/403 invalid or unauthorized identity**, validation 400, tenant-disjoint 404, 409 oversized evidence, pre-auth 413, search rate 429 and 502/503 provider errors. It deliberately does **not** set this policy on the public `/healthz` route, `/api/v10`, static SPA/manifest/assets or external Keycloak. A segment boundary avoids accidentally matching version 10. Registration runs **before** the sensitive search request-size control, authentication and authorization, so pre-auth rejection and downstream response header changes cannot bypass the final no-store directive. Existing explicit endpoint `no-store` branches remain defense in depth.

This is an **HTTP response policy**, separate from the PWA Workbox `runtimeCaching: []` and the `/api` navigation-fallback denylist. Workbox CacheStorage tests do **not** inspect the browser's HTTP cache, upstream proxies or historical cached entries. `no-store` instructs compliant HTTP intermediaries and browsers to avoid caching future private responses; it does **not** delete data already in disk caches, revoke an old JWT, prevent screenshots, force a malicious client to comply, sanitize external CDNs or guarantee effective Azure managed ingress controls. Avoid shared proxy caching of `Authorization` responses and independently inspect all production edge caching/logging policies before rollout.

## Unresolved operational and legal release gates

External on-prem gateways, customer-installed CDNs, Azure Container Apps **managed ingress**, WAF, Log Analytics/APM/tracing, Keycloak log collectors and backup copies may use different request/response storage rules. Inspect effective production settings and actual synthetic canary traffic end to end; avoid logging full request URI/query, original document SHA256 imprint, Authorization bearer, response bodies or subject identifiers without purpose/retention approval. Obtain authorized privacy/DPIA and retention decisions under #113/#115, not by treating this header as GDPR certification. Signed WORM/evidence retention #17, historical QTSP/EU Trusted List CMS verification #15 and legal CAB/AgID/eIDAS qualification #13 remain OPEN; pilot evidence status stays `Unverified`.
