# npm 10 locked clean installs — PWA and browser suite (#75)

**Scope:** deterministic dependency resolution for two npm projects, not a certified reproducible build or legal timestamp service. ADR 0044; child issue #75 of still-open #20.

## Committed artifacts and installation contract

- src/frontend/package-lock.json: genuine npm lockfileVersion 3, **475 entries** including root, resolved against the public npm registry on an ephemeral GitHub Actions Node 22/npm 10 runner.
- tests/frontend/package-lock.json: genuine npm lockfileVersion 3, **9 entries** including root, resolved in the same runner.
- Every registry package has its specific version, registry HTTPS tarball URL and integrity hash. The exact generated bytes were obtained from the public-only CI seed output, verified against the two package.json manifests and committed unchanged. The temporary CI step emitting the base64 lockfiles was removed immediately after committing them.
- The React PWA build, Playwright test installations in both CI jobs, and the web Docker build now call npm ci --no-audit --no-fund. Docker copies package.json **and** package-lock.json before executing npm ci. The npm ci command refuses to install if the lock and manifest disagree; it never silently updates the lock.
- The backend CI job runs Python standard-library tests for both root manifest snapshots and their real registry lock trees. The repository check requires lockfileVersion 3, matching direct dependency maps, nonempty resolved transitive entries with fixed semver, HTTPS registry tarball URLs and integrity. It refuses reintroduction of npm install in the active CI or web Dockerfile.

## Change control and limits

On a dependency change: review upstream package advisories and manifest changes, run npm install --package-lock-only with the same npm 10 behavior in a controlled environment, inspect the lockfile diff (including resolved sources and integrities), and commit both manifest and lockfile together. In CI, run npm ci in each directory; never use npm install to resolve dependencies silently during tests or Docker production build. Do not add registry passwords or npm tokens to lockfile URLs.

npm ci only pins npm dependency resolution and checks tarball integrity; it does not make a package safe. Post-install scripts, Playwright browser downloads, Node 22 and nginx image manifests pinned as of #76 (see CI_DOCKER_IMAGE_DIGESTS.md), GitHub runner OS, .NET and Terraform providers may still change, and upstream package downloads may become unavailable. Container digest pinning, SBOM/SAST/SCA, release artifact attestations, API contract/cross-tenant tests and actual PWA installation checks remain #20. There is no independent FIDO MDS R46 root, CAB/HSM-signed monotonic witness, Azure/on-prem production parity, QTSP or eIDAS qualification. #64/#61/#57 and V015/V016 registration issuance interlocks remain OPEN.

Technical sources: [npm ci](https://docs.npmjs.com/cli/v10/commands/npm-ci), [npm lockfile schema](https://docs.npmjs.com/cli/v10/configuring-npm/package-lock-json), [ADR 0044](../adr/0044-locked-npm-dependency-trees.md).

## Separate npm dependency inventory for CI (#77)

The PWA and browser lockfiles also feed deterministic CycloneDX JSON 1.5 `npm-lockfile-only` inventories through `tests/integration/generate_npm_sbom.py`. The frontend CI verifies then uploads two short-lived JSON files; details and strict nonclaims in [runbook](CI_NPM_CYCLONEDX_SBOM.md). This adds no vulnerability verdict, publisher signature, installed-asset attestation, container/.NET system inventory or long-term evidence custody.
