# TEST-ONLY triple high-water reconciliation: real dual-PostgreSQL rollback vs signed file (#72)

**NON-AUTHORIZING / UNAPPROVED / SAME CI HOST / NOT IMMUTABLE / NOT TRUSTED FIDO OR QUALIFIED EVIDENCE.** See [ADR 0041](../adr/0041-three-synthetic-highwater-store-reconciliation.md), child [#72](https://github.com/KeyserDSoze/TemporalMark/issues/72), still OPEN parents [#64](https://github.com/KeyserDSoze/TemporalMark/issues/64), [#61](https://github.com/KeyserDSoze/TemporalMark/issues/61) and [#57](https://github.com/KeyserDSoze/TemporalMark/issues/57).

## What this increment checks

The existing mandatory `tests/integration/mds-full-pgdump-restore.sh` uses a real PostgreSQL 17 **whole logical** `pg_dump -Fc` and `pg_restore` into a **separate database on the primary cluster**. The original primary database then has synthetic latest serial **4**, while the whole restored primary database holds older serial **3**. Separately, an opt-in `witness-ci` PostgreSQL 17 container and its dedicated read-only witness SQL login normally retain latest signed seal **4**, so a restored old primary database cannot silently appear current.

**Attack tested:** a privileged operator with the *secondary* witness PostgreSQL superuser can bypass the restricted `SECURITY DEFINER` writer and rewrite latest witness checkpoint back to correctly signed serial **3**, without actually needing to delete its separately auditable event row for serial 4. **Before #73**, comparing only an older fully restored primary DB + older separate witness checkpoint + older correctly signed manifest/seal could pass the two-source preflight as `UNAPPROVED` *even when event4 remained*. **After ADR 0042**, the retained event4 makes the checkpoint=3 inconsistent and the two-source reader DENIES; the privileged superuser must erase/roll back the event tail as well to reproduce the old UNAPPROVED result. Neither its signatures nor SQL privilege separation establishes which signed version is the newest.

The new isolated `ReviewerMdsThreeSourceHighWaterCandidateReconciler` requires one additional **test-only** file journal holding RSA-PSS signed version 3 followed by 4 with original event-byte hash chain and caller-selected disposable test signer SPKI. It explicitly reads and validates the file *before* and *after* the existing two-store SQL verification; requires identical source-policy hash, **serial** and **signed seal SHA256** between journal and witness PostgreSQL; and relies on the existing exact signed manifest, seal and read-only V017 primary snapshot checks. A missing, corrupted, stale or wrong-key journal, version mismatch or unavailable SQL witness denies; there is **no automatic rebuild or fallback**. Return is always `UNAPPROVED/THREE_TEST_STORES_NO_INDEPENDENT_CUSTODY`, never `TRUSTED`, `ACTIVE` or a credential authorization.

## Mandatory negative disclosure: triple rollback is not solved

The fixture then deliberately **replaces the journal with an older but correctly signed full file** while the same privileged operator has reverted the witness SQL and supplies the old full restored primary DB. With all three states consistently at **3**, the new comparator returns `UNAPPROVED`: **it cannot determine that serial 4 ever existed**. This is an intentional attack demonstration, *not evidence of secure custody*. The CI Docker host controls both PostgreSQL volumes, app DB credentials, test keys, and the normal file. No host-root, backup administrator, clock or malicious signer is outside the trusted computing base.

The double file read mitigates an ordinary concurrent append race but is **not** a distributed atomic snapshot or tamper-proof `openat2`/O_NOFOLLOW; a privileged attacker may change the file between checks, replace key pins, replay all signed volumes, or submit newly signed bogus higher version. On-prem OSS and Azure production still require independently governed signed latest-pointer custody, offsite Object Lock/WORM or other independently enforced monotonic service, HSM/CAB key bootstrap and rotation, physical PITR/recovery/region split-brain proof, authoritative time, privacy and legal audit, and explicitly equivalent secure operational deployments. FIDO official R46 root/x5c/CRL and real WebAuthn signed review/enrollment are still blocked (#57/#55/#53/#44/#50/#46/#38). No eIDAS/QTSP qualification claim.

## #73 addendum — original two-source witness audit is now checked

The original #72 TDD fixture deliberately proved the *historical* checkpoint-only two-source reader could accept old main+old witness checkpoint with latest audit event4 still present. [ADR 0042](../adr/0042-ci-witness-bounded-audit-history-reconciliation.md) now changes that behavior: internally retained event4 must DENY checkpoint3 even without a signed file. The fixture has been extended to simulate a superuser who removes **both** latest row and event tail, then proves that the normal signed file at4 still blocks it, but replacing that file with an older correctly signed copy permits a fully stale all-three **UNAPPROVED** result. This is why child #73 can be closed without closing independent custody parent #64. [Dedicated runbook](MDS_CRL_WITNESS_AUDIT_RECONCILIATION.md).
