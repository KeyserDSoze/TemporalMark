# Azure Container Apps managed-identity PostgreSQL token supplier candidate (#131)

**Status: offline prequalification, NOT deployed and NOT wired to the API/Provisioner/migrations.** See [ADR 0097](../adr/0097-container-apps-managed-identity-postgres-token-candidate.md), scoped [#131](https://github.com/KeyserDSoze/TemporalMark/issues/131), [Npgsql data-source candidate](ENTRA_POSTGRES_NPGSQL_CANDIDATE.md), parent [#128](https://github.com/KeyserDSoze/TemporalMark/issues/128) and Azure [#18](https://github.com/KeyserDSoze/TemporalMark/issues/18). No Azure subscription, Container App or database was accessed by the offline tests.

## Why this boundary is needed

The existing Azure reference still uses a password-based PostgreSQL Flexible Server and places `administrator_password = var.postgres_password` in Terraform state. Its API is configured for a Key Vault secret containing a *conventional* SQL connection string; Npgsql `NpgsqlDataSource.Create` still uses that string. Neither the Entra-only **new-server Terraform candidate** (#129) nor the detached Npgsql token data source (#130) is deployed or used by the app. SQL migration, restricted approver and registrar clients have separate SQL logins.

The new detached class `TemporalMark.Infrastructure.Postgres.ContainerAppsPostgresManagedIdentityCandidate` supplies an **optional async callback** to the detached Npgsql `EntraPostgresDataSourceCandidate` from #130. It uses only .NET 10 framework HTTP/JSON APIs; no new Azure.Identity/NuGet dependency is imposed on the OSS on-premises application. **No application service registration, Terraform identity or production configuration has been changed.**

## Local ACA identity REST security contract

Microsoft Container Apps documents a **local** `IDENTITY_ENDPOINT`, rotated `IDENTITY_HEADER`, `GET` with `X-IDENTITY-HEADER` plus `resource`, `api-version=2019-08-01` and optional `client_id`. This candidate deliberately requires **an explicit user-assigned identity client GUID**, never an omitted `client_id` that would select a system-assigned identity. Its approved identity must be separately provisioned/granted SQL access by an authorized operator; the existing system-assigned identity is used for Blob storage and the current user-assigned identity for Key Vault secret lookup. **Do not assume either has database privileges.**

- Input endpoint: plain **HTTP loopback only** (`localhost`, `127.0.0.1` or `[::1]`), with nondefault explicit port and static safe path, no username/password, query or fragment. Reject public DNS names, link-local `169.254.169.254`, arbitrary IP, metadata endpoint fallback, HTTPS downgrade ambiguity and unreviewed endpoint formats. Actual ACA endpoint shape remains a **live staging requirement**; don't loosen arbitrary URLs to make it work.
- Production transport: connects to a **literal loopback IP** rather than resolving a hostname; no ambient proxy, redirect, cookies, automatic decompression or ambient HTTP credentials. Short HTTP timeout, bounded response and limited connection pool. This does not by itself prove a live ACA runtime configuration or prevent malicious local same-user process interference; runtime/container identity and injection controls remain necessary.
- The callback only accepts `https://ossrdbms-aad.database.windows.net/.default` as the Npgsql/OAuth **scope**, and requests `resource=https://ossrdbms-aad.database.windows.net` on the local ACA **REST** endpoint. These strings intentionally differ. It pins `client_id` and `api-version` and sends the platform header **only** in `X-IDENTITY-HEADER`, never in the URL or logs.
- Response: require HTTP 200, JSON, at most 32 KiB, matching `resource`, `token_type=Bearer` and matching user-assigned `client_id`; reject blank/nonprintable/oversized access tokens, invalid expiry, tokens expiring within two minutes or expiring more than 24 hours from the trusted injected clock. Azure returns `expires_on` as epoch seconds, typically a string. No JWT signature validation or real access grant is implied: PostgreSQL must validate the actual Entra access token, the app must validate network/TLS and approved DB role grants.
- Errors: fail closed on missing, malformed, oversized, near-expiry or foreign-identity token, HTTP 401/403/429/302/500 and transport exceptions. Throw only a fixed safe exception without inner details because the backend/transport may echo tokens or `IDENTITY_HEADER` in an exception. Explicit caller cancellation is propagated. No token cache, refresh timer, disk writes, logging, retry or SQL-password fallback is added; a new token is requested for every new physical DB connection made by the separate Npgsql callback. PostgreSQL pool sessions already connected are **not immediately revoked** by token expiry/revocation.

## Offline testing

`tests/backend/TemporalMark.Provisioner.Tests/ContainerAppsPostgresManagedIdentityCandidateTests.cs` uses only an **in-memory HTTP handler**, fixed synthetic client GUID/header, and synthetic, non-issued token strings. Tests verify request path/query/header with no header in URL; wrong endpoint, scope, client ID, response resource/type, expired/future token, nonprintable token, malformed/oversized response, HTTP error/redirect without retry, transport exception sanitization, cancellation, no caching, hardened production handler flags and composition with the unused Npgsql data source **without opening a SQL socket**.

No test in this scope connects to Azure, creates a PostgreSQL role, proves JWT cryptographic validity, checks a live identity assignment or exercises a real ACA networking path.

## Approval gates BEFORE connecting to the active application

1. Have cloud/security/DB owners approve a **distinct SQL-use user-assigned managed identity** and its client GUID, enforce least privilege, attach it only to the applicable Container Apps main process and verify allowed identity exposure. Review actual live `IDENTITY_ENDPOINT` contract, header rotation, system-managed identity policy, network/egress, container process isolation, anti-SSRF controls, logging/telemetry and secrets. The current API identities and Terraform stack are unchanged.
2. In a separate CAB-approved **nonproduction private Azure** environment, create/check Entra PostgreSQL service principals and SQL role mappings, schema/grant separation, API per-tenant access, migration-owner DDL, approver/registrar reviewer grants, token lifespan and renewal, pool invalidation, TLS certificate chains, VNet private DNS, HTTP errors, identity revocation and outage/recovery.
3. Review end-to-end wiring of this token supplier to `EntraPostgresDataSourceCandidate`, then to the API and separately privileged CLI/migrations in a dedicated ADR and RED/GREEN integration tests. Do not infer that Azure control-plane RBAC grants SQL permissions or that the current SQL password-based app can be changed without migration.
4. Preserve and inspect the existing registry, 20 checksummed migrations, audit/seals and full `pg_dump/pg_restore`; plan cross-region/DR, break-glass and safe rollback. Protect/rotate **current and historical Terraform states/backups** that still contain the PostgreSQL administrator password. Do not delete tenant data, weaken immutable retention or disable existing admin credentials without verified migration/cutover.
5. Follow the compliance/QTSP/CAB/AgID and privacy/WORM production gates independently. This prototype is **not a qualified electronic time stamping service**, not an approved Entra PostgreSQL deployment and not legal evidence custody.

## Separately approved PostgreSQL runtime identity resource candidate (#132)

A **distinct** UAI `azurerm_user_assigned_identity.postgres_runtime_candidate` is now modeled in the isolated, **not deployed** `infra/azure/candidates/entra_postgres` Terraform root, separate from the current API's Blob system MI and Key Vault UAI and from the Entra PostgreSQL administrator group. It exports candidate `resource_id` (future ACA identity attachment), `client_id` (pinned selection for this #131 HTTP callback) and `principal_id` (Entra service-principal object used to verify/create future nonadmin PostgreSQL role by approved DB owner). No actual IDs/SQL grants are proved by Terraform mock provider; no identity is attached to Container Apps or made an Azure/SQL administrator. See [ADR 0098](../adr/0098-isolated-postgres-runtime-managed-identity-candidate.md) and [runtime UAI candidate runbook](AZURE_POSTGRES_RUNTIME_UAI_CANDIDATE.md). Both detached .NET candidates remain unused by API/Provisioner/migrations; #128 and #18 still block real authentication and Terraform secret state remediation.
