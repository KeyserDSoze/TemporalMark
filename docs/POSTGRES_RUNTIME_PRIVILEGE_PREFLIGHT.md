# PostgreSQL runtime SQL privilege preflight — isolated/read-only (#133 / ADR 0099)

**Update #134 / ADR 0100 (2026-11-20):** The earlier optional, detached-only #133 SQL preflight is now an explicit **mandatory pre-listen startup gate** when — and only when — the API is configured in the `ContainerAppsEntraCandidate` PostgreSQL mode. It still never changes SQL grants/data, is not invoked by the default password-mode API or by privileged CLIs/migrations, and has **not** been tested against actual Azure Entra SQL principals. Real cloud staging/role custody and Terraform admin state remediation remain #128/#18 OPEN. See [API opt-in runbook](API_POSTGRES_ENTRA_PRELISTEN_CANDIDATE.md), [ADR 0100](../adr/0100-explicit-api-entra-postgres-prelisten-privilege-gate.md). Earlier detached-only text below refers to the #133 historical scope.

**Development/prequalification only.** The standalone verifier from #133 is now **wired into the API only for explicitly selected `ContainerAppsEntraCandidate` mode** under #134 / ADR 0100: a mandatory one-time, fail-closed pre-listen check against the authenticated runtime PostgreSQL session. It is **not** enabled in default `Password` mode, the active Azure Terraform deployment, Provisioner, migration runner or registrar/reviewer CLIs. See [ADR 0099](../adr/0099-detached-readonly-postgres-runtime-privilege-preflight.md), [#133](https://github.com/KeyserDSoze/TemporalMark/issues/133), Azure [#128](https://github.com/KeyserDSoze/TemporalMark/issues/128) and [#18](https://github.com/KeyserDSoze/TemporalMark/issues/18). No new migrations, SQL permissions or Entra provider packages are created. The existing Azure PostgreSQL bootstrap admin password **remains in Terraform state**.

## What the component checks

`src/backend/infrastructures/TemporalMark.Infrastructure/Postgres/PostgresRuntimePrivilegePreflight.cs` exports:

```csharp
await PostgresRuntimePrivilegePreflight.VerifyAsync(
    alreadyOpenAuthenticatedPostgresConnection,
    expectedRuntimeLoginFromApprovedOperatorConfiguration,
    cancellationToken);
```

It **never opens a connection or writes SQL**. The caller must separately authenticate and open an `NpgsqlConnection` with credentials appropriate to its approved deployment; the expected runtime login is a fixed, independently reviewed configuration value **not derived from an HTTP request, OIDC JWT, tenant, log or document hash**. The caller then runs one parameterized, read-only PostgreSQL catalog/ACL `SELECT` against this exact session.

The preflight requires all of these conditions at the time of inspection:

- `session_user = current_user = expected login` and catalog `rolcanlogin=true`; deny superuser, `CREATEDB`, `CREATEROLE`, replication and `BYPASSRLS`.
- Membership of the existing `temporalmark_runtime_group`, with **no direct/transitive membership** of `temporalmark_provisioner_group`, `temporalmark_approver_group`, `temporalmark_credential_registrar_group`, built-in super-privilege groups `pg_monitor`, `pg_read_all_data`, `pg_write_all_data`, `pg_execute_server_program`, `pg_read_server_files`, `pg_write_server_files`, or optional Azure `azure_pg_admin`. The optional Azure role is checked through `pg_roles`, not blindly referenced on open-source installations where it is absent.
- Deny database `CREATE`, schema `public` `CREATE`, direct `INSERT`/`UPDATE`/`DELETE`/`TRUNCATE` on `public.organizations` and `public.organization_memberships`, and `EXECUTE` on privileged legacy `bootstrap_organization` and `bootstrap_verified_organization` functions.
- Require `USAGE` on schema `public`, `SELECT` on organizations/memberships, `INSERT` on the timestamp registry and tenant audit events. Checks use PostgreSQL's **effective** `has_*_privilege` functions instead of only ACL text.
- The return value is **success without any credential or catalog report**, or a generic fixed `InvalidOperationException` without inner exception. Malformed expected login is rejected before SQL; user-initiated cancellation is preserved. SQL errors, missing mandatory groups/functions/tables, network loss, schema drift or unknown privilege state fail closed.

`tests/backend/TemporalMark.Postgres.Tests/PostgresRuntimePrivilegePreflightTests.cs` runs against the existing **real PostgreSQL 17 Docker** fixture with four separate **local-only** test logins:

- **Positive** local `temporalmark_api` with runtime group and no elevated grants: pass; migration count remains 20 before/after.
- **Negative** migration owner/superuser `temporalmark`, provisioning CLI login, independent approver login, and a correct runtime connection with a **different claimed login**: denied, no leaked credential or role string in exception.

The GitHub Docker smoke uses a dedicated `TEMPORALMARK_RUNTIME_TEST_DB` fixture **only for these real local tests**. All other real PostgreSQL migration/tenant-concurrency checks, full logical `pg_dump/pg_restore` tests, Keycloak signed TOTP/PKCE, tenant A/B HTTP 401/403, Playwright and Terraform mock plans must still pass. No live Azure managed identity, Azure subscription, PostgreSQL Entra token or cloud SQL role is used or inferred by this fixture.

## What it does NOT prove

This is a **point-in-time, non-exhaustive** runtime database session security gate: optional when invoked as a detached standalone component (#133), but **mandatory at API startup for explicit `ContainerAppsEntraCandidate` mode** (#134 / ADR 0100). The default on-prem `Password` mode never invokes it. It does not prove the real Azure Entra managed identity exists, belongs to the approved tenant, was issued the right token, is attached to a Container App, or was granted and reviewed the right SQL mapping. It does not prove TLS/private VNet/DNS, complete PostgreSQL object ownership/default privileges, hidden extra functions, unreviewed role groups, security-definer logic, row-level security isolation, future privilege drift or immediately revoke existing pooled DB sessions. For production, independently manage SQL role grants/ownership and continuously re-check actual privileges after migrations/role changes, plus run end-to-end live private Azure data-plane tests with the separately governed UAI and token supplier.

The preflight **is enabled in the current API only when explicit `ContainerAppsEntraCandidate` mode is selected**, before HTTP listening; it is **not enabled** in default password-mode API, migration runner or privileged CLIs. This API-only opt-in is not selected by the active Azure reference Terraform and does not attest real Entra SQL principals. Existing password-based on-prem installations and Azure reference deployment are unchanged. Azure #128/#18 still require approved managed-identity SQL role mapping, distinct migration/registrar/reviewer DB principals, credential rotation/historical state custody, TLS/private connectivity, rollback/restore and CAB. The project is **not** a qualified timestamp provider and no production WORM custody/eIDAS proof is implied.

Official technical sources: [PostgreSQL 17 pg_roles](https://www.postgresql.org/docs/17/view-pg-roles.html), [PostgreSQL 17 system/privilege functions](https://www.postgresql.org/docs/17/functions-info.html), [Microsoft PostgreSQL Entra configuration](https://learn.microsoft.com/en-us/azure/postgresql/security/security-entra-configure), [Azure PostgreSQL Entra managed identity connectivity](https://learn.microsoft.com/en-us/azure/postgresql/security/security-connect-with-managed-identity).

## Evidence/audit append-only SQL ACL prelisten guard (#141 / ADR 0106)

The opt-in API Entra mode now fails startup on a PostgreSQL runtime identity with any effective UPDATE, REFERENCES, DELETE, TRUNCATE or TRIGGER permission on either public.timestamp_registry or public.tenant_audit_events, while still requiring INSERT. To catch both whole-table and **individual-column** UPDATE/REFERENCES, the existing read-only SQL check uses pg_catalog.has_any_column_privilege; DELETE/TRUNCATE/TRIGGER use pg_catalog.has_table_privilege. No application GRANT/REVOKE/DDL, extra SQL connection, migration or production credential is introduced.

[ADR 0106](../adr/0106-postgres-append-only-acl-prelisten.md) / [#141](https://github.com/KeyserDSoze/TemporalMark/issues/141) use genuine PostgreSQL 17 disposable role-per-privilege TDD tests. [Tests-only main 65cb4b0](https://github.com/KeyserDSoze/TemporalMark/commit/65cb4b0206ff286ddbfbb51375463ae98639d0db) produced [RED 44914409424](https://github.com/KeyserDSoze/TemporalMark/actions/runs/44914409424), **14 negative assertion failures and 99 passes among 113 tests**. Every test role first PASSes baseline runtime preflight, then gets one extra table/column privilege (and incorrectly passed the old preflight), followed by verified teardown of that one GRANT, membership and role even on RED failure. The minimal predicate fix is [efb527b](https://github.com/KeyserDSoze/TemporalMark/commit/efb527b23d40762f1f58dee057cc45115cdfbffb). The 20 immutable migration checksums and shared runtime group are unchanged.

**Limitations:** point-in-time SQL ACL sanity only. It does not prove table ownership/DDL policy, runtime role drift prevention, independent WORM evidence sealing, custody/legal qualification, actual Azure UAI SQL mapping, pooled revocation, Terraform password history or CAB. Parent #128/#18, #17, #113/#115, #13/#15 remain OPEN. Official PostgreSQL 17 [privilege functions](https://www.postgresql.org/docs/17/functions-info.html) and [GRANT syntax](https://www.postgresql.org/docs/17/sql-grant.html).

## Tenant organization and last-admin table ACL misgrant prelisten guard (#142 / ADR 0107)

The nondefault `ContainerAppsEntraCandidate` API's one-time, read-only PostgreSQL session prelisten check already demanded SELECT and denied table-level INSERT/UPDATE/DELETE/TRUNCATE on `public.organizations` and `public.organization_memberships`. PostgreSQL 17 separately permits **single-column UPDATE**, **whole-table or individual-column REFERENCES**, and **table TRIGGER** grants. A mis-granted runtime principal could previously pass this check despite these extra rights (including capability to mutate a membership role). [ADR 0107](../adr/0107-postgres-tenant-invariant-acl-prelisten.md) / [#142](https://github.com/KeyserDSoze/TemporalMark/issues/142) extend the existing **single read-only SQL SELECT** so both tenant tables reject any column UPDATE or REFERENCES via `pg_catalog.has_any_column_privilege` and any TRIGGER via `pg_catalog.has_table_privilege`; existing no-INSERT/DELETE/TRUNCATE and #141 evidence/audit ACL denies stay enforced. Nothing grants/revokes rights in the application or changes schema/seed data.

Actual PostgreSQL 17 RED-first [tests-only `main` 7059298](https://github.com/KeyserDSoze/TemporalMark/commit/70592980ac4568f1be0e2d02195537143aebbef0), [CI 44915914633](https://github.com/KeyserDSoze/TemporalMark/actions/runs/44915914633) produced eight **expected** failure assertions with a different disposable login per case (one extra column UPDATE, table/column REFERENCES or TRIGGER). Four additional unrelated failures were caused by exhaustion of PostgreSQL connection slots in the test environment: one Npgsql pool per generated login persisted after the tests. [Source/test patch fa3a581](https://github.com/KeyserDSoze/TemporalMark/commit/fa3a581c1521104e0ccd38b62391b1737e084a27) fixes the SQL ACL denials and sets **`Pooling=false` only for the two disposable role test-fixture connection-string builders**; production/application Npgsql pooling is unchanged. Tests use owner-controlled cleanup of each test GRANT, group membership and generated login and verify the 20 migration ledger entries unchanged.

**Limitations:** this is one point-in-time check on an already-open SQL session, mandatory only in explicitly selected Azure Entra candidate mode. It is not a real Azure UAI/SQL role/grants test, continuous drift monitoring, owner/ALTER/DROP restriction, verified independent tenant administration, RLS, WORM custody, GDPR-DPIA or qualified timestamping. Default OSS/on-prem Password mode remains unchanged; #128/#18/#14 and legal/privacy gates remain OPEN. Sources: [PostgreSQL 17 privilege functions](https://www.postgresql.org/docs/17/functions-info.html), [GRANT](https://www.postgresql.org/docs/17/sql-grant.html).
