# Microsoft Entra PostgreSQL Npgsql 10 candidate — offline, detached (#130 / ADR 0096)

**Update #134 / ADR 0100 (2026-11-20):** The former *detached-only* #130 Npgsql candidate is now composed through a new, **explicitly opt-in, Production-environment-only API branch**, `RegistryPostgres:AuthenticationMode=ContainerAppsEntraCandidate`, with the strict local #131 ACA token supplier and read-only SQL #133 role preflight **before opening HTTP listeners**. The default SQL password path, current Azure Terraform deployment, privileged CLIs and migration runner are unchanged; this opt-in has **not** been used or proven on live Azure, and no Entra PostgreSQL SQL role was granted. See [ADR 0100](../adr/0100-explicit-api-entra-postgres-prelisten-privilege-gate.md) and [current API runbook](API_POSTGRES_ENTRA_PRELISTEN_CANDIDATE.md). The original sections below describe the earlier #130 scoped release, not the latest wiring.

**Development/prequalification only. NOT wired to the API, operator CLI, PostgreSQL migration runner, Azure Terraform or on-prem deployment.** See [ADR 0096](../adr/0096-detached-npgsql-entra-token-candidate.md), scoped [#130](https://github.com/KeyserDSoze/TemporalMark/issues/130), open parent [#128](https://github.com/KeyserDSoze/TemporalMark/issues/128), Azure [#18](https://github.com/KeyserDSoze/TemporalMark/issues/18), and the prior isolated [Entra-only Terraform candidate](AZURE_POSTGRES_ENTRA_CANDIDATE.md).

## Why an isolated candidate first?

The API currently calls `NpgsqlDataSource.Create` with a conventional connection string and the separately privileged Provisioner CLI uses SQL login credentials. `scripts/apply-migrations.sh` uses `PGPASSWORD`. The Azure current Terraform configuration **still persists PostgreSQL admin password** in its resource/state and the standalone Entra-only Terraform candidate #129 was not deployed. Switching the active API or migration owner today would risk breaking identity, migrations, backups and tenant isolation, so this slice adds a **reusable, manually callable .NET library candidate only**:

`src/backend/infrastructures/TemporalMark.Infrastructure/Postgres/EntraPostgresDataSourceCandidate.cs`

The component is part of the existing `TemporalMark.Infrastructure` .NET 10 assembly and uses the **already locked Npgsql 10.0.0** reference, not an Azure-specific mandatory package. The API and Privileged CLI are unchanged and do not invoke it; no process automatically detects Entra/Azure credentials or switches auth. On-prem behavior is preserved.

## Security contract

1. Supply exactly one canonical `<server>.postgres.database.azure.com` Azure PostgreSQL endpoint, `Port=5432`, explicit verified SQL `Username` for a separately created, least-privilege managed-identity PostgreSQL principal and a fixed `Database`. Arbitrary hosts, loopback, public IPs, host lists, private-link alternative hostnames or nondefault port are denied at configuration-validation time. **This is only a hostname syntax check, not VNet/private DNS/IP validation.** The host must resolve privately through a separately approved network topology.
2. Demand `SSL Mode=VerifyFull` for certificate/hostname checking and `GSS Encryption Mode=Disable` to avoid Npgsql 10 default preference for GSS before TLS. Reject configuration with `Password`, `Passfile`, `Trust Server Certificate`, `SSL Key` / `SSL Certificate` or `SSL Password`; **this path is token-only**. Certificate trust roots and chains are independently controlled by the deployment. Npgsql's `ContainsKey()` reports recognized options even when not supplied; use the builder's **explicitly configured `Keys` collection**, avoiding false fail/pass decisions (verified on the real .NET test suite).
3. The caller supplies a trusted async `Func<string,CancellationToken,ValueTask<string>>` token callback. The module **always** supplies the fixed `https://ossrdbms-aad.database.windows.net/.default` scope to the callback. It never builds a scope from an untrusted tenant, JWT, URL or query. The callback must be implemented later using reviewed Entra/Managed Identity credentials and an explicitly pinned identity; the module does **not** call IMDS, Azure CLI, environment default credentials or a live Azure endpoint.
4. Use Npgsql `NpgsqlDataSourceBuilder.UsePasswordProvider`: `OpenAsync()` obtains a fresh token **for each new physical connection**; `Open()` always throws `NotSupportedException` to prohibit a synchronous/fallback SQL password. No module cache, refresh timer or token file is introduced; the caller must ensure the token is valid and not expired and handle token errors under approved operations. Pooled active sessions are **not immediately revoked** by rotating a credential.
5. A blank token, malformed credential callback or failed token acquisition throws a fixed, generic exception **without an inner exception**; an exception from an Azure credential provider could itself contain secrets, so do not pass raw messages to API clients, logs or tracing. Explicit cancellation propagates. No bearer, JWT, token or database password is printed/stored. **This does not eliminate sensitive values from PostgreSQL wire protocol**: Entra token is transmitted as the PostgreSQL password during authentication over TLS.

## Tested offline contract and remaining live gates

The mandatory backend xUnit suite includes `tests/backend/TemporalMark.Provisioner.Tests/EntraPostgresDataSourceCandidateTests.cs`: safe no-socket construction, rejection of arbitrary/multihost/IP endpoints, other port, missing or unsafe role/database, weaker TLS, GSS preference/default, SQL password, passfile and certificate bypass, missing provider, fixed audience, cancellation, blank token, and absence of supplier exception leaks. These tests use **synthetic non-JWT strings only** and do **not open a PostgreSQL socket, validate a certificate, acquire an Entra token or run Azure SQL**.

**Remaining, explicitly not completed (#128/#18):** independently authorize the Entra managed identity; configure and inspect a real PostgreSQL Entra database principal via live administrators; narrow SQL grants, migration-owner and approver/registrar identities, last-admin controls, token issuance, revocation, expiry refresh/connection pool behavior and direct/private TLS validation. Implement and exercise a concrete credential callback in a separately reviewed API/runtime or migration-job rollout with **real Azure staging**, full `pg_dump/pg_restore`/replay, native token expiry and least privilege, signing/evidence audit, WAF/log privacy and CAB-approved rollout/rollback. The current Azure PostgreSQL admin password is STILL stored in Terraform state; secure old snapshots and rotate credentials under documented approval before declaring passwordless deployment.

## Separate ACA managed-identity token supplier candidate (#131)

An **unconnected** HTTP-based Container Apps provider `ContainerAppsPostgresManagedIdentityCandidate` now exposes an async callback `GetTokenAsync` for the previously detached Npgsql `EntraPostgresDataSourceCandidate`. It validates the fixed OAuth `.default` scope, maps it to the **REST** `resource=https://ossrdbms-aad.database.windows.net`, pins an independently approved UAI client GUID, requires local ACA endpoint/header, and checks token identity/expiry with sanitized errors. See [ADR 0097](../adr/0097-container-apps-managed-identity-postgres-token-candidate.md) and [runbook](AZURE_CONTAINER_APPS_POSTGRES_IDENTITY_CANDIDATE.md). Unit tests compose the two objects without opening a real database connection. Neither is used by current API/Provisioner/migration scripts; the live PostgreSQL SQL password in Terraform state and identity/grant/rotation/rollback blockers under #128 remain.

## Generic Npgsql token-shape and post-supplier cancellation hardening (#140 / ADR 0105)

**New scoped change (2026-11-21):** The generic `EntraPostgresDataSourceCandidate.RequestTokenAsync` used as Npgsql's asynchronous password provider previously checked only `string.IsNullOrWhiteSpace` after retrieving a token from a caller-provided credential callback. Its concrete Azure Container Apps supplier already rejected nonprintable/oversized tokens, but the generic adapter itself could still forward a malformed, control-character/newline-bearing, Unicode, or excessively large bearer when a future supplier bypassed that upstream check. It also didn't recheck caller cancellation after awaiting a callback that could ignore the cancellation signal.

Following [ADR 0105](../adr/0105-npgsql-token-shape-cancellation.md) and scoped [#140](https://github.com/KeyserDSoze/TemporalMark/issues/140), the **independent Npgsql boundary now refuses any token outside 1–16,000 printable ASCII characters** (from `!` to `~`, inclusive), without trimming/mutating or echoing the value, and checks caller cancellation again after the callback returns, **before** forwarding to Npgsql. Invalid tokens still result in a fixed generic exception with no original/inner exception, while explicit cancellation preserves `OperationCanceledException`. The accepted upper bound matches the concrete #131 ACA supplier; exactly 16,000 printable characters are admitted. No cache, retry, ambient credential, SQL password fallback, new dependency, SQL migration or Azure deployment was added. The preexisting fixed PostgreSQL audience, passwordless TLS VerifyFull configuration and synchronous-open denial remain.
