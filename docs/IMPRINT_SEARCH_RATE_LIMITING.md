# Shared PostgreSQL document-imprint search admission — scoped pilot #116

**Not qualified timestamping, WORM audit or a GDPR retention policy.** See [ADR 0083](../adr/0083-postgres-atomic-imprint-search-rate-admission.md) and open [parent #115](https://github.com/KeyserDSoze/TemporalMark/issues/115), [#113](https://github.com/KeyserDSoze/TemporalMark/issues/113) and [#17](https://github.com/KeyserDSoze/TemporalMark/issues/17).

## What the gate actually does

Following signed-JWT validation and a fresh active PostgreSQL `tenant_admin` membership check, `POST /api/v1/stamps/search` validates the UTC period, exact 64-character document SHA-256 hex and bounded pagination. It then calls the shared PostgreSQL 17 primary to consume **two atomic fixed-window quotas** in one SQL transaction:

| Scope | Limit | Database time window |
|---|---:|---|
| One authenticated OIDC `sub` within one organization | 12 successful admissions | 60 seconds, UTC epoch aligned |
| All subjects within the same authenticated tenant | 30 successful admissions | Same 60-second window |

These are conservative **pilot constants**, not service-level policy promises. Denied attempts do not increment counters. A denied request returns HTTP `429`, an integer `Retry-After` of 1–60 seconds, `Cache-Control: no-store`, and **no match/list/hasMore/document imprint**. A malformed imprint still receives 400 before quota; unauthorized role/tenant access receives 401/403. This is not a pre-auth network/edge traffic limiter.

Admission precedes the SQL document-imprint registry read and existing independently scoped #114 audit event. Audit must still persist before any successful search metadata is returned; audit outage still fails closed with HTTP 500. An unavailable/corrupted quota database also fails closed, without local allow-list. These events must never be interpreted as legally sealed custody or proof of HTTP delivery.

## Deployment and migration

- Run **V019** via `scripts/apply-migrations.sh` using the separate migration-owner credentials before deploying the new API binary. Earlier V001–V018 must be checksum-verified unchanged. The normal local `docker compose -f docker/compose.yml run --rm migrate` handles a persistent development volume without deleting data. Production Azure and on-prem must execute the same controlled migration job, backup/change approval and restore test.
- All active API replicas must point at **one writable PostgreSQL primary**. This single-primary invariant is essential: independent region/cluster primaries, edge caches, per-process counters and stale read replicas do not jointly enforce the budget. PostgreSQL transaction-scoped advisory locks serialize each tenant across threads/processes, and the same SQL function updates tenant and principal quotas atomically.
- The SQL `SECURITY DEFINER` function `public.consume_imprint_search_rate(uuid,text)` is callable only by the runtime group. Its two counter tables are not directly readable or writable by that group; migration/schema owners remain privileged. The function uses `pg_catalog,pg_temp` search path and qualified table names. If permission, primary database or clock integrity fails, deny traffic and investigate; do not skip or bypass the limiter.
- Monitor non-sensitive aggregate 429 rates and primary-DB availability under approved telemetry, **never** raw searched SHA-256, bearer, HTTP JSON body or the requester’s credential. Set no reverse-proxy body recording. Production ingress/proxy log validation and independent DPIA review are still required by #115. A **scoped web-Nginx container access-only format** strips request URL/headers/body and IP from its own normal access events (#117; [runbook](NGINX_ACCESS_LOG_PRIVACY.md)), but Azure-managed ingress, external proxies, ASP.NET Core/error logs and production telemetry pipelines remain unverified.
- Rate tables store authenticated OIDC **subject IDs**, tenant IDs, last window and count; these are personal/behavioral metadata. The normal V019 admission function opportunistically deletes up to 32 principals and 16 tenants whose state is over 3 minutes old, **only when another request invokes it**. New forward-only **V020/#118** additionally provides an **owner-only, bounded, manually invoked cleanup** for inactive principals and tenants even without traffic, preserving active counters and returning aggregate deletion counts only (see [owner runbook](IMPRINT_RATE_COUNTER_CLEANUP.md), [ADR 0085](../adr/0085-bounded-owner-imprint-quota-cleanup.md)). **No automatic scheduler, guaranteed idle-row TTL, privacy-approved cadence, backup erasure, DPIA/legal policy or production maintenance verification exists yet**. Those remain open #115/#113; do not deploy as a privacy-complete service.
- No new Azure-only dependencies or secret requirements. Azure managed PostgreSQL and OSS on-prem PostgreSQL must apply the same constraints. Multi-primary, network-level DoS, reverse proxy/bodies, signed audit custody, real QTSP/CAB approval and account/MFA assurance remain separate release gates.

## Deterministic PostgreSQL server-minute integration evidence (#135 / ADR 0101)

The original V019 contract is a **fixed PostgreSQL UTC epoch-minute**, not a rolling 60-second interval: up to **12 admitted requests per authenticated OIDC subject** and up to **30 per verified tenant** in a single `floor(extract(epoch FROM clock_timestamp()) / 60)` bucket. A 31st request shortly after a **new** bucket starts is correctly admitted, even when the immediately preceding minute had exhausted its budget. Conversely, a 31st request *within the same bucket* must receive generic HTTP 429 / `Retry-After` 1–60 without returning search match data. The PostgreSQL server clock is authoritative, not the API runner's clock. Near a bucket transition, a fixed-window rate limiter can admit 30 requests at the end of one minute and another 30 at the start of the next; this pilot does **not** claim rolling or sliding-window protection.

The real PostgreSQL 17 integration tests now use test-only `SearchQuotaServerMinuteEvidence.RunAsync` to sample the **same server** `clock_timestamp()` epoch minute both before and after the **entire** principal/tenant/concurrency quota exercise and the independently owner-read SQL counters. Only a complete scenario whose start and end buckets match may assert the 12th permitted/13th denied and 30th permitted/31st denied; actual `hits` and maximum per-principal state are also checked. If a server bucket changes, the observation is correctly **inconclusive**, and the test reruns against a **fresh disposable tenant** at most three total attempts. If all three cross a minute boundary, the test **fails**; it never silently skips, spins, sleeps or weakens the threshold. A SQL exception or genuine within-bucket limit breach fails immediately. Synthetic unit tests prove the decision rejects a crossed-window observation and fails closed after three rollovers; they do not replace the real database clock checks.

A separate **real PostgreSQL** rollover regression uses a **test-only migration-owner SQL connection** to seed a disposable tenant's original V019 rows as *already exhausted* (tenant `hits=30`, actor `hits=12`) with a `window_start` in the **previous server epoch-minute**. A real call via the normal restricted runtime login must then return `allowed=true`, reset both counters to 1 in the same new minute, and keep their `window_start` values aligned and strictly newer than the old rows. This requires no wall-clock waiting, fake SQL function, production GRANT, SQL migration edit or API change. Other tests continue to enforce future clock rollback rejection, concurrent sessions, 401/403, `429`, tenant spoof denial and fault closure.

**Investigation caveat:** the historical CI [44824634172](https://github.com/KeyserDSoze/TemporalMark/actions/runs/44824634172) had 94/95 PostgreSQL tests with an unexpected 31st request allowed, but its logs did **not** record server bucket values. A transition is a plausible and directly testable explanation, **not forensic proof** of that exact historical failure. The new tests distinguish real within-bucket rate bugs from correct boundary resets and preserve the evidence needed for future regressions. See [ADR 0101](../adr/0101-postgres-verified-epoch-minute-quota-test-evidence.md) and [#135](https://github.com/KeyserDSoze/TemporalMark/issues/135) for actual RED/GREEN final-SHA CI evidence.

**No product change:** V019/V020, the API and gateway, on-prem and Azure runtime, principal/tenant SQL ACLs, SQL `SECURITY DEFINER`, actual database 60-second limits and 20 immutable migration checksums are unchanged. Existing [#115](https://github.com/KeyserDSoze/TemporalMark/issues/115) and [#113](https://github.com/KeyserDSoze/TemporalMark/issues/113) remain OPEN for unverified pre-auth/edge flood protections, multi-primary/region failover, Azure ingress telemetry, GDPR actor metadata retention/deletion/DPIA and legal privacy policy. Independent WORM/eIDAS/QTSP gates remain OPEN.

## Pre-auth HTTP body resource budget for sensitive imprint lookup (#136 / ADR 0102)

A **separate**, per-request **4,096-byte** JSON body ceiling now applies only to `POST /api/v1/stamps/search`, at two independent entrypoints: direct .NET 10 Kestrel (including access that bypasses the frontend via Azure-managed ingress) and the pinned Nginx web reverse proxy used by OSS on-prem and as Azure's frontend image reference. Kestrel sets its `IHttpMaxRequestBodySizeFeature.MaxRequestBodySize` before `UseAuthentication`, returns a generic **413** + `Cache-Control: no-store` immediately for declared Content-Length >4096, and enforces an actual stream read cap on **chunked/unknown-length** bodies; if the feature is unavailable/read-only it fails closed. For the single exact Nginx search location, `client_max_body_size 4k` rejects a known oversized body before the proxy buffers/passes it. This does NOT adjust SQL V019 12/actor + 30/tenant per PostgreSQL UTC fixed minute, JWT/active-role checks, `429`/Retry-After, valid JSON search, the protected search audit, or any migration. It is not an anonymous request-per-second/IP quota. Existing `/stamps/issue`, exports, PWA and OIDC paths remain unchanged.

Real container tests check 4096 bytes still reaches anonymous JWT **401**, 4097 returns **413** on both API and Nginx, direct Kestrel uppercase route match, other POST unaffected, minimal Nginx 413 access event and absence of synthetic imprint/query/header/JSON/body canaries in real web/API stdout+stderr; a separate real **Keycloak-signed JWT + chunked oversized request** must also be **413** with no matching data. Exact source and runtime proof is tracked [#136](https://github.com/KeyserDSoze/TemporalMark/issues/136), [ADR 0102](../adr/0102-scoped-imprint-search-body-budget-kestrel-nginx.md) and [operator runbook](IMPRINT_SEARCH_BODY_BUDGET.md).

**Residuals #115/#113 remain OPEN:** Nginx error logging under unexpected paths, Azure managed ingress/Log Analytics/CDN/WAF, operator-customized sidecars, per-IP pre-auth rate/connection/timer/slow-read protection, personal actor `sub` retention/backup erasure/DPIA, fixed-minute burst behavior, single writable PG primary/HA governance and legal qualified timestamp/WORM stop lines. Even the 4KiB cap does not prevent repeated small requests or incomplete chunked network consumption; no live Azure claim.
