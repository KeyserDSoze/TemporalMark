# Azure Terraform reference — pre-qualification ONLY

This stack lays out a **reference development architecture** using native Azure services: resource group, VNet, delegated subnets, private PostgreSQL Flexible Server, versioned Blob evidence container with an **unlocked** immutability policy, Log Analytics, Container Apps API/web with system-managed identity, and RBAC.

## Prerequisites
Azure subscription with resource-provider registrations; Terraform >=1.8; Azure CLI credentials, Azure Container Apps and PostgreSQL quota. Build and publish images separately. The web image embeds `VITE_OIDC_AUTHORITY` at build time; it must match the target public HTTPS OIDC issuer. Provide a valid tenant-aware OIDC provider, not development Keycloak.

```sh
cd infra/azure
cp terraform.tfvars.example terraform.tfvars
# Replace example strings; use secure secret injection, never commit real passwords.
terraform init
terraform plan
terraform apply
```

**Default network safety (#123 + #124):** The **entire Container Apps environment now uses an internal VNet load balancer by default** (`internal_load_balancer_enabled=true`), in addition to the web and API apps having internal ingress. `enable_public_web_ingress=false` (the default and checked-in example) keeps these two boundaries internal; `frontend_url` is `null`. The explicit operator opt-in `enable_public_web_ingress=true` switches BOTH the environment to external/public mode and the web app to external ingress, but **API app ingress stays internal**; insecure HTTP stays disabled for both. This is an intentional exposure decision requiring **independent WAF/ingress-log/DPIA/security/CAB approval**, not evidence that such approval exists, and this stack still creates no WAF or private endpoint. **Changing an existing environment's internal-load-balancer property may require replacing the environment** and changing routing/private DNS, so never apply an unreviewed state transition on a production workload. An app's internal ingress only allows traffic from other apps in the same environment; it does not mean every VNet caller can access it. See [environment network runbook](../../docs/AZURE_INTERNAL_ENVIRONMENT.md), [private web ingress guide](../../docs/AZURE_PRIVATE_INGRESS.md), [ADR 0091](../../adr/0091-azure-internal-container-app-environment.md), [ADR 0090](../../adr/0090-azure-private-default-web-ingress.md).

**Evidence storage network safety (#125):** The evidence Storage Account now **disables its public network endpoint** and requires HTTPS; the VNet has a **dedicated Blob Private Endpoint**, the `privatelink.blob.core.windows.net` DNS zone and a linked nondelegated subnet. Its container remains private, Shared Key disabled and the immutability policy deliberately **unlocked**. Terraform's AzureRM provider uses Azure AD for Blob data-plane management, and the container is ordered after the private endpoint and DNS link. A **real Terraform apply from an ordinary public GitHub-hosted runner can fail** because the Storage container resource requires data-plane access to the private endpoint; use only a reviewed VNet-connected runner with DNS and RBAC, or a separately approved ARM control-plane provisioning design. This is a **deployment blocker**, not something to bypass by temporarily exposing Storage. See [private Blob operator guide](../../docs/AZURE_EVIDENCE_BLOB_PRIVATE_LINK.md) and [ADR 0092](../../adr/0092-private-azure-blob-evidence-network.md). No real Azure access or independent legal WORM custody is proved by the mocked CI.

**Important pilot limitations / blockers:**
- The API requires **versioned SQL migrations** in `scripts/migrations` (see `docs/DATABASE_MIGRATIONS.md`); the separate `scripts/apply-migrations.sh` runner must be run from within the VNet after provisioning. A production Azure migration job is **not** wired yet; `scripts/postgres-init/` is a development fixture, not an Azure upgrade mechanism.
- A preconfigured OIDC authority and registered web/API clients are required. Tenant admin identities and memberships are not automatically enrolled on Azure.
- **PostgreSQL server bootstrap administrator password still enters Terraform state** through `var.postgres_password` and is **not fixed by #127**. The API registry connection value no longer does: it is an external version-pinned Key Vault reference plus a dedicated user-assigned identity. Prior state snapshots may still contain the old connection string and need independent credential rotation/state custody. Entra-only PostgreSQL administration, migration credentials and protected state remain #18 release blockers. See [ADR 0094](../../adr/0094-azure-api-keyvault-bootstrap-secret-reference.md) and [Key Vault runbook](../../docs/AZURE_KEY_VAULT_REGISTRY_SECRET.md).
- No HSM/TSU signer, trusted UTC(k) implementation, RFC 3161 issuing API, historical Trusted List verifier, signed manifest, independent immutable evidence writer, WAF, SIEM correlation or DR drill is provided yet.
- Blob immutability is intentionally **unlocked**; locking is irreversible. Obtain retention, privacy and CAB/legal approval before selecting and locking a production policy. The platform's initial indefinite retention policy is **not** fulfilled by the simple retention-days setting.
- Logs in Log Analytics have 30-day interactive retention, not legally sufficient evidence preservation. **V020/#118 adds an owner-only manually executed SQL function** to purge idle subject/tenant rate-counter rows on the shared PostgreSQL 17 primary (see [operator runbook](../../docs/IMPRINT_RATE_COUNTER_CLEANUP.md)); Terraform does **not** install a maintenance scheduler or approve a retention/DPIA policy. SQL owner credentials and schema migrations need independent change control. The **shared frontend Nginx image** uses an explicit minimal stdout access format (only HTTP status, method and duration), with a disposable Docker image/live HTTP privacy regression documented in [Nginx access-log runbook](../../docs/NGINX_ACCESS_LOG_PRIVACY.md) / ADR 0084. The shared .NET 10 API binary also filters normal ASP.NET Core request diagnostics and registers zero-field HTTP logging options (#119; [API diagnostics runbook](../../docs/API_LOG_PRIVACY.md)) and is tested separately using fake request canaries on the running Docker API. **Azure Container Apps managed public ingress/access telemetry, API warning/error/exception logs, external WAF/CDN/gateway, Nginx error logs, Log Analytics collection and backup retention were NOT tested or approved by these container-only changes.** Independently inspect deployed images, every effective ingress/log sink, body/header capture and legally approved deletion/DPIA before deployment; #115/#113 remain OPEN.
- Azure pricing, scale, network segmentation, region, security posture and HSM choice require CAB/architecture review; Terraform creation alone proves no QTSP compliance.
- **When explicitly made public**, the API frontend has **no application gateway/WAF configured** in this reference. The default ACA environment and web ingress are private under #123/#124. **Scoped #120 / ADR 0087 rejects mutable API/web image tags at Terraform PLAN time:** both image input variables require lowercase OCI SHA-256 manifest digests (`registry/repository@sha256:<64 hex>`). Plan-only mocked-provider Terraform CI checks 11 success/negative cases. The sample `.tfvars` digests are deliberately FAKE and must be replaced using a reviewed manifest digest obtained from the real registry after publishing. See [Azure image digest release guide](../../docs/AZURE_OCI_DIGEST_IMAGE_GUARD.md). **This does not verify OCI publisher signatures, SBOM/provenance, image vulnerabilities, Azure runtime pull/revision, private ACR identity, production rollout or CAB approval**; those remain under #18/#115.

For audit work consult `docs/COMPLIANCE.md`. Validate region-specific service SKUs and Terraform provider behavior before applying.

## Deployment OIDC issuer syntax guard — #122, ADR 0089

`oidc_authority` now uses a strict plan-time HTTPS FQDN syntax check rather than just accepting the `https://` prefix. The API receives this value as `Authentication__Authority`. Validated formats support reviewed Keycloak realm paths and tenant-specific Entra OIDC paths; unqualified `http://`, `https://` without a hostname, `localhost`, IP literals, URI userinfo/credentials, queries, fragments, empty/`..` segments and trailing slashes are rejected. CI runs **17 real plan-only mocked Terraform cases** with no Azure credentials or resource deployment, plus the existing OCI image digest 11-case suite. See [OIDC issuer operator guide](../../docs/AZURE_OIDC_ISSUER_GUARD.md), [ADR 0089](../../adr/0089-azure-oidc-issuer-input-validation.md), [OIDC Discovery](https://openid.net/specs/openid-connect-discovery-1_0.html).

**The issuer syntax does NOT prove the identity provider is trusted.** Before Azure production, independently review the approved issuer and discovery metadata `issuer` exact match, TLS/JWKS trust, allowed algorithms and role/tenant binding, current account revocation, and **frontend build-time `VITE_OIDC_AUTHORITY` vs API runtime authority parity**. No provider allowlist or actual Entra/Keycloak network/metadata verification is performed by Terraform; deployment state credentials, managed Azure ingress, log retention, CAB/AgID qualification and reviewer/registrar V015/V016 controls remain blocked under #18/#25/#115/#13/#15. The example `terraform.tfvars.example` remains synthetic, not a valid deployment.

## Post-deployment private Blob check (#126, ADR 0093)

After an **approved** Azure deployment, an authorized VNet-connected runner can invoke `python3 scripts/azure_private_blob_preflight.py --subscription-id ... --resource-group ... --storage-account ... --private-endpoint ...` from the repository root. It checks account public/Shared Key/TLS policy, approved Blob PE, private NIC/DNS match and a read-only Entra `az storage blob list` without printing blob identifiers. See [the exact runbook](../../docs/AZURE_EVIDENCE_BLOB_PRIVATE_LINK.md) and [ADR 0093](../../adr/0093-live-azure-blob-private-runner-preflight.md). This is **not automatically run in public CI**; CI tests are simulated. It is not real application PUT/GET, an external public denial test, a solution to the existing AzureRM container Terraform private-runner bootstrap requirement or legal WORM evidence. Release blockers #18/#115/#17 remain open.

## API database secret reference (#127, ADR 0094)

The API now uses `azurerm_container_app.api.secret.key_vault_secret_id`, not a direct connection string value. Configure the two **non-secret identifier** inputs `registry_connection_secret_uri` (approved, version-pinned Key Vault URI) and `registry_connection_key_vault_id` (ARM ID of exactly the same dedicated RBAC-enabled vault). Terraform creates a dedicated user-assigned managed identity before Container Apps creation, assigns `Key Vault Secrets User` at that vault, and attaches it alongside the existing system-assigned Blob writer identity. No Key Vault secret *value* is imported into Terraform state by this specific app secret configuration. Only a reviewed externally provisioned secret will be usable; the provided .tfvars values are fictional.

**Mandatory actual Azure gates:** provision and approve dedicated Key Vault/secret independently; test private Key Vault DNS/firewall/Entra role propagation and error/revision behavior, least-privilege database login, vault rotation and live end-to-end staging API connectivity on an authorized runner. Review old state/backups and rotate any formerly embedded connection string. **PostgreSQL administrator password is still in Terraform state** and the broader #18 secrets architecture/controlled migration and managed storage/private runner are not complete. See [operator guide](../../docs/AZURE_KEY_VAULT_REGISTRY_SECRET.md). CI new **10 plan-only mock tests** do not verify real Azure access or deployment.

## Isolated PostgreSQL 17 Entra-only candidate (#129 / ADR 0095)

The **new** directory `infra/azure/candidates/entra_postgres/` is an independent, **non-applied, prequalification-only Terraform root**, not referenced by this existing Azure deployment. It defines a new distinctly named `-entra-candidate` server, explicit Entra-only auth with SQL password authentication disabled, private PostgreSQL subnet/DNS, a reviewed Microsoft Entra **group administrator** and a separate candidate database ordered after admin creation. CI only runs mock-provider `terraform test`, plus a mandatory Python source-policy check proving that the candidate source has **no SQL admin credential variable/assignment** (computed administrator attributes are unknown in a mocked plan). Consult [ADR 0095](../../adr/0095-isolated-entra-only-postgres-candidate.md) and the [candidate runbook](../../docs/AZURE_POSTGRES_ENTRA_CANDIDATE.md).

**Do not run `terraform apply` on this candidate** or point it at the existing registry: the current API, CLI and migration jobs are not Entra-token-ready. This main Azure reference **still contains `administrator_password = var.postgres_password`** and its current/historical Terraform state may contain PostgreSQL admin credentials, so #128 and parent #18 remain OPEN for approved end-to-end token authentication, safe state/credential rotation, migration-role grants, real Azure VNet/DB/Entra validation, backup/DR and CAB change control. A new Terraform module and synthetic CI plans alone do not make the active solution passwordless or production-qualified.
