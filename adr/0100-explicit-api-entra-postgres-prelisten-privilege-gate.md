# ADR 0100 — Explicit opt-in Azure Container Apps Entra PostgreSQL runtime API composition with pre-listen SQL privilege gate

Status: **Accepted for scoped, undeployed pilot [#134](https://github.com/KeyserDSoze/TemporalMark/issues/134)**, 2026-11-20. Parent #128/#18 Azure PostgreSQL auth migration/production remains OPEN. No Azure apply, live staging, SQL role creation or credential rotation is authorized by this ADR.

## Prior architecture and authoritative sources

Reviewed ADR 0001, 0094–0099; docs/COMPLIANCE.md, ROADMAP.md, THREAT_MODEL.md, DATABASE_MIGRATIONS.md, ENTRA_POSTGRES_NPGSQL_CANDIDATE.md, AZURE_CONTAINER_APPS_POSTGRES_IDENTITY_CANDIDATE.md and POSTGRES_RUNTIME_PRIVILEGE_PREFLIGHT.md; current `src/backend/applications/TemporalMark.Api/Program.cs`, .NET 10 Infrastructure Npgsql 10 candidate and restricted PostgreSQL roles, current Azure Terraform and private Blob/Key Vault dependencies, 20 immutable V001–V020 migrations, real Docker PostgreSQL and signed Keycloak two-tenant HTTP CI. The existing API currently always uses `NpgsqlDataSource.Create(ConnectionStrings:Registry)` with a conventional password connection string. The active Azure reference still configures `azurerm_postgresql_flexible_server.registry.administrator_password = var.postgres_password` in Terraform state; the isolated Entra-only server and dedicated UAI Terraform **candidates have not been deployed**.

Microsoft [Managed identities in Azure Container Apps](https://learn.microsoft.com/en-us/azure/container-apps/managed-identity) documents local `IDENTITY_ENDPOINT` and secret `IDENTITY_HEADER`, optional explicitly selected user-assigned `client_id`, and a platform-local endpoint that is **not** an Azure PostgreSQL SQL grant. Microsoft [Azure PostgreSQL managed identity connectivity](https://learn.microsoft.com/en-us/azure/postgresql/security/security-connect-with-managed-identity) requires an authenticated Entra database principal and separately approved database privileges. Npgsql 10 [async password provider](https://www.npgsql.org/doc/security.html) supports passing Entra access tokens to new physical connections. Prior #130 and #131 candidates validate canonical Azure PostgreSQL host, `SSL Mode=VerifyFull`, disabled GSS, no SQL password/passfile, hardened pinned-loopback ACA HTTP token resource/scope/client ID, and safe exceptions. Prior #133 provides an **already open** PostgreSQL session read-only `PostgresRuntimePrivilegePreflight.VerifyAsync` to reject an overprivileged application login. All three components have independent offline/local regression tests but previously **no API integration**.

## Decision

1. Add exactly one nondefault explicit API `RegistryPostgres:AuthenticationMode` selector: unset or literal `Password` preserves the current `NpgsqlDataSource.Create(ConnectionStrings:Registry)` behavior and OSS on-prem/legacy Azure reference; literal `ContainerAppsEntraCandidate` chooses the previously reviewed Npgsql token-only Entra candidate and ACA MI token supplier. Any other value, case, whitespace or typo **fails startup** rather than falling back to SQL credentials. No automatic cloud detection, `DefaultAzureCredential`, SQL password downgrade, port/ip fallback, mutable feature flag from an HTTP request or required Azure NuGet dependency.
2. Enable Entra path only with ASP.NET **Production** environment **and** all explicit operator-owned inputs: existing `ConnectionStrings:Registry` must be **passwordless** canonical Azure PostgreSQL FQDN, port 5432, explicit username and database, `SSL Mode=VerifyFull` and `GSS Encryption Mode=Disable`; `RegistryPostgres:UserAssignedClientId` must be a strict nonzero GUID; `RegistryPostgres:ExpectedRuntimeLogin` must match the SQL connection-string username EXACTLY. Separately use **platform-supplied process env** `IDENTITY_ENDPOINT` and `IDENTITY_HEADER` (never appsettings/HTTP): validate local loopback endpoint, refuse arbitrary/IMDS host, require confidential header. The expected login and client ID are deployment-reviewed fixed metadata, never tenant claims.
3. Implement a small Infrastructure-owned `ContainerAppsEntraApiRegistryCandidate` wrapper composing #130/#131, owning the Npgsql datasource and HTTP identity token supplier. Creation validates all input **before** network or token acquisition; if Npgsql datasource construction fails, dispose token supplier. Only a successful returned wrapper owns the resources; dispose both on application stop. Validate input failure without logging or including host/credentials/platform header in exception or inner exception. This is a bounded offline construction candidate and keeps on-prem dependencies identical.
4. The API registers the wrapper's single `NpgsqlDataSource` in DI only for selected Entra mode; before calling `app.Run()` or binding HTTP listeners, execute a **bounded cancellation** first `OpenConnectionAsync` (real Entra token + PostgreSQL TLS login in an actual deployment) and then #133 read-only `PostgresRuntimePrivilegePreflight.VerifyAsync` on the opened SQL session against the exact approved runtime login. Any token, SQL, timeout, role-check or configuration failure **aborts startup** with one generic safe error without original exception/inner details. No background retry or SQL fallback. One pre-listen check does not prove full lifecycle security or prevent later privilege drift.
5. Do NOT change Azure Terraform/Container Apps identity assignments, Key Vault secret reference or live PostgreSQL server password, CLI, migrations, on-prem compose, API endpoint authorization, qualified timestamp service configuration or tenant isolation. Existing main Azure deployment has no selected new auth mode and remains password-based until separately approved staged cutover. No actual Azure token, role grant, ACL/ownership, private DNS/TLS or Entra SQL identity is tested by fake offline token tests or existing PostgreSQL local credentials.
6. **TDD before implementation**: commit RED xUnit tests in the existing Provisioner.Tests for composition (valid inputs no token/socket on construction, wrong runtime SQL username, missing/invalid UAI client GUID, untrusted endpoint, missing/CRLF header, password or passfile/TLS bypass, wrong Azure host, safe error messages, expected exact default). Commit mandatory Python API source policy in the existing backend job requiring mode selector, explicit non-development guard, pre-listen async open+privilege preflight and no appsettings platform header/identity endpoint. Observe real GitHub Actions RED. Then implement minimal wrapper and API changes; preserve all locked dependencies and 20 migration checksum files, and require exact docs-inclusive final SHA four-job CI plus aggregate status.
7. Update the operator runbook and ADR/docs. Live Azure staging still requires independently approved UAI directory ownership, tenant/client/principal IDs, actual Entra PostgreSQL nonadmin SQL role/grants, private network, cert verification, token refresh/revocation, TLS and connection pool/session behavior, independent CLI/DDL/reviewer/registrar role bridges, historical Terraform state password rotation, backups, CAB break-glass and rollback. This **opt-in mode is not automatically production-authorized** and must fail closed without these resources. On-prem remains open-source capable.

## Limitations and closure contract

Close only #134 upon exact docs-inclusive SHA success of backend/frontend/terraform/docker-smoke and combined `temporalmark/ci-4-core-jobs=success` with real PostgreSQL dump+restore and signed Keycloak MFA/two-tenant API tests; keep #128/#18/#115/#17/#13/#15 OPEN. This does not certify eIDAS qualified timestamping, QTSP status, legally accepted retention/WORM, a real Azure connection, or the removal of a Terraform-stored admin password.
