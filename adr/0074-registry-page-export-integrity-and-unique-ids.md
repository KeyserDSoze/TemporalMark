# ADR 0074 — Validate timestamp evidence and uniqueness before listing/export delivery

Status: Accepted for **limited registry integrity hardening**, 2026-11-18. [#105](https://github.com/KeyserDSoze/TemporalMark/issues/105), child of open WORM/export [#17](https://github.com/KeyserDSoze/TemporalMark/issues/17).

## Reviewed baseline and threat

Reviewed [ADR 0004](0004-evidence-time-and-retention.md), [ADR 0002](0002-qualified-vs-delegated-timestamping.md), [ADR 0072](0072-canonical-sha256-base64-issuance-ingress.md), `TimestampRecord.Validate()`, `TimestampRegistryService`, `ITimestampRegistry`, its real PostgreSQL repository's `WHERE organization_id = @org`/ordered pagination, Business xUnit regression tests, the authenticated `GET /stamps`, `GET /stamps/{id}/receipt` and `GET /stamps/export` API routes, `docs/COMPLIANCE.md`, `docs/THREAT_MODEL.md` and `docs/ROADMAP.md`.

`DownloadReceiptAsync` already verifies `record.Validate()`, including matching SHA-256 of retained DER, and `ExportZipAsync` verifies records *during* ZIP construction. But `PageAsync` checks only tenant and UTC period: a repository bug, tampering, or a corrupt database row can return an unverified/altered response DER and metadata as ordinary listing data without local consistency rejection. In addition, the registry API itself does not reject **duplicate record IDs** in a page/period export. A corrupted/compromised repository could produce repeated `tokens/{id:N}.tsr` ZIP entry names and ambiguous manifest rows. Normally PostgreSQL PK constraints exclude duplicate IDs in the same table, but business read boundaries should fail closed on inconsistent results.

## Decision

1. Keep DB ownership and API tenant access checks unchanged. After `ITimestampRegistry.PageAsync` and `ForExportAsync` return, but **before** returning a page or constructing any ZIP bytes, validate each returned record's organization ID, requested `UtcPeriod` membership, and existing `TimestampRecord.Validate()` integrity. Reject duplicate `Id` values within the *same returned collection* with a generic `InvalidOperationException`; never return a partial page or ZIP if malformed. A single common private helper is used by both methods to avoid divergent policy.
2. Continue bounding synchronous exports to `ExportLimit=10000`, rejecting 10001 before any ZIP allocation. Keep DownloadReceipt's own tenant/integrity checks. Do not change SQL schema, authorization, API routes, original DER bytes, tokens, or manifestation fields.
3. TDD: ADR first, RED-first Business tests proving a tenant-owned page rejects altered `TokenSha256Hex` and changed DER, and that both page and export refuse duplicate IDs; retain positive page and unique export and prior cross-tenant tests. Implementation minimal. Update runbook/threat/roadmap and issue; only close on an independently observed **exact final documentation-inclusive main SHA** `temporalmark/ci-4-core-jobs=success` with real backend/frontend/docker-smoke/terraform logs and test counts.
4. Explicitly **not** protection against a malicious actor who rewrites **both** DER and stored hash, forges issuer evidence or inserts coherent new records. Also not a cross-page unique/snapshot witness, complete export coverage proof, signed manifest, independently witnessed archive, WORM object-lock, protected legal retention, historical QTSP qualification, CAB/AgID certification or attested UTC(k). These remain #17/#15/#13. Any new `InvalidOperationException` indicates a trust-boundary failure that must be surfaced as a failed request rather than leaking/serving corrupt data; complete API error response hardening requires its own review. All pilot receipts remain `Unverified`.

## Deployment and residual risks

Exactly the same business service is used on OSS on-prem and Azure; no cloud-specific feature, credentials or database migration. SQL V015/V016 registrar stop-line and FIDO MDS trust gates remain frozen. This is a **SHA-256 local consistency check**, never proof that a timestamp was issued by a qualified TSA. Period exports still cap at 10000; an independent signed high-water/manifest witness and DR evidence are required before legal claims.
