# ADR 0036 — Fail-closed, independently persisted signed *test* high-water journal

Status: **accepted for offline .NET 10 test-only monotonic journal and real PostgreSQL rollback regression; not an approved immutable witness** — 2026-11-16. Focused [#67](https://github.com/KeyserDSoze/TemporalMark/issues/67), child of OPEN #64/#61/#57. Reviewed ADR 0032–0035, V017, docs/MDS_CRL_FULL_PGDUMP_RESTORE_TEST.md, existing RSA-PSS sealed test witness and .NET 10 FileStream exclusive-open/Flush(true) semantics.

## Threat and trust boundary

#66 tests a real entire logical PostgreSQL `pg_dump/pg_restore` but the latest seal SHA remains only an ephemeral test-process variable. This slice introduces an **actual separate on-disk file**, *not stored in PostgreSQL or restored by pg_restore*, with an RSA-PSS SHA256 signed, hash-linked, strictly increasing high-water event sequence. Normal startup MUST fail if the file is absent, truncated, malformed, invalidly signed, expired or for the wrong source policy/key; no automatic file reset/repair. A distinct explicitly invoked test bootstrap operation may create a **new** empty file only using `CreateNew` (never overwrite). An API append operation must open it `FileShare.None`, validate the *entire* chain and only append a strictly newer, independently signed event, then `Flush(flushToDisk: true)`. A read independently opens and verifies the entire file, and provides **only a synthetic `UNAPPROVED` latest seal digest**.

No self-provisioned or caller-supplied RSA key is a FIDO Alliance trust root. Here the source policy, RSA public key and its SPKI SHA256 pin are **provided by the test harness**, not approved and securely distributed by CAB, HSM or an isolated security operator. RSA signatures verify the exact original canonical ASCII event bytes, never normalized data. The journal is a **normal mutable file**; a host administrator or storage backup agent can delete, replace, truncate, copy an older whole journal, or change the caller's pinned key. `FileShare.None` serializes normal cooperating processes only on the same filesystem, not privileged host tampering, races through symlinks, network mounts or multi-region split-brain. `Flush(true)` asks the OS to flush buffered writes but does not constitute WORM or guaranteed power-loss safe transaction/parent directory sync.

## Protocol and narrow implementation

- Header: exactly three LF-terminated ASCII lines: fixed `TEMPORALMARK-UNAPPROVED-SIGNED-FILE-HIGHWATER-1`, uppercase 64-hex source policy SHA256 and uppercase 64-hex externally supplied signer-SPKI SHA256. No whitespace, extra headers or alternate encodings.
- Each event is one LF-terminated `Base64(originalSignedPayload)|Base64(detachedRsaPssSignature)` line, strict canonical Base64 with one `|`. The UTF-8-compatible original payload is strictly printable seven-bit ASCII with terminal LF and precisely six fields plus terminal empty field: `TEMPORALMARK-UNAPPROVED-SIGNED-FILE-HIGHWATER-EVENT-1`, policy SHA256, strictly positive canonical integer version, uppercase 64-hex SHA256 of the corresponding ADR 0034 seal, uppercase 64-hex SHA256 hash of the **previous original signed payload** (first entry uses 64 zeros), and strictly positive canonical UTC Unix-seconds observation time. Every event is signed by the pre-provisioned public RSA key (2048–4096) with maintained `RSA.VerifyData(SHA256, PSS)`.
- Re-read and verify **all** entries under the same exclusive stream before read or append. Enforce matching policy/pinned SPKI, signature and hash chain, strict serial increase and monotonic observed seconds, no future observations and latest observation less than 24 h old, max 128 events, max 128 KiB total file, max signed payload 512 bytes, no empty/trailing/partial lines or alternate Base64. Reject corrupt/missing file, stale/future clocks, wrong key/pin, unknown source policy, lower/equal version, same-version different digest, unbounded data, attempts to continue broken chain and concurrent writers. Return only `UNAPPROVED/TEST_FILE_HIGH_WATER_NO_INDEPENDENT_CUSTODY`, version, synthetic seal digest and latest payload digest — no raw signatures, keys, trust flag, SQL grants or timestamps for legal reliance.
- Test-only explicit `BootstrapNewForTests` creates a **new empty journal file**, with `CreateNew` and `Flush(true)`, in an existing test-owned directory; **ordinary inspection/append will never initialize it**. Do not create or chmod production directories; do not follow arbitrary user-provided paths on a production caller (no production call path exists).
- A new xUnit file-only regression uses ephemeral RSA keys and isolated temp directory to verify persistence after closing/reopening/restart simulations, same/equivocating version rejection, concurrent writers, wrong key/pin, tampered payload/signature/header, missing/truncated file, stale/future UTC, no silent repair. In the existing real #66 PostgreSQL `pg_dump/pg_restore` smoke fixture, append old and then newest signed events to a separate temp journal and **re-open it** after restoring the earlier database. Feed the journal-derived latest seal digest into the existing ADR 0034 verifier: restored old DB and earlier authentic signed witness/seal must fail against the journal-derived latest digest; attacker replacing **journal + pinned key/config** may still replay old evidence. File journal *inspection is not cryptographically bound* to a future SQL decision, and TOCTOU between read and reconcile is still a production blocker.
- Tests first (RED type missing) before implementation; all four GitHub Actions jobs green on exact final `main` HEAD before closing ONLY #67. Parent #64 stays OPEN for real separately controlled write-once/immutable offsite witness authority, CAB-pinned keys/rotation, user/DB admin separation, full-cluster PITR/region and restore/corruption, authenticated signed MDS+CRL source and critical availability controls. #61/#57/#55/#53/#44/#50/#46/#38 remain OPEN. V015/V016 registrar SQL freeze and suspended CLI unchanged; no active WebAuthn credential, qualified eIDAS/QTSP or WORM evidence claim.

## On-prem / Azure

The prototype depends only on .NET 10 and POSIX/Windows-style file APIs; no mandatory Azure service. This does **not** establish separation of duties or durability on either on-prem or Azure. Before any production use, an independently governed witness/signature provider, immutable retention design, signed root provenance, secure backup/restore and disaster recovery must be designed, legally reviewed and independently tested. Ordinary database, app or backup administrators must be unable to rewrite or roll back the authoritative witness.
