The real SQL period export already returns strictly increasing (`issued_utc`, `id`) by its ORDER BY. The authenticated Page and Search read boundaries reject a different order; **synchronous ZIP Export does not** even though it validates records/bytes/IDs. A misbehaving alternate repository may produce an internally valid but nondeterministically ordered manifest and ZIP. The offline unqualified v1 checker validates unique IDs and UTC-in-period plus physical contiguity, but accepts swapped manifest rows or physical TSR members in a different order. Those archives need not satisfy the *actual v1 exporter* layout.

## Decision

1. **Versioned v1 ordering rule:** `entries` in a v1 manifest are required to be strictly ascending by (`IssuedUtc` **exact UTC 100ns ticks**, canonical RFC UUID `Id`), with identical UTC ticks resolved by ascending UUID bytes. The physical ZIP **local header** sequence is exactly `manifest.json` first then the `responseFile` for each entry **in manifest order**, with no gaps (existing ADR 0123), not merely a matching unordered bag of valid members. This is a local canonical deterministic representation of the **current** seekable in-memory ZIP producer, not an RFC3161 or eIDAS requirement or a signed witness.
2. **Commit accepted ADR first**, then **Business test-only RED** with original same-tenant UTC/DER+SHA-consistent, canonical document-imprint, `Unverified` records: out-of-order timestamps, reversed UUID tie at the same timestamp (both otherwise pass all read gates) must fail at `ExportZipAsync` *before allocating/exporting* with existing fixed generic `InvalidOperationException("Repository returned an unordered registry batch.")`. Positive strictly ordered different-UTC and UUID-tied records and zero/one receipts stay green. Update fake registry to emulate actual SQL sorting by default, introducing a separate adversarial explicit `overrideExport` list to avoid conflating random fixture order with a PostgreSQL behavior regression.
3. **Python offline test-only RED:** build otherwise locally valid v1 ZIPs whose manifest rows are reversed by UTC ticks or same-time ID, and ZIPs whose manifest is correctly sorted but TSR local member order is swapped. Require a fixed generic `ExportVerificationError` with no raw source, filename, DER, OID or tenant in the CLI stderr. Positive multi-entry same-UTC and different-UTC sorted v1 archives with actual current manifest/physical member order, empty and one receipt remain accepted. Observe genuinely executing, missing-denial **RED** from the backend GitHub Action(s) before any production code or offline parser changes. A compilation, fixture or import failure is not acceptable RED.
4. **Only after observed RED:** re-use `TimestampRegistryService.RequireAscendingRegistryOrder(records)` immediately after `ValidateReturnedRecords(...,forExport:true)` and before manifest/ZIP allocation. Do not sort returned records, truncate or alter source evidence; preserve all existing 10,000 count, 1MiB/64MiB DER, 16KiB/2MiB metadata, reference and 8MiB manifest/80MiB archive caps and typed over-budget exceptions. In the strict standalone Python verifier, check strict ascending pairs of `(parse_utc_ticks(row["IssuedUtc"]), uuid.UUID(row["Id"]).int)` in the same bounded manifest iteration and validate physically ascending local file names exactly against `manifest.json` and the sequence of signed-test-independent `responseFile` names. No unsafe archive extraction or additional unbounded decompression, no unstable clock-dependent comparator or on-prem/Azure behavior drift.

This positive verifies the contract against actual SQL but cannot make an unsigned ZIP trustworthy.

## Alternatives rejected and nonclaims

- **Silently sorting a buggy repository's rows or a received unsigned manifest:** rejected. An altered order is part of original evidence provenance and indicates adapter/output-contract drift; silently rewriting it can hide truncation or timeline discrepancies. Reject atomically instead.
- **Demanding monotonically increasing cryptographically trusted issuance times:** unsupported by pilot. The TimestampRecord IssuedUtc is not independently signed UTC(k) qualified evidence; this order is deterministic **metadata**, not notarization.
- **Treating ZIP ordering as completeness/custody:** false. An adversary may coherently replace **both** unsigned ZIP manifest and DER; signed independent high-water and WORM storage, full snapshot/coverage, RFC3161 CMS signer/policy/revocation/EU Trusted List and CAB/AgID/eIDAS legal launch stay unimplemented. v1 retains `Unverified` status. Physical layout validity never proves a period is complete.
