# ADR 0095 — Isolated passwordless Microsoft Entra PostgreSQL candidate (no migration/apply)

Status: **Accepted for scoped prequalification [#129](https://github.com/KeyserDSoze/TemporalMark/issues/129)**, 2026-11-20. **Parent #128/#18 remain OPEN; candidate only, NOT production-authorized.**

## Baseline and sources reviewed

Reviewed [ADR 0001](0001-architecture-and-deployments.md), ADR 0090–0094, `infra/azure/main.tf`, `versions.tf`, 46 existing Azure mocked-plan assertions in `infra/azure/tests`, `infra/azure/README.md`, `docs/DATABASE_MIGRATIONS.md`, `scripts/apply-migrations.sh` (20 immutable checksummed migrations), `docs/COMPLIANCE.md`, `docs/ROADMAP.md`, `docs/THREAT_MODEL.md` and issue #128. Current main Azure registry Flexible Server is **password-authenticated** and its admin password is stored through `var.postgres_password` in Terraform state. The API's connection string secret was moved to external Key Vault in #127, but that **does not** prepare Npgsql for Entra token auth or remove the SQL admin password from current/historical state.

Microsoft [Entra authentication concepts](https://learn.microsoft.com/en-us/azure/postgresql/security/security-entra-concepts), [Entra configuration](https://learn.microsoft.com/en-us/azure/postgresql/security/security-entra-configure) and [managed identity connectivity](https://learn.microsoft.com/en-us/azure/postgresql/security/security-connect-with-managed-identity) explain password-only, mixed and Entra-only server modes, the independent initial Entra administrator, PostgreSQL role mapping and token-based database login; enabling Entra may **restart** the server. Azure Database PostgreSQL server role access is **separate** from Azure control-plane RBAC, and a Microsoft Entra admin must create lower-privilege DB roles. Microsoft cautions tokens already issued may remain valid until expiry and provisioning order matters for database ownership. HashiCorp [AzureRM PostgreSQL Flexible Server](https://registry.terraform.io/providers/hashicorp/azurerm/4.44.0/docs/resources/postgresql_flexible_server) and [Entra administrator](https://registry.terraform.io/providers/hashicorp/azurerm/4.44.0/docs/resources/postgresql_flexible_server_active_directory_administrator) support the `authentication` block and separate admin resource. Existing deployed SQL admin/password attributes may persist in state even if removed from HCL; **this is NOT a safe in-place migration**.

## Decision

1. **Do not edit** `infra/azure/main.tf`, its API/DB roles or any SQL migration. Introduce a self-contained **candidate-only** Terraform root at `infra/azure/candidates/entra_postgres/`, not referenced by existing root. No automatic/apply workflow, no connection to production. Candidate resource requires an explicitly *different* new PostgreSQL 17 server name ending in `-entra-candidate`, and externally reviewed VNet-delegated subnet and private DNS zone ARM IDs. It **does not create or delete** the existing resource group, VNet, DNS, Blob, Key Vault, registry server or any tenant data.
2. Configure candidate `azurerm_postgresql_flexible_server` with **explicit** `authentication { active_directory_auth_enabled=true; password_auth_enabled=false; tenant_id=var.entra_tenant_id }` and **omit** `administrator_login`, `administrator_password`, password variables, data sources reading secrets and public network access (set `false`). Keep version 17, a pilot-only SKU and 14-day backup setting, `prevent_destroy` and existing private-network assumptions. Define exactly one `azurerm_postgresql_flexible_server_active_directory_administrator` with independently approved **Group** Entra object ID, tenant ID and group name. One candidate database may be created **after** admin assignment with explicit `depends_on`; this is not proof of data-plane SQL role provisioning.
3. Fail closed with input validations (non-empty IDs and strict UUID/name/ARM formats, DNS suffix, fixed subnet suffix `/subnets/postgres`, no shared/public network, group name constraints) and cross-input resource preconditions for matching subscription/resource-group and distinct role/tenant context. Group-only administrator is a candidate governance choice, **not a claim of group custody or CAB approval**; object GUID syntax is not actual Entra directory verification.
4. **TDD before implementation:** commit `mock_provider "azurerm"` Terraform plan asserts (Entra-only, no password-login/secret, private networking, group admin, candidate database) + negative cases; wire an independent mandatory Terraform CI step. Prove RED before adding the Terraform candidate source, then implement and verify GREEN. Keep all existing 46 mocked Azure plans.
5. The candidate root should not be applied to any Azure subscription without a fresh approved topology, subscription/tenant ownership, access control, private DNS and migration-jobs/DB-principal design, rollback and data retention review. The active API and provisioning/registrar/migration clients still expect password-based PostgreSQL logins; `scripts/apply-migrations.sh` uses `PGPASSWORD` and current Keycloak role checks. A separate Npgsql managed identity rotating token adapter, token-enabled migration runner, Entra-backed PostgreSQL role grants, repeatable real signed HTTP tenant tests, backup/restore, cross-region/DR, review of OAuth token expiry and an independently approved cutover must precede *any* switch. Do not perform Azure apply, change `main` resource authentication, modify irreversible Blob policy or delete prior SQL credentials.
6. A plan-only test does **not** prove a private Azure database reachable, an Entra principal valid, a token accepted, or safe migration of existing state containing credentials. #128 remains OPEN until a deployed end-to-end Entra-based data plane works without SQL admin secrets and is independently approved, with old current/historical Terraform state secured, credentials rotated and safe production cutover. #18/#115/#17/#13/#15 remain OPEN for production privacy, DR, WORM and QTSP.

## Completion evidence

Close only the scoped #129 after exact final docs-inclusive `main` SHA 4/4 GitHub core CI jobs and combined `temporalmark/ci-4-core-jobs=success` with real Terraform mocked-plan tests, .NET, Playwright, PostgreSQL migration/backup restore, Keycloak signed multi-tenant HTTP/MFA, Nginx/API synthetic log probes. The isolated candidate must not claim to solve #128 or actual Azure deployment.
