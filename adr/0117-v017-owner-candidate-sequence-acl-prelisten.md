## Reviewed authoritative baseline

Consulted ADR 0099/0100/0111/0114/0115/0116, `docs/POSTGRES_RUNTIME_PRIVILEGE_PREFLIGHT.md`, `docs/API_POSTGRES_ENTRA_PRELISTEN_CANDIDATE.md`, `docs/DATABASE_MIGRATIONS.md`, `docs/ROADMAP.md`, `docs/THREAT_MODEL.md`, issue #61/#64, existing `PostgresRuntimePrivilegePreflight.Sql`, the real PG17 disposable LOGIN xUnit fixture and **immutable** `V017__unapproved_mds_crl_candidate_checkpoint.sql`.

V017 creates `public.mds_unapproved_candidate_checkpoints` and `public.mds_unapproved_candidate_events` with serial, issuer/source hash and UNSIGNED unapproved digest metadata. It explicitly REVOKEs all runtime group and PUBLIC table privileges. Its append-only-by-trigger is *not* cryptographically immutable, and an SQL owner can override it. The candidate events table's `event_id bigint GENERATED ALWAYS AS IDENTITY` creates `public.mds_unapproved_candidate_events_event_id_seq`, explicitly REVOKEd from application groups. The V017 owner-only staging function `record_unapproved_mds_checkpoint_candidate` is already denied effective EXECUTE by the Entra prelisten; it is a SECURITY INVOKER diagnostic and does NOT authorize metadata. V017's table and sequence direct effective runtime ACLs were omitted from the prelisten. A hypothetical unsafe login-specific/per-column/PUBLIC GRANT bypasses its current membership and existing quota/enrollment table checks.

PostgreSQL **17** official [GRANT](https://www.postgresql.org/docs/17/sql-grant.html) distinguishes table, column and **sequence** permissions; a GRANT on a table does not automatically grant sequence use. Official [system privilege inquiry](https://www.postgresql.org/docs/17/functions-info.html) defines `has_any_column_privilege` for any-column or table-wide `SELECT/INSERT/UPDATE/REFERENCES`, `has_table_privilege` for table `DELETE/TRUNCATE/TRIGGER`, and `has_sequence_privilege` for sequence `USAGE/SELECT/UPDATE`. [Sequence functions](https://www.postgresql.org/docs/17/functions-sequence.html) explains the distinct capabilities; the test MUST NOT execute nextval/setval/currval. A sequence SELECT can reveal a counter; UPDATE/USAGE could allow changes or increments. This is **point-in-time hypothetical SQL ACL drift detection** only, not evidence of any actual deployed overgrant or tamper.
