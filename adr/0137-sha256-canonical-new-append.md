# ADR 0137 — SHA-256-only canonical document-imprint admission on NEW pilot registry append

**Status:** ACCEPTED for direct-`main` test-first scoped [#179](https://github.com/KeyserDSoze/TemporalMark/issues/179), 2026-11-23 Europe/Rome. Parent delegated qualified TSA verification #15, immutable evidence/custody #17, and eIDAS legal qualification #13 remain OPEN. This is neither a standards-wide SHA-256 mandate nor a qualified-timestamp declaration.

Only the pilot issuer normalizes its **document** SHA-256 imprint to exactly **32 octets**, standard padded **44-character Base64**, with exact ordinal decode/re-encode, and sets `HashAlgorithmOid = "2.16.840.1.101.3.4.2.1"`. This is deliberately distinct from `TokenSha256Hex`, the local SHA-256 of the **raw retained TSR DER**, which Domain.Validate already checks. The exact-imprint search selects precisely the SHA-256 OID plus canonical Base64 (ADR 0081). However, direct writer admission under ADR 0135/0136 only checks nonblank original metadata/UTF8 bounds and `Unverified`; V001 stores arbitrary text. A direct writer could therefore insert a fresh, otherwise original, authorized-tenant, SHA-consistent `Unverified` record with an unsupported algorithm OID, malformed/improperly padded Base64, or decoded-length mismatch. Such data can be missing from normal exact-imprint lookup even when offered on Page/export. This is a hypothetical internal inconsistency, not evidence that any existing issuer or QTSP signed a malformed response.

## Decision: narrow new-append-only profile

1. **Accepted ADR committed before tests or production changes.** Direct app-owned pilot *new append* must require `HashAlgorithmOid` equals exactly `2.16.840.1.101.3.4.2.1` (ordinal), and `DigestBase64` is **exactly 44 characters**, decodes to **exactly 32 bytes** with standard `Convert.FromBase64String`, and compares ordinally to `Convert.ToBase64String(decoded)`. Reject whitespace-alias text, invalid alphabet/URL-safe forms, missing/excess padding, nonzero pad bits, decoded non-32 lengths and wrong algorithm OIDs. Fixed 44-character precheck bounds decoder allocation and operation; no unbounded reserialization. Preserve the earlier original 16KiB/1MiB byte and optional 8MiB reference budgets, `Unverified`-only rule and the writer's **existing sanitized** `InvalidOperationException("Stored receipt exceeds pilot registry write limits.")`, raised before SHA of original DER or opening the DB connection. Do not reflect a supplied imprint/tenant/algorithm in errors/logging.
2. **Real RED first:** commit test-only real PostgreSQL17 writer cases with self-consistent original small DER / SHA256, authorized tenant, UTC issued time, nonblank provider/policy and `Unverified`. Check wrong algorithm, leading/embedded whitespace, invalid alphabet, pad-bit alias of valid SHA-256, 31/33-decoded-byte (including same 44-char length), missing padding and URL-safe alphabet independently. Each `record.Validate()` must succeed before the writer call (to distinguish the gap from existing Domain checks). Require generic `InvalidOperationException` and zero matching SQL rows. Add positive **nonzero canonical SHA-256 digest** original readback and foreign-tenant lookup denial, retaining existing exact 16KiB metadata/1MiB DER and status cases. Observe actual compiled **real PG17 RED** in Actions (no unrelated test/fixture/SQL error) before changing any source. No temporary disabling of unrelated protections; if CI backend prerequisites fail, diagnose before counting the RED.
3. **GREEN only after genuine RED:** add a small private canonical SHA-256/OID helper within `TimestampRegistryWriteBudget` and call it from `IsNewRegistryRecordAdmissible`. Keep issuer ingress validation (independent, before upstream TSA POST) unchanged and pre-existing SQL writer call position unchanged. No new API, serialization, tenant selection, retry, credential path, DB migration, automatic correction or qualified status. Neither `TimestampRecord.Validate` nor existing immutable V001–V020 is tightened: old/owner-modified rows may still exist, must not be silently modified, and retain their existing independent read gates. Future approved non-SHA256 RFC3161 algorithms need a separate profile and indexed search design, ADR and tests; this ADR is specific to the current SHA-256-only pilot, not an assertion of RFC3161-wide algorithm prohibition.
4. After independently observing RED/GREEN, update this ADR, `docs/REGISTRY_INTEGRITY_READ_GATES.md`, `docs/COMPLIANCE.md`, `docs/THREAT_MODEL.md`, `docs/ROADMAP.md`. Close only #179 after verifying exact **latest documentation-inclusive main SHA** four backend/frontend/terraform/docker-smoke jobs and independent ci-verdict/combined status success, Business, real PG17 tests, 20 V001–V020 migrations/full database restore, offline v1 ZIP verifier, signed Keycloak A/B and Nginx privacy. Do not close parent #15/#17/#13/#18/#61/#64.

## Threat/assurance boundary

A canonical document imprint is **not** proof that `messageImprint` within a DER/CMS timestamp matches the document, nor proof of signer path/nonce/revocation/historical EU Trusted List qualification, trusted UTC, incident authorization, cross-tenant WORM custody or completeness of exports. A DB schema owner or manual restore still bypasses app admission; independently verified historical artifacts and complete trust/retention remain open. No self-issued qualified timestamp may be inferred from a matching Base64 string.
