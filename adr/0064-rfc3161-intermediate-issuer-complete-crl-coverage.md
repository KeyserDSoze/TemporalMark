# ADR 0064 — Two signed complete CRLs for a verified root→intermediate→RFC3161 signer path

Status: Accepted restricted offline PKIX revocation slice (2026-11-16), [#95](https://github.com/KeyserDSoze/TemporalMark/issues/95), child of open [#15](https://github.com/KeyserDSoze/TemporalMark/issues/15). Does **not** establish qualified timestamp/legal trust.

## Reviewed context

Reviewed [ADR 0002](0002-qualified-vs-delegated-timestamping.md), ADR [0052–0063](0063-rfc3161-offline-direct-issuer-signed-full-crl.md), [TSA operator runbook](../docs/TSA_HTTP_TRANSPORT.md), [threat model](../docs/THREAT_MODEL.md), [roadmap](../docs/ROADMAP.md), `ExternalRfc3161TimestampProvider`, `ExternalRfc3161CertificateChainPolicy`, `ExternalRfc3161IssuerCrlPolicy`, API configuration and real disposable RSA root/intermediate/TSA+CRL tests. #94 introduced strict operator-reviewed **single complete issuer CRL** and conservatively rejected any intermediate path because a root CRL cannot establish TSA signer revocation if it is signed by an intermediate. The X509 path validator (#92/#93) already validates intermediate certificates embedded in the actual CMS, to the sole custom reviewed root, at the bounded CMS-signed `genTime`; CRL coverage must refer to **that exact selected path**.

[RFC5280 §6.3](https://www.rfc-editor.org/rfc/rfc5280#section-6.3) processes the revocation status of each non-root certificate against its actual issuer, considering CRL issuer identity/signature and scope. [RFC10007](https://www.rfc-editor.org/rfc/rfc10007.html) clarifies that each CRL issuer cert MUST have a `keyUsage` extension granting `cRLSign`. Our conservative existing `ExternalRfc3161IssuerCrlPolicy.ValidateDirectIssuerLeaf` verifies direct issuer DN, `CrlSign`, root/issuer SKI to CRL AKI, issuer public-key RSA SHA256 signature over exact signed CRL TBS, CRLNumber, signed freshness window `thisUpdate ≤ genTime < nextUpdate`, and rejects ANY entry for the issued certificate. This same proof can be repeated independently for **intermediate CA cert using root CRL** and **TSA leaf using intermediate CRL**.

## Decision

1. Keep `TimestampProvider:IssuerCrlBase64Der` required for every configured external TSA and interpreted as **approved root-signed complete CRL**. Add `TimestampProvider:IntermediateIssuerCrlBase64Der` as an optional second server-controlled complete signed CRL. If provided it MUST be canonical single DER-CRL Base64, within the existing 1 MiB bound, and fully structurally parsed **before sending any imprint**; reject malformed/noncanonical/unknown-extension CRL even if unused. Blank/missing means no intermediate CRL (for direct root→leaf deployments). No URL or tenant controls can configure either issuer.
2. Establish the **actual** signer path once via a new `ExternalRfc3161CertificateChainPolicy.BuildValidatedSignerChain` returning a fresh caller-owned `X509Chain` already `Build`-verified under the existing custom root, selected intermediates only embedded in CMS, `VerificationFlags.NoFlag`, `DisableCertificateDownloads=true`, `RevocationMode.NoCheck`, time set to the previously verified signed `genTime`. The existing void `ValidateSignerChain` retains its behavior using/disposal of that builder. Dispose the validated chain after use.
3. The revocation gate `ExternalRfc3161IssuerCrlPolicy.ValidateSignerPathRevocation` takes the **same cryptographically verified CMS signer**, approved root, CMS certificate bundle, signed `genTime` and one/two preflight-parsed CRLs. It constructs the validated path itself, requires exact signer and root DER endpoints and exactly **two elements** (`signer, root`) or **three** (`signer, intermediate, root`). Direct path requires the root CRL and no superfluous intermediate CRL. Three-element path **requires both**: use the authenticated **root CRL** to check the *actual selected intermediate CA certificate* and the authenticated **intermediate CRL** to check the *actual verified TSA signer*, with mandatory `CrlSign` and all earlier #94 CRL signature/scope/time/serial checks at the **same signed genTime**. Reject missing second CRL, wrong issuer, unsigned/altered/expired CRL, revoked intermediate or leaf, or more than one intermediate. Never substitute arbitrary other CMS certificates for chain elements. No implicit OS trust, network retrieval, CRL distribution-point fetch or downgrade to `NoCheck`.
4. Keep support narrow: only complete **RSA SHA-256 PKCS#1 v1.5** v2 CRLs with root/intermediate issuer keyIdentifier AKI, issuer critical `CrlSign`, CRLNumber, and no unsupported reason/delta/indirect/extensions. Multiple intermediates, partial reason/indirect/delta CRLs, unsupported signing algorithms or no CRL for any path element fail closed. Existing `X509Chain.RevocationMode.NoCheck` remains **path-only**; revocation is checked separately over the validated path.
5. Unit tests generated from disposable RSA X.509 root→intermediate→leaf and **genuinely signed** root/intermediate CRLs, testing positive path and revoked intermediate, revoked leaf, wrong/interchanged CRLs, wrong signer key with same subject DN, stale/noncanonical/missing CRLs, unsupported longer chains, missing embedded intermediate, and direct-path parity. ADR then RED-first tests must precede implementation on `main`, observe actual failed backend CI, then GREEN code, documentation and all four GitHub Actions jobs successful on exact final docs-inclusive `main` SHA. Close child #95 only after final CI verified and parent #15 updated.

## Legal and operational limitations

Two CRLs check more than one issuer but are **not** complete historical OCSP/CRL validation for arbitrary CA paths, reason/scope coverage, monotonic authentic historical CRL snapshots, immutable CRL evidence/witnesses, or a determination of historical EU Trusted List QTSP qualified service status. The operator must independently authenticate, review and rotate **both** CRLs, monitor freshness (nextUpdate), and preserve trusted records of source and approval; no automatic HTTP downloads or rollback-resistant CRL custody are implemented. Real QTSP integration, UTC(k)/HSM, immutable archive/WORM #17, regulatory dossier #13 and parent #15 remain OPEN. Pilot evidence remains `Unverified` and cannot be called eIDAS-qualified.
