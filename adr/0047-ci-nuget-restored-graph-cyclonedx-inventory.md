# ADR 0047 — CI-only CycloneDX inventory from all nine .NET NuGet restore snapshots

Status: **accepted for disposable CI inventory only; not a dependency lock, vulnerability scan or production artifact attestation** (2026-11-16). Scoped child [#78](https://github.com/KeyserDSoze/TemporalMark/issues/78) of open #20.

## Reviewed inputs and problem

Reviewed ADR 0001 and 0043–0046, docs/ROADMAP.md, docs/THREAT_MODEL.md, docs/CI_NPM_CYCLONEDX_SBOM.md, .github/workflows/ci.yml, all **nine** .NET 10 project csproj files (five production and four test projects) and existing action/npm/Docker source policies. #77 exports two **npm-lockfile-only** CycloneDX 1.5 inventories. NuGet has no committed packages.lock.json files: repeated restores may resolve a different transitive package graph, even for an identical source commit. No parallel .NET inventory is retained with CI. Claims of complete SBOM or stable transitive resolution would be false.

## Decision

1. Use `dotnet restore` on every discovered `.csproj` under `src/backend` and `tests/backend` (currently exactly nine). The .NET SDK creates `obj/project.assets.json` per project; no new NuGet package or marketplace action is required. The restore step must **fail** if the tree lacks any of those projects. Do not print NuGet feeds or credential-bearing assets files to CI logs.
2. Add a deterministic Python standard-library generator `tests/integration/generate_nuget_sbom.py`. For each project, read the actual SDK-generated `project.assets.json` version 3 and its `libraries` map, include **only** entries where library `type` equals `package`, exclude project references. Require exact `Name/Version` keys and canonical 64-byte SHA-512 decoded from actual library `sha512` base64 (no invented digest or package provenance). Represent every package *per project* with project-specific unique `bom-ref`, `pkg:nuget/Name@Version` purl, source .csproj path and SHA-512 in CycloneDX JSON 1.5. List all nine projects and SHA-256 of their exact `.csproj` and assets bytes in application metadata properties; package project names might repeat across projects, deliberately do not deduplicate. Omit unknown dependency edges, timestamps, runtime image assertions and vulnerability verdicts.
3. Strictly validate the generated inventory **against all nine original current SDK assets** and project hashes. Reject malformed/absent source, extra projects, empty or invalid targets, invalid package SHA, mismatched name/version, duplicate refs, changed sources, extra/missing/altered components or invalid purls. No untrusted source path or NuGet credential content is copied into exported BOM.
4. TDD required: commit this ADR **before RED**; implement an offline source-policy guard `tests/integration/check_nuget_sbom_workflow.py` and unit tests in the backend *before* any NuGet SBOM step exists, producing real failing backend CI on absent restore/inventory/upload steps with guard tests green. Then GREEN: generator, validator and fixture-negative unit suite, plus backend `dotnet restore` for all nine projects, generator/validator with output in `$RUNNER_TEMP/temporalmark-nuget-sbom`, SHA-pinned `actions/upload-artifact` with only `*.json`, `if-no-files-found: error`, seven-day retention. Keep global `permissions: contents: read`. Ensure main-branch CI all four jobs successful at **exact final HEAD**, including Docker PostgreSQL whole `pg_dump`/witness restore, PWA security, real Keycloak TOTP/PKCE and Terraform. Only then close child #78 and update #20.
5. Document the new inventory/runbook, real RED and GREEN evidence and residual controls in docs/ROADMAP and docs/THREAT_MODEL. No new production API, tenant privilege, Azure/on-prem contract, FIDO root trust, reviewer registration or SQL V015/V016 interlock changes.

## Limitations and security obligations

NuGet `project.assets.json` reports packages selected for a specific SDK restore; **it is not a NuGet lockfile**, and SHA-512 metadata alone is not verified publisher identity or a cryptographic software-release attestation. SDK/project paths and restored packages can vary by runner, target framework, package source and time. The inventory excludes container OS packages, native build dependencies, frontend assets, dynamic downloads, and legal/evidentiary evidence. This is not whole-runtime composition analysis, SPDX/CycloneDX certified validation, SCA/SAST, publisher signature verification, production incident SBOM or WORM preservation. Subsequent work under parent #20 includes NuGet locked-mode restoration, system-wide OCI SBOM, SCA/SAST/secret scanning, release attestations and CAB custody. #64/#61/#57/#17 and reviewer V015/V016 security blockers remain OPEN; do not claim qualified timestamping or eIDAS/QTSP status.

Sources: [NuGet dependency resolution](https://learn.microsoft.com/en-us/nuget/concepts/dependency-resolution), [CycloneDX 1.5 schema](https://github.com/CycloneDX/specification/blob/master/schema/bom-1.5.schema.json).

## Versioned NuGet SDK restore-asset schema amendment (2026-11-16)

The first real GREEN candidate `fddfef0` passed the policy but [CI 43878487858](https://github.com/KeyserDSoze/TemporalMark/actions/runs/43878487858) failed while processing the restored .NET 10 API project because the originally assumed `project.assets.json` **v3** is not universally emitted by newer .NET 10 SDKs. The [NuGet accepted v4 proposal](https://github.com/NuGet/Home/blob/dev/accepted/2025/Multiple-Equivalent-Framework-Support-TFM-As-Aliases.md) documents `assets.version=4` for SDKAnalysisLevel 10.0.300+, mainly to support framework-alias mapping, and [NuGet maintainers explicitly warn the assets format is not a stable integration API](https://devblogs.microsoft.com/dotnet/nugetaudit-2-0-elevating-security-and-trust-in-package-management/).

Accordingly, the *implementation* accepts **only known v3 or v4** SDK assets versions, provided their top-level `libraries` map, package entries, target set and canonical SHA-512 metadata match the validated subset. It rejects unknown future versions (test v5 RED) rather than silently misparsing them. This extends the parser's supported observed version surface while preserving the source-level package identity, per-project bijection and no-security-certification limitations. The original proposal's unconditional v3 assumption is superseded by this amendment. No new production qualification or trusted provenance is implied.
