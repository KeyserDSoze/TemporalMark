# ADR 0030 — Offline signed CRL validation for one direct certificate issuer, **non-authorizing**

Status: **accepted for a deliberately isolated testable CRL cryptography preflight, never MDS trust or signer activation**, 2026-11-16. Focused [#59](https://github.com/KeyserDSoze/TemporalMark/issues/59) child of [#57](https://github.com/KeyserDSoze/TemporalMark/issues/57)/#55, following ADR 0025–0029.

## Context / reviewed sources

FIDO Metadata Service changed signer roots from GlobalSign R3 to R46 in August 2026, with cross-signed transitional x5c[2] from August 31 and 2029-03-18 R3 sunset ([FIDO changelog](https://fidoalliance.org/mds-changelog/)). Pinned Fido2 4.3.3 currently validates BLOB signing with an R3 root and has distinct revocation branches, including NoCheck for system-trusted paths; this is NOT sufficient proof that a signing certificate cannot be revoked. ADR 0029's test-only JWS path deliberately uses `X509RevocationMode.NoCheck`, and all results are `UNAPPROVED`.

To test real revocation handling without inventing an ASN.1/CRL/signature engine, pin **BouncyCastle.Cryptography 2.7.0** (MIT; stable 2026-07-30; .NET 10 compatible). Verify tagged `release-2.7.0` APIs `X509CrlParser.ReadCrl`, `X509Crl.IsSignatureValid`, `X509Crl.IsRevoked`, `X509V2CrlGenerator.Generate`, `DotNetUtilities.FromX509Certificate`, `Asn1SignatureFactory` against upstream. NuGet: https://www.nuget.org/packages/BouncyCastle.Cryptography/2.7.0 ; [RFC 5280 §5](https://www.rfc-editor.org/rfc/rfc5280#section-5).

## Decision, intentionally narrow

1. Implement standalone infrastructure-only `ReviewerMdsOfflineCrlCandidateVerifier`: require an original **caller-injected** X509 v3 CA issuer (keyCertSign + cRLSign and CA=true), a direct leaf cert with matching issuer and appropriate validity and leaf key usage, and **exactly one** externally supplied DER X.509 **v2 full CRL**. There is no root approval, network fetch, trust-store fallback, MDS cache, DB/CLI/API consumer, signer registration, SQL privilege or tenant write. The caller-provided CRL may be malicious and must be checked cryptographically before acting on it.
2. Reject empty/huge/malformed/noncanonical CRL bytes, mismatched issuer, unauthorized issuer cRLSign, incorrect CRL signature (using only issuer cert public key), missing or expired `nextUpdate`, `thisUpdate` in the future, excessively long freshness interval, unknown critical CRL extensions, delta CRLs, indirect CRLs, unsupported critical entry policies, revoked leaf serial, invalid leaf/issuer validity. No `X509Chain.RevocationMode.NoCheck` is used to **pretend** a verified CRL is current.
3. At most one directly issued leaf is evaluated in this slice. No indirect/delegated CRL issuer, intermediate/re-cross-cert chain, delta merge, distribution-point URL validation, CRLNumber monotonic shared checkpoint, or operational OCSP handling is available; reject rather than silently accept these. The certificate issuer is **not anchored to a trusted production R46 root**. Successful one-leaf CRL cryptography does not confer FIDO MDS signer or device trust.
4. Tests first RED on `main` using **ephemeral** separate CA and leaf RSA keys with `System.Security.Cryptography.X509Certificates`, generated real RSA-signed DER v2 CRLs using **BouncyCastle** at runtime, signed valid and revoked cases, unknown critical and delta, invalid signatures and issuer/keyUsage, freshness edge cases and no-CRL fail-closed. No test private key is committed.
5. Every positive returns **`ReviewStatus=UNAPPROVED`, `PolicyStage=CRL_SIGNATURE_CHECK_ONLY_ROOT_UNTRUSTED`**, the CRL SHA-256 and no raw certs/keys or trusted/active signer flag. It is not wired into ADR 0029's JWT candidate: accepting a test CRL must **never** make an approved trusted metadata entry. To build actual production root+CRL verification across the complete R46/R3 transition and all certificates remains #57/#55, with CAB-approved roots, issuer mapping, signed CRL distribution, observed time and rollback-safe persistent CRL version, revocation of intermediates, OCSP and cross-platform on-prem/Azure validation.
6. Four-job exact-head CI and test-first RED/GREEN required before closing **only #59**. Preserve V015/V016 SQL issuance freeze and suspended registrar CLI. #57/#55/#53/#44/#50/#46/#38 remain OPEN. No WORM/eIDAS/QTSP or timestamp qualification inferred.

## Operational security and privacy

This is an offline component and adds no mandatory Azure service, third-party proprietary trust, SSRF or secret endpoints. Keep generated test keys ephemeral, avoid logging certificate/CRL raw data or PII, carry real certificate status and signer role governance only after separate privacy/DPIA and CAB review. The package and version need routine vulnerability monitoring; no metadata or CRL from an untrusted supplier may be used to authorize operations.
