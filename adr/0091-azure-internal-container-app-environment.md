# ADR 0091 — Internal-by-default Azure Container Apps environment load balancer

Status: **Accepted for scoped prequalification [#124](https://github.com/KeyserDSoze/TemporalMark/issues/124)**, 2026-11-20. Azure production [#18](https://github.com/KeyserDSoze/TemporalMark/issues/18), log/privacy [#115](https://github.com/KeyserDSoze/TemporalMark/issues/115) and [#113](https://github.com/KeyserDSoze/TemporalMark/issues/113) remain OPEN.

## Reviewed baseline and documentation

Reviewed ADR 0001, 0084, 0086, 0087, 0089 and especially [ADR 0090](0090-azure-private-default-web-ingress.md), `infra/azure/main.tf`/`variables.tf`/`outputs.tf`, existing mocked `tests/ingress_boundary.tftest.hcl`, `.github/workflows/ci.yml`, `infra/azure/README.md`, `docs/AZURE_PRIVATE_INGRESS.md`, `docs/THREAT_MODEL.md` and parent issues #18/#115/#113. The #123 change sets both **per-app** ingress modes internal by default, with `enable_public_web_ingress=false`; the API always remains internal. But the enclosing `azurerm_container_app_environment.main` does not set `internal_load_balancer_enabled`. The AzureRM [provider schema](https://registry.terraform.io/providers/hashicorp/azurerm/latest/docs/resources/container_app_environment) documents an external/public environment IP unless the internal load balancer flag is true. Microsoft [Azure Container Apps networking](https://learn.microsoft.com/en-us/azure/container-apps/networking) documents the public/external vs VNet/internal **environment** boundary, distinct from [application ingress](https://learn.microsoft.com/en-us/azure/container-apps/ingress). Thus a Terraform reference apply could still allocate an unnecessary publicly addressed environment even when neither app is intended for external callers.

## Decision

1. Set `azurerm_container_app_environment.main.internal_load_balancer_enabled = !var.enable_public_web_ingress` with the existing delegated `infrastructure_subnet_id`. No separate environment switch is provided; a caller cannot accidentally request public environment without also deliberately requesting public web. In the default and explicit private setting, the **environment uses an internal load balancer** and both web and API have internal ingress. With explicit web public opt-in, the environment is external/public, web is external, but API `ingress.external_enabled=false`. Both apps still reject insecure HTTP. Keep the conditional Terraform `frontend_url=null` in private mode as accepted in ADR 0090.
2. Before the source change, commit real `terraform test` `mock_provider "azurerm"` **`command=plan`** tests asserting the planned environment field, combined with per-app status and optional public URL semantics. Require default private true, explicit private true, and explicit public false for `internal_load_balancer_enabled`. Wire this independently to mandatory core Terraform CI, preserving previous OCI 11, OIDC 17 and per-app ingress 3 tests. Observe genuine RED from the missing environment property before implementing. No Azure credentials, actual resources, private data or Terraform apply is involved.
3. Explicitly document that **`enable_public_web_ingress=true` is a network release decision for BOTH the web app and its environment**; it does not verify a signed CAB approval, present a WAF, shield from malicious external requests, guarantee private-only API routing across unreviewed extra resources, sanitize Azure managed ingress/logs or satisfy GDPR-DPIA. The default **internal environment may not be reachable from browsers outside the private network**; a real private DNS/network access topology remains an independent production design. Container Apps per-app `external_enabled=false` does not mean every VNet client can call it; Microsoft documents it as an app-to-app environment scope.
4. Treat toggling `internal_load_balancer_enabled` on an **existing environment as a potentially destructive/replacement lifecycle change**, depending on AzureRM/provider version and deployed infrastructure. The project has NO approved automatic conversion, rollback, external-public DNS handling, front-door/WAF, private endpoint or state migration runbook. Before any real apply, an operator must review the provider plan for replace/destroy, original workload availability and required private DNS, evidence retention, regulatory change approval and staged migration; never use CI mock plans to claim safe in-place conversion. Keep the existing application and PostgreSQL/Keycloak functions unchanged and retain OSS on-prem parity for application capabilities.
