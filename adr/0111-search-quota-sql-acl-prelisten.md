# ADR 0111 — Deny mis-granted direct SQL privileges on shared search-quota tables at Entra prelisten

Status: **Accepted only for bounded candidate hardening [#146](https://github.com/KeyserDSoze/TemporalMark/issues/146)** on 2026-11-21. Parent Azure Entra production #128/#18 and search governance #115/#113 remain OPEN; WORM #17 and legal QTSP/eIDAS #13/#15 are NOT approved. No actual Entra SQL login, Terraform apply, CAB/GDPR sign-off or qualified custody established.

## Security baseline and evidence

Reviewed accepted ADR 0001 architecture portability, ADR 0082/0083 privacy-minimized search and V019 per-actor/tenant shared-primary 12/30 quota, ADR 0099/0100 read-only detached runtime preflight and explicit Production-only Entra API activation, ADR 0106/0107 effective ACL denies for evidence/audit and organizations/memberships; docs/COMPLIANCE, DATABASE_MIGRATIONS, POSTGRES_RUNTIME_PRIVILEGE_PREFLIGHT, API_POSTGRES_ENTRA_PRELISTEN_CANDIDATE, IMPRINT_SEARCH_RATE_LIMITING, THREAT_MODEL and ROADMAP; `src/backend/infrastructures/TemporalMark.Infrastructure/Postgres/PostgresRuntimePrivilegePreflight.cs`, current `tests/backend/TemporalMark.Postgres.Tests/PostgresRuntimePrivilegePreflightTests.cs`, immutable V001–V020 scripts and local PG17 grants. V019 explicitly REVOKEs ALL direct table permissions from PUBLIC and `temporalmark_runtime_group` on `public.imprint_search_rate_tenants` and `public.imprint_search_rate_principals`. Only a trusted `SECURITY DEFINER public.consume_imprint_search_rate(uuid,text)` procedure manipulates the counters after signed JWT and current admin authorization. V020 owner-only manual maintenance likewise leaves the SQL runtime with zero direct table rights.

The **nondefault** API Entra startup preflight checks org/membership/registry/audit ACLs but has **no predicate for either V019 quota table**. A grant to a specific runtime LOGIN (or another inherited role) of `SELECT` could expose a tenant's OIDC actor identifiers; `INSERT/UPDATE/DELETE/TRUNCATE` could alter 12-per-actor/30-per-tenant quota state or deny legitimate searches; `TRIGGER/REFERENCES` are owner-like schema-risk capabilities. Because PostgreSQL can GRANT `SELECT/INSERT/UPDATE/REFERENCES` for **one column only**, checking the table-level ACL misses that form. The security gap is a missing *prelisten drift/misgrant check*, NOT evidence of actual current SQL misgrants, proven runtime exploitation, regulatory WORM or audited Azure deployment.

Official [PostgreSQL 17 system privilege functions](https://www.postgresql.org/docs/17/functions-info.html) document that `has_any_column_privilege` succeeds for either a table-wide grant **or one column** for `SELECT`, `INSERT`, `UPDATE`, `REFERENCES`. Official [GRANT](https://www.postgresql.org/docs/17/sql-grant.html) documents column vs table granularity and `DELETE/TRUNCATE/TRIGGER` table-only privileges.

## Decision and delivery

1. Keep the existing single parameterized **read-only** SQL catalog SELECT on the **already-open** API runtime connection; it never changes database roles/permissions/tables or opens credentials. For **each** of the two existing V019 tables, deny effective `SELECT`, `INSERT`, `UPDATE` and `REFERENCES` by `NOT pg_catalog.has_any_column_privilege('public.<table>', '<privilege>')`; deny effective `DELETE`, `TRUNCATE`, `TRIGGER` via `NOT pg_catalog.has_table_privilege`. Baseline runtime remains allowed to `EXECUTE public.consume_imprint_search_rate(uuid,text)` through the dedicated role; no new SQL function EXECUTE deny, no function/role grant change, no schema migration and no new dependency. Preserve previous org/tenant/evidence/audit safety predicates, login role attributes, fail-closed generic exception with no inner, and cancellation.
2. **RED-first on main before source**: extend the existing **real PG17 Docker** xUnit ACL fixture with 18 test cases: for each quota table `SELECT`, `SELECT(one column)`, `INSERT`, `INSERT(one column)`, `UPDATE(hits)`, `DELETE`, `TRUNCATE`, `REFERENCES(organization_id)`, `TRIGGER`. Each case creates a unique disposable runtime LOGIN with generated test-only password and membership in `temporalmark_runtime_group`, demonstrates baseline preflight **PASS** and then grants just the unsafe privilege to this one LOGIN. Require the preflight to fail with its existing generic no-inner exception. Always `REVOKE` the extra grant/membership and `DROP ROLE` even on RED; use `Pooling=false` on generated unique logins only to avoid PG17 slot exhaustion. No shared runtime-group ACL modifications or table rows affected. Verify actual RED expected failure at the live Docker postgres test step (not an unrelated build/setup issue).
3. After verified RED, implement the minimum 14 read-only ACL conditions. Update preflight/Entra operator documentation, imprint rate-limiting runbook, migration docs, THREAT_MODEL and ROADMAP. Do not invent legally binding timestamping, portability differences or approved GDPR retention.
4. Verify **exact final docs-inclusive `main` SHA** four core jobs backend/frontend/terraform/docker-smoke 4/4 SUCCESS, fifth ci-verdict SUCCESS and combined `temporalmark/ci-4-core-jobs=success`; real PostgreSQL 18 new cases and all former 121, 20 immutable migrations, full pg_dump/pg_restore regression, Keycloak registrar/reviewer MFA/TOTP/PKCE and signed tenant A/B API 401/403/SQL 429. Close only scoped #146 after GREEN. Parents #128/#18/#115/#113 remain OPEN for real Azure SQL UAI, production migration/no Terraform administrator password, IP/ingress and privacy governance. #17/#13/#15 custody and qualification remain OPEN.

## Residual stop line

This point-in-time check covers only **two named V019 tables** in **explicit opt-in Entra PostgreSQL API mode**. It does not prevent an authorized owner from changing ACL after startup, revoking runtime EXECUTE, altering/dropping SQL objects, changing SQL search_path or grants on future tables, rolling back the quota database clock, bypassing HTTP auth in default password mode, violating data retention/DPIA, or establishing legally qualified timestamps. Correct privileges must be granted/reviewed by independent production SQL administrators. Existing V019's shared-writable-primary quota enforcement and V020 owner cleanup remain separate requirements.
