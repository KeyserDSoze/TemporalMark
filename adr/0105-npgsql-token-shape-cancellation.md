# ADR 0105 — Validate opaque Entra token shape at generic Npgsql password-provider boundary

Status: **Accepted for scoped offline hardening [#140](https://github.com/KeyserDSoze/TemporalMark/issues/140)**, 2026-11-21. Parent [#128](https://github.com/KeyserDSoze/TemporalMark/issues/128) and [#18](https://github.com/KeyserDSoze/TemporalMark/issues/18) remain OPEN; no Azure apply, real SQL grant, migration or qualified-evidence claim.

## Review and threat boundary

Reviewed ADR 0001 modular on-prem/Azure portability, ADR 0096 Npgsql 10 token-only datasource, ADR 0097 ACA local managed identity REST token provider, ADR 0100 optional production-environment-only API prelisten SQL role check, ADR 0103 duplicate token JSON key rejection, ADR 0104 whole-token HTTP response timeout; `docs/ENTRA_POSTGRES_NPGSQL_CANDIDATE.md`, `docs/AZURE_CONTAINER_APPS_POSTGRES_IDENTITY_CANDIDATE.md`, `docs/THREAT_MODEL.md`, `docs/COMPLIANCE.md`; current `EntraPostgresDataSourceCandidate`, `ContainerAppsPostgresManagedIdentityCandidate` and existing Provisioner.Tests. The Npgsql password provider receives one opaque credential over TLS for each new physical connection, always with fixed scope `https://ossrdbms-aad.database.windows.net/.default`. The higher-level ACA supplier checks the returned token is ASCII printable and <=16000 characters, but the independent public `RequestTokenAsync` adapter currently accepts **any nonwhitespace string** from a caller-supplied delegate, including control/NUL/line-break/unbounded Unicode and multi-megabyte strings. That makes downstream resource use and future logging/credential handling dependent on every current/future delegate implementing the same checks. Another race: the caller may cancel while a callback is running, but if a cooperative callback returns successfully after cancellation, no second cancellation check currently stops the result reaching Npgsql. These are offline boundary safety properties, not evidence that actual Azure JWT syntax/audience/role claims are correct.

Source context: Microsoft's [Azure PostgreSQL managed identity](https://learn.microsoft.com/en-us/azure/postgresql/security/security-connect-with-managed-identity) explains bearer tokens used as PG credentials; [Npgsql security](https://www.npgsql.org/doc/security.html) describes asynchronous password providers. The existing concrete ACA provider's bound and its unit tests are the local, already accepted shape limit; this ADR harmonizes the **generic adapter**, not a general JWT validator.

## Decision

1. At the **generic Npgsql token callback** `EntraPostgresDataSourceCandidate.RequestTokenAsync`, after the trusted supplier returns, reject null/empty, length > **16,000 characters**, and any character outside printable ASCII `! ... ~` (0x21..0x7E). This is exactly the local ACA provider's existing bound; legitimate Azure opaque/JWT bearer strings use printable ASCII. Do not trim or sanitize bad values: return **no credential** and fail closed. 16,000 printable characters at boundary are allowed; test exact upper edge and 16,001 denied. Do not log or return bytes, hashes, prefixes, character classes, SQL connection string, or original supplier exception. This protects both current ACA and future caller-supplied credential factories.
2. **After awaiting** the token callback, recheck the *original caller cancellation token* before validating/returning the token. Preserve existing pre-call cancellation behavior. If the caller cancelled after the callback began, throw `OperationCanceledException`; if a supplier silently ignored cancellation and returned, never forward a stale/unwanted credential. The explicit caller's cancellation must remain distinguishable from arbitrary external provider exceptions and propagate. Other supplier failures and invalid token strings are converted into the existing **fixed generic `InvalidOperationException`, no inner exception**.
3. Keep exact fixed scope, async-per-new-physical-Npgsql-open policy, synchronous-open denial, token-free connection strings, mandatory TLS VerifyFull/GSS Disable and canonical host constraints. Never add token cache, retry, logging, SQL password fallback, Azure/Cloud dependency, environment-selected dev credentials or export to disk. No change to `ContainerAppsPostgresManagedIdentityCandidate` concrete validation, default OSS/on-prem path, API identity mode, PostgreSQL migrations (V001–V020 unchanged), Terraform or Azure environment.
4. **TDD RED-first:** commit xUnit tests on `main` before implementation: multiple malformed ASCII control/unicode and 16,001-length canaries, returned token redaction/no inner exception, true 16,000 printable acceptance and single supplier scope, cancellation occurring inside an otherwise successfully completing callback. Run GitHub backend on tests-only main SHA and inspect actual failing tests; implement minimal source only afterward. Then full current core CI including Docker PostgreSQL 17, Keycloak signed MFA/tenant-isolation and browser tests, no tests against Azure.
5. Record this as limited **input-shape/resource and cancellation hardening** only. It does NOT cryptographically validate JWT/access token, real Entra audience/issuer/expiration or revocation, authenticate the selected UAI to a live private Azure PostgreSQL instance, establish SQL role/grant least privilege, prove pool session revocation, or eliminate Terraform-stored SQL admin password/history. These remain open #128/#18 with CAB approvals; independent GDPR privacy #113/#115, WORM #17 and eIDAS QTSP legal #13/#15 are not addressed.
