# ADR 0124 — Bound the serialized v1 manifest and physical ZIP output in the .NET period exporter

Status: **Accepted for scoped TDD [#166](https://github.com/KeyserDSoze/TemporalMark/issues/166)**, 2026-11-22 Europe/Rome. This is an **unqualified, non-authorizing synchronous export interoperability/resource guard**, not a WORM/qualified custody mechanism. Parent #17, QTSP #15, legal #13, signed monotonic custody #61/#64 and production #18 remain OPEN.

Previous latest docs-inclusive `main 07e1b4e` passed [GitHub Actions 45014678179](https://github.com/KeyserDSoze/TemporalMark/actions/runs/45014678179) with 34/34 Python v1, 280/280 Business, real PG17 247/247, 20 migration hashes and four original jobs.

Existing .NET pilot export enforces <=10,000 receipts, <=1 MiB raw retained DER per record and <=64 MiB cumulative raw DER **before** creating its in-memory ZIP. But it serializes the manifest's `EvidenceReference`, `ProviderId` and other repository metadata directly into a compressed `ZipArchiveEntry`, without bounding the actual serialized JSON length or ZIP bytes. The independent offline v1 verifier rejects **manifest.json uncompressed >8 MiB** and **physical ZIP >80 MiB**. A legacy/owner-modified row may have a valid DER hash, UTC, tenant and `Unverified` state yet contain a large metadata string. Its compressed ZIP may appear tiny while its original JSON manifest is too large for the offline v1 checker. Counting C# `string.Length` or estimated character counts is insufficient: JSON escape sequences and UTF-8 encoding change serialized byte length. A missing producer limit is a **pilot interoperability/capacity defect**, not proof of a real attack or legal forgery.

References: [.NET JsonSerializer.SerializeAsync](https://learn.microsoft.com/en-us/dotnet/api/system.text.json.jsonserializer.serializeasync), [.NET ZipArchive](https://learn.microsoft.com/en-us/dotnet/api/system.io.compression.ziparchive), [Python zipfile](https://docs.python.org/3/library/zipfile.html).

## Decision — ADR-first, tests-first, incremental on main

1. Commit this ADR **first** on `main`. Then commit only new Business xUnit tests with valid original small DER/SHA/tenant/period: reject (a) one `EvidenceReference` of 8 MiB ASCII plus JSON overhead, (b) several distinct receipts whose separately smaller metadata aggregate >8 MiB with a shared test string, (c) Unicode metadata whose **JSON-escaped UTF-8 output** exceeds 8 MiB even though character length is lower. Every negative expects `ExportTooLargeException`, not a corrupted-row or different error; test a large accepted but <=8 MiB manifest and empty/ordinary exports. Confirm **genuine** GitHub backend RED missing-denial assertion failures (not fixture, compiler or OOM) before touching production code.
2. After RED, build the same v1 manifest in memory as the current anonymous object, serialize **once** to a `MemoryStream` with a **hard 8 MiB maximum on actual emitted bytes** enforced during both sync and async `Write` paths. Reject the next attempted bytes with the existing generic `ExportTooLargeException` before constructing/allocating any ZIP. Copy those **exact serialized bytes** into the `manifest.json` ZIP entry to avoid a divergent second serialization, while preserving all field names, timestamps and pilot `Unverified` status. Do not use an unbounded `SerializeToUtf8Bytes` temporary or a character-only estimate. Do not include untrusted manifest values in diagnostics.
3. Before returning the completed ZIP bytes, require **physical ZIP length <=80 MiB**, also raising `ExportTooLargeException` (API 413) otherwise; no partial ZIP or success audit download. Retain source <=1 MiB/DER, <=64 MiB DER and <=10k records, current UTC/tenant/hash/status checks, and same OSS on-prem/Azure executable. No SQL migration, new API schema, retention policy or cloud-specific dependency.
4. Update operator runbooks, ADR, threat model, roadmap and README with real TDD evidence and limitations. Close **only #166** when the exact final docs-inclusive main SHA demonstrates actual GitHub Actions backend/frontend/terraform/docker-smoke **4/4 success**, ci-verdict+combined success, new Business suite, Python offline **34/34**, real PostgreSQL17/Keycloak/restore/ingress tests and all **20** migration checksums. If still unverified, keep the issue open.

## Residual security/legal boundary

This fixes the **producer/verifier byte-budget mismatch** and bounds manifest output bytes, **not PostgreSQL row materialization, maximum allocation of the JSON serializer's own short-lived buffers, memory consumed by concurrent exports, temporary in-memory ZIP allocation before the final check, streaming arbitrary-period exports, authenticated/signed manifest, immutable WORM retention, complete period evidence, RFC3161/CMS cryptographic validity, historic QTSP/EU Trusted List or CAB qualification**. All current receipts remain `Unverified`; no direct trust-status promotion is implied. Production and qualification release gates #17/#15/#13/#61/#64/#18/#38/#50 remain OPEN.
