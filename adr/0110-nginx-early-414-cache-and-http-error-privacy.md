# ADR 0110 — Protect pre-location Nginx 414 responses from caching and request-line diagnostic leakage

Status: **Accepted only for scoped shared Nginx web-container hardening [#145](https://github.com/KeyserDSoze/TemporalMark/issues/145)**, 2026-11-21. Parent #115/#113 and Azure #18 remain OPEN; no legal WORM/eIDAS/QTSP claim. No production cloud, CAB or GDPR/DPIA review.

## Existing architecture and standards

Reviewed ADR 0001 (on-prem/Azure application parity), 0084 (exact three-field web Nginx access log), 0102 (Nginx+Kestrel 4096-byte search POST body gate), 0108 (per-instance actual connected-peer 2r/s burst12 search preauth limiter), 0109 (case-insensitive full-match search location), current `docker/nginx-privacy-logs.conf` installed at HTTP scope by pinned shared `src/frontend/Dockerfile`, `docker/nginx.conf.template` server with three-field access log, sensitive search `error_log crit`, Nginx `limit_req`, generic local 429, and active `.github/workflows/ci.yml` real #117/#119/#136/#143/#144 privacy probes. Reviewed docs/COMPLIANCE, NGINX_ACCESS_LOG_PRIVACY, NGINX_EDGE_SEARCH_BURST, IMPRINT_SEARCH_BODY_BUDGET, THREAT_MODEL and ROADMAP. All 20 PostgreSQL migrations, active Azure Terraform, JWT auth and tenant SQL search quotas are outside scope.

**Gap:** Nginx rejects an oversized request line **before location matching** with HTTP `414 URI Too Long`, so the existing search-only `error_log /dev/stderr crit` and generic 413/429 protections cannot be assumed to cover this path. Official [Nginx core module](https://nginx.org/en/docs/http/ngx_http_core_module.html#large_client_header_buffers) says a request line longer than one configured large header buffer yields 414; [RFC 9110 §15.5.15](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.15) explicitly says a 414 response is **heuristically cacheable** unless otherwise controlled. At present Nginx's web server has no explicit no-store 414 response policy and the HTTP-level Nginx error logger may inherit inherited noisy diagnostics from the image before any `location` is selected. Nginx official [logging contexts](https://docs.nginx.com/nginx/admin-guide/monitoring/logging/) support `http` and `server` error-log scope. These are privacy boundary considerations; test actual leak rather than claiming it occurs without evidence.

## Scoped decision

1. **Tests-first real pinned Nginx Docker** (before production change): guarded synthetic HTTP/1.1 local fixed-loopback request-target **over 16 KiB**, with fake query/document imprint/token/agent canaries and no live JWT, must yield **414** and `Cache-Control: no-store`. Reject any reflected synthetic canary or tenant/match fields in response or whole actual web-container stdout/stderr; continue to require only `tm_access status/method/duration` records, including a 414. 200 SPA and ordinary 401 small anonymous search remain unaffected; require no forced no-store on successful static SPA. CI runs this step before #143 burst and after existing #136 413 privacy probe. Observe actual Docker RED where missing 414 no-store (or leak) is the reason, not build/network failure.
2. **After observed RED:** static shared `docker/nginx-privacy-logs.conf` (already installed at Nginx **HTTP** scope) adds a tightly scoped `map $status $tm_early_reject_cache_control { default ""; 414 "no-store"; }`. Existing `docker/nginx.conf.template` **server** adds `add_header Cache-Control $tm_early_reject_cache_control always;`, so only responses with a 414 status receive this additional header; other response cache directives including SPA/PWA are preserved. **Do not add a new global HTTP-scope `error_log crit`**: unlike the risk initially hypothesized, real Docker's default early 414 error path emitted only `tm_access status=414 method=- duration=...` and no canary-bearing stderr/stdout error message (see test-only RED evidence below). Suppressing all below-critical Nginx HTTP errors would make unrelated incident diagnostics less useful without fixing an observed leak. Keep existing explicit sensitive-location `error_log crit`, 4KiB gate, 2r/s burst12, generic 429, upstream `proxy_intercept_errors off`, original URI forwarding, all other routes and direct Kestrel unchanged.
3. **Avoid `error_page 414 = @named` internal redirects**: an Nginx early 400/414 rejection may have no valid normalized URI and could be incorrectly turned into a 500, as recorded by [Nginx ticket #1756](https://trac.nginx.org/nginx/ticket/1756) and [Nginx support discussion](https://github.com/nginx/nginx/discussions/1087). The conditional header approach avoids rewriting or internally redirecting malformed URI requests. No code changes to status/method, no custom 414 body, credentials, SQL, roles, Terraform or external tokens.
4. Explicit **operations tradeoff after real RED**: preserve inherited Nginx HTTP error diagnostics rather than suppress all below-critical errors, because the actual pinned Docker Nginx early 414 fixture emitted **no URI/query/token canaries in web stdout/stderr**. This is **not a proof for all other HTTP errors, malformed headers, managed Azure ingress, WAF/CDN, API, Keycloak, sidecars or operator overrides**. Retain the scoped `error_log crit` for the sensitive search route, review independent sanitized structured diagnostics and DPIA before real deployment. Early rejected requests may have an unparsed HTTP method; the actual access event was `tm_access status=414 method=- duration=...`, still inside the *three-field* allowlist. No persistent IP/hash/body storage added.
