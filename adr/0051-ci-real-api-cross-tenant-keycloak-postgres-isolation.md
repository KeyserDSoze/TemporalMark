# ADR 0051 — Real signed Keycloak and PostgreSQL two-tenant API HTTP isolation matrix (CI only)

Status: **accepted for disposable integration test scope, not production RLS or a qualified trust service**, 2026-11-16. Issue [#82](https://github.com/KeyserDSoze/TemporalMark/issues/82), children of open [#20](https://github.com/KeyserDSoze/TemporalMark/issues/20) and [#14](https://github.com/KeyserDSoze/TemporalMark/issues/14).

## Reviewed baseline and security boundary

Reviewed ADR 0001/0003/0005/0040/0050, `docs/ROADMAP.md`, `docs/THREAT_MODEL.md`, `docker/keycloak/temporalmark-realm.json`, `docker/compose.yml`, `scripts/migrations/V001–V005`, `scripts/postgres-init/002_local_seed.sql`, `src/backend/applications/TemporalMark.Api/Program.cs`, `PostgresTenantAuthorization`, `PostgresTimestampRegistry`, `PostgresTenantAuditRepository`, existing PostgreSQL fixtures and four-job [GREEN CI 43888465332](https://github.com/KeyserDSoze/TemporalMark/actions/runs/43888465332). Scope is **real compiled Docker API**, Keycloak-issued signed JWT and a real PostgreSQL server; no fake authentication, unit-mocked membership, or client-controlled tenant selector.

The API's `/api/v1` group requires validated JWT issuer/audience/signature, and the endpoint's `TenantAdminAsync` requires `sub`, `organization_id`, signed `tenant_admin` and currently active matching organization and SQL membership. The authorization group protects list, summary, receipt, period export, audit and issue. Current browser test verifies only one seeded dev admin; it does not establish two-tenant isolation or 401/403 distinction.

## Decision: bounded TDD matrix

1. **Test first:** commit this ADR before adding a real HTTP integration script to the already tested `docker-smoke` job, run against `http://127.0.0.1:8080` and `http://127.0.0.1:8081` only. Use Python standard library, actual HTTP `401`/ `403` and JSON/ZIP/TSR decoding, not frontend mocks. The initial RED must show missing independent dev-only Keycloak user/tenant fixture, not a spurious unavailable server. The test verifies unauthenticated access for all seven route families is `401`, authenticated B/A identity, role denial, disabled membership and invalid bearer signatures; follow-up authenticated negative cases should distinguish `403` from `401`.
2. **Development-only signed token fixture:** provision a second fixed demo organization B and three separate disposable Keycloak subjects under existing `temporalmark` development realm: signed B `tenant_admin` with matching claim, a signed `tenant_admin` claiming B but **inactive SQL membership**, and an A `tenant_member`. Preserve separate signers and audience validation via the existing development-only password-grant client; add the necessary `organization_id` *access token* protocol mapper only to that explicitly labeled CI client. No password grant or fixture belongs in a production deployment. If testing wrong audience, use a distinct explicit CI client without the API audience mapper.
3. **Database canaries:** seed B only with the existing owner's `bootstrap_organization` function against the **disposable PostgreSQL CI owner**, not with API or an elevated new permanent login; add an inactive B membership separately. Insert one A and one B synthetic *unverified* DER-like canary response with distinct digests and cryptographically correct SHA256, and a distinct A/B synthetic audit row using the already installed development schema. A canary is **not** a real RFC3161 qualified mark or WORM-backed evidence. All real application fetches execute under existing `temporalmark_api` restricted login, not the fixture owner's login. Enforce explicit `CI_TEST_ONLY` invocation and a known localhost/disposable issuer before executing privileged fixture setup. Teardown is the existing CI `docker compose --profile witness-ci down -v`; never target a production database.
4. **HTTP assertions:** success for A and B `/me`, `/stamps`, `/summary`, `/audit`, respective receipt download and ZIP export; deny cross-tenant receipt with `404`, prove ZIP `manifest.json` includes only caller tenant and its canary, audit/summary/list exclude foreign canary, and client-supplied B/A `organization_id` in query/header cannot override the signed issuer membership. The false `tenant_admin` B subject with inactive SQL membership must yield `403`; a signed A `tenant_member` is also denied. API issue with unavailable configured external TSA must remain **503**, not qualified issuance, for authorized admin, and `403` for unauthorized. All unauthenticated calls remain `401`. Verify evidence responses' `Cache-Control: no-store` and audit of prepared access without claiming delivery.
5. **RED then GREEN:** source/test before Keycloak fixtures and SQL fixture creation; capture real CI failure on expected absent B token. GREEN fixture makes actual API + Keycloak + PostgreSQL tests pass. Never modify production auth code to bypass verification and never remove existing Keycloak real MFA, full PostgreSQL witness restore, locked-mode CI, PWA or Terraform jobs. Final exact-main all four jobs and live isolation assertions must be SUCCESS before closing only #82; parent #20/#14 remain open.

## Residual risks and explicit exclusions

The test uses **disposable development password grants** for its synthetic signed access JWTs and canaries, not real human MFA; other existing browser MFA/PKCE smoke remains independent. It neither establishes RLS across all SQL roles, production IdP live account revocation, independent custody, audited provisioning of the initial admin, malicious operator defense, signed reviewer WebAuthn authorization, RFC3161 verification, legal WORM storage nor QTSP eIDAS qualification. SQL owner can violate isolation and audit append-only constraints, so this is specifically HTTP-path scoped. Security #64/#61/#57/#50/#44/#38/#17/#13 and V015/V016 fail-closed restrictions remain OPEN.

## Implementation finding — Keycloak profile completeness and JWT lifetime

The first genuine RED [CI 43892292576](https://github.com/KeyserDSoze/TemporalMark/actions/runs/43892292576), SHA `46cbfc2`, reached real Keycloak and failed at absent `demo-tenant-b` (`HTTP 401`); all preceding main CI jobs/DB restore/MFA passed. Initial disposable fixture commit `582102e` then reached the same real password grant but Keycloak refused with `HTTP 400`, `LOGIN_ERROR resolve_required_actions`, `Account is not fully set up`. Dev-only fixture users need complete `firstName`, `lastName`, `email`, `emailVerified` fields, as existing imported working test identities do. This is an **IdP fixture integrity failure**, not evidence of a protected API bug.

For the dedicated genuine short-lived signed JWT case, Microsoft.IdentityModel.Tokens `TokenValidationParameters.DefaultClockSkew` is **300 seconds** by default (see [Microsoft documentation](https://learn.microsoft.com/en-us/dotnet/api/microsoft.identitymodel.tokens.tokenvalidationparameters.defaultclockskew)). This is too lenient for a strict fail-closed expiry acceptance test. Require `ValidateLifetime=true`, `RequireExpirationTime=true`, and `ClockSkew=TimeSpan.Zero` on the API's existing Keycloak/JWT bearer validator; the production operational contract **must** synchronize and monitor API/IdP host clocks. A zero clock tolerance can reject otherwise legitimate recently issued tokens when infrastructure clocks drift; that is an intentional availability trade-off, not independent UTC(k) proof or qualified timestamping.

The ZIP's internal manifest uses `JsonSerializer.SerializeAsync` without web camel-case options, hence its individual record property is `Id` (Pascal case); externally serialized HTTP list JSON uses web `id` casing. The integration test asserts each format as actually emitted, without weakening tenant scoping.

Close #82 only after exact-final-main full four-job CI and the genuine two-sided canary evidence matrix pass.
