**Technical confirmation:** PostgreSQL 17 [text `octet_length`](https://www.postgresql.org/docs/17/functions-string.html) returns *bytes*, not characters; [`CASE`/COALESCE](https://www.postgresql.org/docs/17/functions-conditional.html) conditionally projects values, and V001 `evidence_reference text` is nullable/unbounded. On the supported UTF-8 DB configuration, .NET `Encoding.UTF8.GetByteCount` counts the same logical text bytes before manifest/JSON encoding; JSON escaping can expand further, and remains independently capped by ADR 0124. The existing Business **positive** `ExportAcceptsLargeButInBudgetJsonManifestAndPreservesMetadata` accepts a legitimate 7MiB evidence reference and must continue passing: setting a new arbitrary 4KiB limit would be a backwards-incompatible regression.

## Threat and decision

The real PostgreSQL adapter's previous #172/#173/#174 one-statement SQL limits *DER*, but `evidence_reference` is still emitted unconditionally and `MapRecord` calls `GetString(10)`. A legacy/corrupt/compromised table may contain a very large reference with entirely SHA-consistent original 4-byte DER. This can force database-result transmission, Npgsql large managed text, API list/search JSON or ZIP source allocation **before** the existing 8MiB serialized ZIP manifest check. No observed cross-tenant leak or qualified timestamp invalidity is claimed.

1. **Admit at most 8,388,608 raw UTF-8 bytes for a single `EvidenceReference` and 8,388,608 total reference bytes across one selected read batch** (including search lookahead and export's selected 10,001 rows). NULL contributes zero and remains NULL, empty strings remain valid, exact boundary is inclusive. A 7MiB ASCII reference remains valid **with identical original content**. This is a *pilot resource* limit aligned with the already-existing 8MiB serialized ZIP manifest cap, **not** a legal metadata maximum; further JSON escaping/structural overhead can still cause the original ZIP `ExportTooLargeException`.
2. Commit this ADR **first**. Commit **tests only** in real PG17 xUnit and Business xUnit. A single SHA-consistent authorized 8MiB+1 reference must cause the **Postgres provider** (not merely Business) to reject on all four read surfaces before `GetString(10)`; an aggregate >8MiB from individually valid refs must reject entire page/search/export batch, not partial records. Exact-request ID and tenant filters preserve other-tenant/missing null/404. Preserve 7MiB positive, UTC ordering, null optional reference, 1MiB DER and original SHA256/hash/status. Business fake adapter must independently reject over-limit references. Real GitHub Actions RED must exhibit **missing-denial assertions with correct fixture/compilation**, not incidental failures.
3. **After genuine RED**, for page/search/export change each already-existing `WITH chosen AS MATERIALIZED` to additionally select **only `COALESCE(octet_length(evidence_reference),0)::bigint AS ref_bytes`**, not raw metadata. Extend existing window `guarded` with `bool_and(ref_bytes <= @max_ref_bytes) OVER ()` and `sum(ref_bytes) OVER ()`. Project **both** `response_der` (ordinal 9) and `evidence_reference` (ordinal 10) only when DER and reference per-row/aggregate admission succeeds; otherwise **`NULL::bytea` and `NULL::text` for every selected row**. The provider checks `IsDBNull(9)` before `MapRecord/GetFieldValue<byte[]>/GetString(10)`; use the existing generic page/search `InvalidOperationException` and specialized export `ExportTooLargeException` (HTTP 413). Preserve the selected row order, authorized org/imprint/UTC filters, one PG17 statement/MVCC snapshot and row-count lookahead. Never silently truncate a reference or rely on a stored hash to validate its origin.
4. For single GET preserve exact `WHERE organization_id=@org AND id=@id`. In **one** SQL statement combine existing DER cap and row-local `COALESCE(octet_length(evidence_reference),0) <= @max_ref_bytes` into the `CASE` guarding *both* DER (column 9) and reference (column 10). Found oversized row has NULL guarded DER and raises the **existing `ReceiptTooLargeException` before MapRecord**, preserving HTTP **409/no-store and zero prepared download audit**; missing/foreign ID remains `null`/404. No separate metadata preflight or race.
5. Business defense-in-depth: `DownloadReceiptAsync` after tenant and exact-ID checks rejects a returned reference beyond cap with the same `ReceiptTooLargeException`. `ValidateReturnedRecords` after tenant and DER limits but before SHA256 checks per-row and aggregate `Encoding.UTF8.GetByteCount(EvidenceReference)`. Page/search use generic `InvalidOperationException`; ZIP uses existing `ExportTooLargeException` to retain 413. No change to `TimestampRecord.Validate` (issuer path), no manifest schema change, successful API JSON/DER shape remains the same.
6. Update this ADR, registry runbook, threat model, roadmap, issue #175 with independently inspected test-only RED and exact docs-inclusive final 4/4 GREEN including Business+PG17, checked V001–V020 migrations/full restore, signed-Keycloak two-tenant 401/403/409/404/413 and audit, offline v1 checker and Nginx privacy. Close only child after confirmed exact-head combined status. Keep legal/WORM #17, QTSP #15, qualification #13, independent witness #61/#64, Azure #18 and WebAuthn #38/#50 OPEN.

## Alternatives rejected

- Truncate long references or omit the field silently: changes evidence metadata, hides corruption and breaks manifest provenance; fail closed instead.
- Apply a new 4KiB per-reference cap: **breaks the existing explicit 7MiB valid-export regression test** and existing public API behavior without governance approval.
- C#-only `GetString(10)` size check: fails too late, after PG/Npgsql wire materialization and allocations.
- Two SQL round trips (length then payload): opens a snapshot/time-of-check race; retain one statement.
- Scope to DER and trust the manifest's 8MiB cap: page/search have no manifest, and ZIP still loads arbitrary PG text first.

## Stop line and residual risk

Only **`evidence_reference`** is addressed by this ADR; `provider_id`, `policy_oid` and other unrestricted V001 text columns, unbounded global accepted concurrent request memory, internal PostgreSQL TOAST/CPU/sort, compromised database owner and signed independent custody remain outside scope. A raw-reference 8MiB admission is *not* a proof that a JSON ZIP manifest fits 8MiB after UTF8 escaping. The existing exact original DER/SHA256 and pilot `Unverified` read restrictions remain mandatory. This does **not** provide WORM/hold/retention, authenticated complete-period exports, CMS/TSR historical QTSP validation, own qualified TSA or CAB/AgID approval.
