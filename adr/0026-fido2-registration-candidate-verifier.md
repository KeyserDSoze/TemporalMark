# ADR 0026 — Fido2 4.3.3 registration candidate verification without trust activation

Status: **accepted for isolated, NON-AUTHORIZING WebAuthn attestation candidate processing only**, 2026-11-15. Child #52 of #44/#50/#46/#38. Read ADR 0017–0025, especially the V015/V016 issuer freeze (ADR 0025).

## Library decision and evidence

Use the current stable `Fido2` NuGet **4.3.3** (released 2026-11-11), compatible with .NET 10, MIT-licensed upstream `passwordless-lib/fido2-net-lib`. Prefer the maintained library's `IFido2.MakeNewCredentialAsync(MakeNewCredentialParams)` for WebAuthn clientDataJSON, authenticators, CBOR/COSE, challenge, RP/origin and attestation cryptographic parsing/verification. Do NOT write a homegrown WebAuthn CBOR/COSE/signature verifier, and do not use the v5 preview in production. Upstream public source `Src/Fido2/IFido2.cs`, `Src/Fido2/MakeNewCredentialParams.cs` and `Src/Fido2.Models/Objects/RegisteredPublicKeyCredential.cs` were reviewed.

The library can report successful `none` or `self` attestation; **this is NOT trusted hardware provenance**. It can also be configured without an FIDO Metadata Service (MDS) trust anchor. A syntactically correct result of `MakeNewCredentialAsync` does not prove independent human registrar consent, physical key custody, supply-chain certificate trust, approved user assignment, or SQL authorization.

## Isolation and invariants

1. Add an infrastructure-only `ReviewerWebAuthnAttestationCandidateVerifier` backed by `IFido2` 4.3.3. Instantiate per immutable, deployment-approved **exact HTTPS origin**, RP DNS from ADR 0017, and explicit library `Fido2Configuration` with `ChallengeSize=48`, `Origins={trustedOrigin}`, `RPID=rpID` and `Validate()`. The verifier is **not** wired to API/PWA, CLI or any SQL function. No migrations, credential registry, or role grants are changed by this increment.
2. The **original options** must come from a trusted server-side ephemeral registration record, not browser JSON. Require exact 48-byte stored challenge matching `CredentialCreateOptions.Challenge`, approved RP ID matching `CredentialCreateOptions.Rp.Id`, 32-byte independent reviewer-handle matching `options.User.Id`, distinct registrar and reviewer subject, bounded 120-second UTC lifetime and currently unexpired record. Require explicit `AuthenticatorSelection.UserVerification=Required` and `Attestation=Direct` or Enterprise (no None/Indirect). Never allow `CredentialMediationRequirement.Conditional`, which skips a user-presence check; the library request is built with its default **Optional** mediation.
3. Validate the raw browser `AuthenticatorAttestationRawResponse` size limits and exact `PublicKey` type before delegating to the library. A trusted **global** credential-uniqueness callback must be injected from an independent registry. Do NOT substitute `async _ => true`. (The future database registry and atomic global constraint are NOT implemented yet; the interface alone is not evidence of uniqueness.) No caller-supplied origin, RP, reviewer or registrar is trusted.
4. After library success, deny `AttestationType=none/self`, mismatched RP, user handle, credential ID and invalid missing key. Return only an **UNAPPROVED, UNTRUSTED, NON-ACTIVATING** candidate with hashes/metadata, not a COSE public key or stored credential object. Even a basic/attca/anonca format requires an independently approved metadata trust policy, CAB review, key custody and separately signed registrar consent before any activation. FIDO metadata, attestation trust-chain enforcement, live real browser virtual-authenticator fixture, global unique credential registry, atomic one-time challenge consumption, and actual human consent remain **#44/#50**.
5. V015/V016 remain in place: the old arbitrary-subject V013 registrar SQL issuance cannot be reenabled via this adapter. The old approval SQL grants remain unchanged and **must be removed** under #38 only after a separate signed, transaction-bound verifier exists. The new library itself does not qualify TemporalMark as a QTSP, timestamp service or legally preserved WORM archive.
6. Tests first RED then GREEN: bad/mutated scope, expired/weak UV, wrong RP/challenge, invalid sizes, self/none attestation, invalid ID, plus **real Fido2 cryptographic parsing** of deliberately forged CBOR/clientData which must throw. A fake result in tests is only a *candidate-handling simulation*, not claimed positive cryptographic proof. Four-job exact-main-head CI required to close #52.

## Operational and privacy notes

Only a hashed candidate credential ID and public-key hash should leave the isolated verifier; no raw JWT, TOTP, private key, attestation certificate, serial number or public-key bytes are logged. Any future attestation trust policy may collect device-identifying data and requires DPIA/privacy assessment, minimum necessary retention and owner approval for EU/Italian obligations. On-prem open-source / Azure use same backend library, with independent trust metadata and operational governance yet to be decided.

## Exact published 4.3.3 API audit and CI adaptation (2026-11-15)

The upstream `main` branch has **newer** interfaces than the NuGet 4.3.3 tag. The published stable tag `4.3.3` was fetched directly during review: it contains `IFido2` with only four methods and does not expose `Fido2Configuration.Validate()`, `MakeNewCredentialParams.Mediation` or `RegisteredPublicKeyCredential.RpId`. The first GREEN attempt used upstream-main APIs and CI correctly reported CS1061/CS0117, so source/test was corrected to the **exact pinned stable package** in `99bbfd6` and `a7abe77`; subsequent CI backend passed. Exact RP DNS+origin validation is implemented by TemporalMark's existing immutable `ReviewerWebAuthnRelyingPartyPolicy` and the Fido2 config; no related-origin/localhost exception or conditional mediation is enabled. The library's stable version performs verification against configured RP ID internally. Any positive test with a fake library is still only a non-authorizing result-shape check, never an accepted WebAuthn signer. Parent #44/#50 require production real-hardware/browser positive attestation and metadata trust.
