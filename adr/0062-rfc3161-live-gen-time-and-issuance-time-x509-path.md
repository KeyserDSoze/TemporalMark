# ADR 0062 — Bound live RFC 3161 signed genTime and verify issuer path at that instant

Status: Accepted as **live delegated pilot** time-consistency control (2026-11-16). Child [#93](https://github.com/KeyserDSoze/TemporalMark/issues/93) of still-open [#15](https://github.com/KeyserDSoze/TemporalMark/issues/15). **This is neither trusted UTC evidence nor historic revocation/qualified QTSP validation.**

## Architecture / documentation review and technical basis

Reviewed [ADR 0002](0002-qualified-vs-delegated-timestamping.md), [ADR 0052–0061](0061-rfc3161-operator-approved-offline-signer-x509-chain.md), [TSA HTTP operator guide](../docs/TSA_HTTP_TRANSPORT.md), [threat model](../docs/THREAT_MODEL.md), [roadmap](../docs/ROADMAP.md), live `ExternalRfc3161TimestampProvider`, its `ExternalRfc3161CertificateChainPolicy` and disposable RSA X.509 fixture tests. #92 introduced `X509Chain` with one operator-approved `CustomRootTrust` and embedded CMS intermediates only, but always sets `VerificationTime=DateTime.UtcNow` and never checks the signed TSA token's `genTime` against the live HTTP request interval. This conflates *validation now* with *certificate validity at signed issuance* and may silently accept a CMS-signed but absurdly stale/future timestamp.

[RFC 3161 §2.4.2](https://www.rfc-editor.org/rfc/rfc3161#section-2.4.2) defines `TSTInfo.genTime` as the UTC creation time of the token, with optional TSA-declared accuracy. The signed `genTime` cannot by itself prove independently synchronized UTC. [.NET explicit X509ChainPolicy.VerificationTime](https://learn.microsoft.com/en-us/dotnet/core/compatibility/cryptography/7.0/x509chainpolicy-verification-time) checks chain validity at the chosen date/time and sets `VerificationTimeIgnored=false`; relying on an implicit now is incorrect for issued tokens. A live issuance API can separately use the locally observed HTTP time interval as a bounded consistency check, without claiming qualified accuracy.

## Decision

1. Introduce `ExternalRfc3161IssuanceTimePolicy.ValidateLiveGenTime(DateTimeOffset signedGenTime, DateTimeOffset requestStartedAt, DateTimeOffset responseReceivedAt)` with an **inclusive fixed 120-second clock-skew allowance**: require `responseReceivedAt >= requestStartedAt`; require `signedGenTime >= requestStartedAt - 120s` and `signedGenTime <= responseReceivedAt + 120s`. Convert all three inputs to UTC for comparison. Reject default/extreme `DateTimeOffset.MinValue/MaxValue` boundaries and out-of-range clock subtraction; errors have generic `TimestampProviderResponseException` text with no timestamp/issuer details. The 120s window is an explicit conservative pilot-operational tolerance, **not an RFC 3161 mandated accuracy, legal proof, trusted NTP reading or negotiable tenant setting**. A compromised pinned TSA key can still lie within that window. Operators must synchronize deployment hosts and detect clock drift independently.
2. Capture `requestStartedAt=DateTimeOffset.UtcNow` immediately **before** the actual named TSA `HttpClient.SendAsync`; capture `responseReceivedAt=DateTimeOffset.UtcNow` when the entire length-bounded response body has been buffered. After the existing RFC 3161 DER/nonce/imprint/CMS signature checks, verified signer EKU, SHA-256 leaf pin and operator-approved reqPolicy/TSTInfo.policy, validate the **same CMS-signed** `token.TokenInfo.Timestamp` with `ValidateLiveGenTime`. No unsigned HTTP dates, untrusted tenant timestamp or CMS `signingTime` attribute is a substitute. This pilot is for fresh issuance only; historical archived tokens require a different verifier with preserved external time evidence.
3. Refactor `ExternalRfc3161CertificateChainPolicy.CreateOfflineChain` and `ValidateSignerChain` to take an **explicit, mandatory** validated `DateTimeOffset signedIssuanceTime`, set `X509ChainPolicy.VerificationTime=signedIssuanceTime.UtcDateTime` (disables `VerificationTimeIgnored` under .NET 10) before `Build`, and continue strict `CustomRootTrust`, `CustomTrustStore` with only reviewed root, CMS-only `ExtraStore`, `DisableCertificateDownloads=true`, `RevocationMode=NoCheck` and `VerificationFlags=NoFlag`. Never default to current time in the provider. The historical date is a **certificate validity reference point**, not proof the cert was *not revoked* then.
4. TDD order: commit ADR to `main` first; commit RED-first boundary/offset/clock-reversal unit tests plus explicitly timed certificate-root→leaf and root→intermediate→leaf fixtures and observe failing GitHub backend. Then implement time policy, named provider time capture/verification and time-parameterized custom root X509 chain. Update old chain tests to supply explicit dates; no change to no-URL provider preflight or existing HTTP/TLS security. Update docs/threat/roadmap and close child #93 **only** on exact final-main 4/4 GitHub Actions GREEN jobs.
5. Maintain unchanged pilot receipt status `Unverified`. Neither Azure nor on-prem requires a mandatory cloud timing service; both must deploy reliable NTP/chrony/system UTC sync and audit drift.

## Residual risks and forward work

A **signed** `genTime` and ±120 s local consistency test do not make UTC traceable to UTC(k) or satisfy qualified timestamp precision/time controls. A compromised approved signing leaf, malicious operator CA/pin/policy, unobserved local clock jump inside the interval, network delay and TSA-declared accuracy uncertainty may all defeat assurance. No CRL/OCSP revocation, certificate revocation **at signed issuance**, historical EU Trusted List qualified service status, independently witnessed UTC, real QTSP interoperability, long-term verification archives, WORM (#17) or legal CAB/AgID qualification (#13) are implemented. Parent #15 remains OPEN.
