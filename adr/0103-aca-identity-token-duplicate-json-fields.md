# ADR 0103 — Reject ambiguous duplicate managed-identity response JSON fields before Npgsql token acceptance

Status: **Accepted for scoped offline credential-boundary hardening [#138](https://github.com/KeyserDSoze/TemporalMark/issues/138)**, 2026-11-21. Parents [#128](https://github.com/KeyserDSoze/TemporalMark/issues/128) and [#18](https://github.com/KeyserDSoze/TemporalMark/issues/18) remain OPEN. No live Azure, SQL grant, Terraform apply, or production authorization.

## Context and evidence

Reviewed ADR 0001, 0097 and 0100; `docs/AZURE_CONTAINER_APPS_POSTGRES_IDENTITY_CANDIDATE.md`, `docs/API_POSTGRES_ENTRA_PRELISTEN_CANDIDATE.md`, `docs/THREAT_MODEL.md`, .NET 10 `ContainerAppsPostgresManagedIdentityCandidate.GetTokenAsync`, existing in-memory fake HTTP tests, Npgsql 10 callback and explicit API opt-in. The existing bound 32 KiB response parser reads `resource`, `token_type`, `client_id`, `access_token`, `expires_on` with `JsonElement.TryGetProperty`; Microsoft's [.NET API documentation](https://learn.microsoft.com/en-us/dotnet/api/system.text.json.jsonelement.trygetproperty?view=net-10.0) states that when multiple identical JSON properties exist, **the last definition wins**. An ambiguous response can have a different interpretation in another decoder, verifier or future audit component. Microsoft [Container Apps managed identity REST documentation](https://learn.microsoft.com/en-us/azure/container-apps/managed-identity) describes the expected token response and locally injected `IDENTITY_ENDPOINT` / confidential `IDENTITY_HEADER`. No remote identity endpoint is trusted by this proposal; the existing pinned-loopback transport and fixed SQL token audience remain necessary.

## Decision

1. Before extracting any credential or metadata from the already-bounded JSON object, iterate **top-level property names** and reject **any duplicate name using ordinal case-insensitive comparison**. Reject equal-value duplicates as well as conflicting values, and case-variant aliases such as `access_token` / `Access_Token`; do not try to choose first or last. This is deliberately stricter than `JsonElement.TryGetProperty` and prevents cross-decoder ambiguity. Require the current exact canonical required names and values unchanged; optional unique unknown fields remain allowed for compatible Azure response evolution. No extra recursive parsing or nested data trust.
2. Reuse the existing generic `InvalidOperationException` failure boundary with **no inner exception**, raw JSON, bearer, identity header or private host in logs/errors. Fail closed and do not retry, select ambient identity, fall back to SQL password or cache token. Preserve explicit cancellation handling. Keep HTTP 200, application/json, size, expiry, UAI client ID and resource checks unchanged.
3. **TDD:** after this ADR, commit RED-first in-memory HTTP xUnit test(s) exercising exact and differently cased duplicate fields, equality/conflict, no token leak/one request, and valid optional unique fields. Obtain an actual failing GitHub backend result on that tests-only main SHA before source implementation. Implement the minimum change in the existing Infrastructure file, rerun all tests and real Docker PostgreSQL/Keycloak plus frontend, Terraform mock CI. No new NuGet dependencies, SQL migrations, API surface, environment configuration, Terraform apply or cloud token request.
4. Update the operator runbook/threat model to specify that this is **one syntactic token-response hardening only**. It cannot attest ACA local endpoint integrity against a compromised same-container process, real Entra token signature, Azure directory status, live SQL role mapping, pooled-session revocation, provider response stability or CAB readiness. Existing `ContainerAppsEntraCandidate` remains nondefault, Azure Terraform reference remains legacy SQL-password-based and stores `administrator_password=var.postgres_password` in state. On-prem OSS behavior stays unchanged.
