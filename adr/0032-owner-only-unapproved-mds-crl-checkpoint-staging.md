# ADR 0032 — Owner-only PostgreSQL **UNAPPROVED** MDS/CRL candidate version checkpoint

Status: **accepted only for SQL anti-rollback candidate staging and integration testing, not real FIDO metadata trust**, 2026-11-16. Scoped child [#62](https://github.com/KeyserDSoze/TemporalMark/issues/62) of #61/#57/#55. Reviewed ADR 0025–0031, docs/DATABASE_MIGRATIONS.md, V015/V016 registrar interlocks, PostgreSQL 17 insert/row-lock semantics, and FIDO August 2026 R3→R46 root change.

## Threat and critical trust boundary

The cryptographic fixtures from #58–#60 use disposable private keys and **arbitrary caller-supplied roots**. They do not provide independently validated FIDO Alliance MDS JWS, R46 trusted signing root, issuer-scoped live CRL/OCSP, or a signed immutable checkpoint. A hash/serial stored in PostgreSQL is **not** proof of a trusted signature, provenance, freshness, or manufacturer status. Restoring an old PostgreSQL backup can restore an old "highest" serial. A malicious schema owner/superuser can edit ordinary tables and triggers. Therefore any positive record **must remain UNAPPROVED forever in this component** and must never grant enrollment/SQL authority.

Official FIDO [MDS changelog](https://fidoalliance.org/mds-changelog/) reports GlobalSign R46 rollout in August 2026, with R3 cross-cert until 2029-03-18. PostgreSQL [ON CONFLICT](https://www.postgresql.org/docs/17/sql-insert.html) and [row-level locks](https://www.postgresql.org/docs/17/explicit-locking.html) permit per-key serialization of concurrent writers within **one PostgreSQL primary**. Neither is a distributed immutability nor disaster recovery guarantee.

## Narrow implementation and rationale

1. Forward-only V017 creates **`public.mds_unapproved_candidate_checkpoints`** keyed by `(candidate_kind, issuer_key_sha256)` and an ordinary append-only-by-trigger **`public.mds_unapproved_candidate_events`** table. Kinds are only `MDS_BLOB` and `ISSUER_CRL`. Each row stores only uppercase 64-hex issuer key identity SHA-256 (which may be **untrusted**), evidence SHA-256, an untrusted **source policy fingerprint**, strictly positive BIGINT `candidate_serial`, a bounded approval-change reference and PostgreSQL observation/expiry timestamps. No JWT, CRL bytes, secret/public keys, certificate subject or PII. Events record accepted **higher** versions and initial records, but not idempotent same-version retries. All rows and returned status are expressly `UNAPPROVED`, not trusted attestation or a certificate-status service.
2. Define only **`public.record_unapproved_mds_checkpoint_candidate(text,text,bigint,text,text,integer,text)`**, owner-invoked (no `SECURITY DEFINER` or app-facing SQL executor), additionally refusing sessions whose `session_user` or `current_user` do not exactly match the physical checkpoint table owner. `REVOKE ALL` function and tables from `PUBLIC`, approver/provisioner/runtime/registrar groups; create **no new LOGIN, group membership, vendor root or application path**. If some deployment accidentally grants EXECUTE directly to a separate SQL login, the internal owner-session check still denies the function; ordinary SQL schema owners/superusers remain trusted administrators.
3. A single atomic function transaction obtains a new key via `INSERT ... ON CONFLICT DO NOTHING` followed by `SELECT ... FOR UPDATE` for existing keys. In PostgreSQL READ COMMITTED, unique-index conflicts and the row lock serialize concurrent candidates. Transactions at stricter isolation may receive serialization failures and **must not** retry invisibly to accept stale data. Reject missing/invalid uppercase fingerprints, nonpositive serial or out-of-range (60–86400 s) TTL, unsafe source/change identifiers, versions lower than the recorded serial, equal serial **with changed content or source-policy fingerprint**, and records expired by the **database clock** even if a higher serial arrives. Equal serial + identical content and pinned source within validity is a **read-only UNAPPROVED idempotent** observation; higher serial with same source-policy fingerprint advances once and appends exactly one event. SQL CHECK constraints protect row shape, event UPDATE/DELETE triggers reject normal mutations. No arbitrary caller-supplied current time, last-update override, blank "renew" or last-write-wins merge.
4. A record that has expired is **quarantined**: normal migration-owner staging cannot silently "recover" it by submitting a fresh higher version. Only an independently reviewed, separately designed recovery protocol can reconcile signed authoritative evidence and unlock a new checkpoint; the schema owner can always bypass ordinary controls and is not a cryptographic witness. No API/CLI/runtime entry point is created.
5. TDD RED first in **live PostgreSQL** tests, then V017 GREEN and CI 16→17 migration count. Test independent issuer/kind keys, rollback/equivocation, no TTL extension on idempotent retry, two concurrent same-key submissions, denied group grants/function access, expired clock and append-only-history boundaries. No change to applied V001–V016 checksums. Four-job exact final-head GitHub CI before closing **only #62**; parent #61 stays OPEN because **disaster recovery, independent signed checkpoints/roots, issuer AKI+CDP/CRLNumber and cross-region replay/corruption protection** remain missing.
6. Security release stop: #61/#57/#55/#53/#44/#50/#46/#38 remain OPEN. No FIDO credential ACTIVE state, new issuer trust, SQL reviewer/registrar grant, timestamp signature, legal WORM/eIDAS qualification or QTSP claim. V015/V016/suspended registrar CLI and on-prem/Azure parity remain unchanged.

## Further work required under #61

A new separately approved adapter must independently verify signed/current FIDO BLOB JWS/x5c and issuer-scoped CRLs against CAB-approved R46 pins, signed CRL numbers and endpoints (including offline import/SSRF policy), and keep a **monotonic external signed/immutable witness** that can detect old DB backups, cross-region split-brain, owner/admin tampering or backup corruption. Root/key rollover must be formalized and audited; clock rollback, outage, stale snapshots and same-version equivocation across **separate primaries** must deny rather than silently accept. CAB/DPIA and independent human authorization before connecting anything to real reviewer enrollment. This child **does not** satisfy those requirements.
