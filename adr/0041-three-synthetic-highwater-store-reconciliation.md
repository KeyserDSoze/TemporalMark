# ADR 0041 — Compare three synthetic high-water observations, without independent custody

Status: **accepted only for a non-authorizing test preflight**, 2026-11-16. [#72](https://github.com/KeyserDSoze/TemporalMark/issues/72) is a narrow child of release-blocking open [#64](https://github.com/KeyserDSoze/TemporalMark/issues/64), [#61](https://github.com/KeyserDSoze/TemporalMark/issues/61), [#57](https://github.com/KeyserDSoze/TemporalMark/issues/57). Reviewed ADR 0032–0039, docs/MDS_CRL_SIGNED_FILE_HIGH_WATER_JOURNAL.md, docs/MDS_CRL_SEPARATE_POSTGRES_WITNESS_TEST.md, V017, CI full logical `pg_dump/pg_restore` and security tests. References: [PostgreSQL 17 privileges](https://www.postgresql.org/docs/17/ddl-priv.html), [pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html), [.NET 10 RSA.VerifyData](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.rsa.verifydata?view=net-10.0).

## Problem / specific attack

The #69/#70 second PostgreSQL witness can retain synthetic latest serial=4 while main SQL is restored to 3. But the **witness superuser**, Docker host, backup operator or independently malicious privileged admin may rewrite the second witness checkpoint to serial=3 and replay an old correctly signed manifest+seal along with the fully restored primary DB. The existing two-server preflight then returns `UNAPPROVED` for a mutually consistent but **stale** set. PostgreSQL role grants do not protect against superuser/owner tampering and signatures without independently held *latest* evidence do not solve rollback. The #67/#68 test-file signed journal is another distinct storage medium; it is NOT itself immutable or off-host.

## Decision, limited trust boundary

1. Introduce **only an isolated .NET 10 test preflight**, with a clearly named `ReviewerMdsThreeSourceHighWaterCandidateReconciler`. Accept already-open primary-owner and separate read-only witness connections, plus an explicit absolute test-journal path, source-policy SHA256, caller-selected test journal public RSA key and its caller-selected SPKI SHA256, and the existing original separately signed manifest/seal and test pins. **No endpoint, CLI, enrollment, main SQL migration, production Azure dependency, registrar grant or trusted FIDO root**.
2. Fail closed on invalid journal, wrong key/pin, missing/stale/future signed events, absent writer/reader restrictions, missing DB row, dissimilar source policy/version/seal SHA, signature failure, stale main database, cancellation or provider outage. First verify all original file events with the existing ADR 0036 implementation; then call the existing ADR 0038 reader, whose ADR 0033/0034 subcomponents validate the signed source manifest/seal against exact V017 read-only primary snapshot. Compare latest serial and full uppercase seal SHA from the signed journal and separate DB using constant-time SHA comparisons. After SQL and original signature verification, re-open/re-verify the signed journal to catch ordinary concurrent changes. Never silently recreate a missing journal, accept a caller-chosen fallback digest or treat identical untrusted claims as production trust. Output only `UNAPPROVED/THREE_TEST_STORES_NO_INDEPENDENT_CUSTODY`.
3. Mandatory **RED/GREEN real CI** on original `MdsSeparatePostgresWitnessRestoreTests`: construct a correctly signed serial-3 then serial-4 journal outside both DBs, keep the latest on disk, then as the witness superuser **deliberately rewind** its checkpoint to serial 3. The actual **full logical restored primary DB** is also at serial 3. Prove old+old passes the existing TWO-source preflight as only `UNAPPROVED`, while the new THREE-source preflight denies because file still holds serial 4. Restore the synthetic witness checkpoint to 4 in `finally`, without accidentally changing normal app grants. Also test successful three-source preflight for current 4/4/4, missing/corrupt journal and wrong test pin; verify original report stays unapproved.
4. A separate explicit regression should demonstrate that replacing the file journal with an **older valid signed copy** while rewinding both SQL stores lets an attacker controlling all three storage states replay old test content. This is an **expected unresolved vulnerability**; we do NOT authorize or label it trusted. The test must not be represented as a production security control.
5. Work direct `main`, ADR before RED, CI logs for RED and GREEN, docs/ROADMAP and docs/THREAT_MODEL updated; close only #72 after all four GitHub Actions jobs succeed on *exact final HEAD*. Keep #64/#61/#57/#55/#53/#44/#50/#46/#38 open. V015/V016 registrar SQL freeze and suspended CLI remain unchanged.

## Residual production blockers

All THREE observations (main DB, second CI PostgreSQL, normal local signed file) are under the same disposable Docker runner/host operator with caller-selected test keys. A privileged attacker can roll back each, replace public key pins and signing roots, alter clock or data, race cross-store reads, or inject any newly signed synthetic higher serial. This design does not provide atomic distributed reads, quorum, remote append-only or Object Lock custody, trusted FIDO Alliance MDS R46 root and all-hop CRL/OCSP, authoritative clock, HSM key custody, CAB-governed approval, legal WORM audit, true PITR/regional disaster recovery, on-prem OSS/Azure production parity or qualified/eIDAS/QTSP evidentiary status. Production needs independently administered signed monotonic custody, secure root/key onboarding and rotation, operational backup/restore and incident ownership, plus separately independently audited protocol trust.
