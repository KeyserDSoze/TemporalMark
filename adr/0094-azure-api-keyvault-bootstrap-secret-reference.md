# ADR 0094 — API registry connection via pre-provisioned Key Vault secret and bootstrap user-assigned identity

Status: **Accepted for scoped prequalification [#127](https://github.com/KeyserDSoze/TemporalMark/issues/127)**, 2026-11-20. Azure parent [#18](https://github.com/KeyserDSoze/TemporalMark/issues/18), privacy [#115](https://github.com/KeyserDSoze/TemporalMark/issues/115) and evidence [#17](https://github.com/KeyserDSoze/TemporalMark/issues/17) remain OPEN.

## Existing state and reviewed decisions

Reviewed ADR 0001 (Azure/on-prem function parity), 0090/0091 (default private ACA ingress/environment), 0092/0093 (Azure Blob private network and limited read-only runner checks), `infra/azure/main.tf`, `variables.tf`, `terraform.tfvars.example`, all five Azure mocked-plan tests, `infra/azure/README.md`, `docs/THREAT_MODEL.md` and issue parent #18. Existing `azurerm_container_app.api.secret.value = var.registry_connection_string` stores the API's sensitive PostgreSQL connection string in Terraform-managed resource attributes/state. Terraform's `sensitive=true` hides routine CLI rendering but **does not prevent storage in state**. The PostgreSQL server's `administrator_password = var.postgres_password` is a separate unresolved sensitive state risk.

Microsoft [Manage secrets in Azure Container Apps](https://learn.microsoft.com/en-us/azure/container-apps/manage-secrets) states that a Container App may reference a Key Vault secret via managed identity and must have read access (Key Vault Secrets User). It specifically notes that a **system-assigned** identity cannot bootstrap a *create* command, because it does not yet exist, while a **user-assigned** identity may be supplied at creation. It documents secret-version-pinned URLs and unversioned auto-rotation; this slice chooses **version-pinned** changes for explicit review. Microsoft [Container Apps deployment troubleshooting](https://learn.microsoft.com/en-us/azure/container-apps/troubleshoot-deployment-errors) documents RBAC propagation and Key Vault networking and secret-reference failures. AzureRM [azurerm_container_app](https://registry.terraform.io/providers/hashicorp/azurerm/4.46.0/docs/resources/container_app) supports `secret.key_vault_secret_id` with an `identity` resource ID and the app's user-assigned identity. These references describe mechanisms, not evidence of an Azure deployment.

## Decision

1. Replace only `registry_connection_string` Terraform variable and `azurerm_container_app.api.secret.value` with `registry_connection_secret_uri` (a **non-secret, full versioned HTTPS** Key Vault secret URI, no query/fragment/userinfo) plus `registry_connection_key_vault_id` (full expected vault ARM resource ID). Both must be explicitly set and syntax-validated; a resource precondition rejects URLs targeting a vault other than the supplied ID. Requiring a 32-lowercase-hex secret version prevents unreviewed automatic latest-version rollout. The secret value is **not queried/created/read by Terraform**, logged, output or put in `terraform.tfvars.example`; sample URIs/ARM IDs are fictitious.
2. Create an `azurerm_user_assigned_identity` for API Key Vault secret reference bootstrap and a vault-scoped **Key Vault Secrets User** role assignment (no Owner/Contributor, no secret write). The operator must provision and approve a **dedicated** RBAC-enabled Key Vault and its secret *outside this Terraform stack*; vault-scope RBAC grants access to other secrets in that vault, so enforce one-purpose approved vault custody. Attach the UAI alongside the existing API **system-assigned identity** used by `Storage Blob Data Contributor` on the private evidence Storage Account, keeping the latter assignment intact. Make API app creation depend on the Key Vault RBAC assignment; this only establishes Terraform graph ordering, **not RBAC propagation or network reachability**.
3. Keep app environment variable `ConnectionStrings__Registry` referencing `registry-connection` secret name. Avoid application/runtime/SQL migration, frontend, on-prem, tenant, MFA, RFC3161 and legal custody changes.
4. **TDD RED first**: add a `mock_provider "azurerm"` `terraform test` plan for the existing API secret's missing Key Vault URI/non-null raw `value`. Commit and observe GitHub terraform job RED on a tests-only SHA before any Terraform source edit. Then implement and expand positive/negative Terraform tests: proper secret reference, identities, role and approved vault scope; reject insecure/invalid/unversioned/mismatching URI and vault ARM ID, preserve all prior 36 plan tests. Link to mandatory core Terraform CI.
5. This does **not** scrub existing remote state snapshots or backups, revoke old DB credentials, provision Key Vault, enforce a Key Vault private endpoint/firewall, prove Entra RBAC propagation, guarantee vault reachability from the ACA VNet, implement production migration jobs or remove `postgres_password` from Terraform state. Existing deployed state may already contain the old cleartext app secret: **treat it compromised until a reviewed state/version/backups/secret-rotation process**. An unreviewed live apply is forbidden; the default internal-only ACA and Blob Private Link remain. Unverified Azure deployment, WAF/log/DPIA, independent WORM and qualified/eIDAS governance remain OPEN.

## Completion boundary

Close #127 only after exact final docs-inclusive `main` SHA shows four core GitHub CI jobs SUCCESS and combined `temporalmark/ci-4-core-jobs=success`, real Terraform mocked-plan GREEN (new and preexisting), .NET/React, live PostgreSQL dump/restore, signed Keycloak MFA cross-tenant authorization, API and web synthetic privacy canaries.
