# ADR 0121 — Fail closed on unsupported qualification/incident labels at pilot registry read boundaries

Status: **Accepted for scoped test-first evidence metadata hardening [#156](https://github.com/KeyserDSoze/TemporalMark/issues/156)**, 2026-11-22 Europe/Rome. ## Reviewed source of truth / problem

Consulted ADR [0002](0002-qualified-vs-delegated-timestamping.md), [0004](0004-evidence-time-and-retention.md), [0074](0074-registry-page-export-integrity-and-unique-ids.md), [0076](0076-offline-zip-structure-sha256-self-consistency.md), [0120](0120-offline-period-zip-strict-envelope.md); `src/backend/domains/TemporalMark.Domain/Stamping/TimestampRecord.cs`, `src/backend/business/TemporalMark.Business/Stamping/TimestampIssueService.cs`, `src/backend/business/TemporalMark.Business/Registry/TimestampRegistryService.cs`, current `TimestampRegistryServiceTests.cs`, `scripts/migrations/V001__baseline.sql`, `docs/REGISTRY_INTEGRITY_READ_GATES.md`, `docs/OFFLINE_PERIOD_EXPORT_VERIFIER.md`, `docs/COMPLIANCE.md`, `docs/THREAT_MODEL.md`, `docs/ROADMAP.md`.

The **only actually implemented** issuer writes `TimestampValidationState.Unverified` and the offline ZIP checker also insists on `"Unverified"`. V001 intentionally allows numeric `validation_state` 0..4 for future evolutions. The domain `TimestampRecord.Validate()` verifies only local nonempty identity, UTC, retained DER and matching SHA256; **a self-consistent DER+SHA256 is not evidence of qualified status**. A migration owner, restore error or test fixture could theoretically inject an otherwise valid tenant-owned row with `VerifiedNonQualified`, `VerifiedQualifiedExternal`, `VerifiedQualifiedOwn` or `AffectedByIncident`. Registry Page/Search, direct DownloadReceipt and ExportZip currently validate DER/tenant but have no **read-side pilot status support gate**, risking unearned metadata/status claims in listing/search/manifest or silently delivering evidence whose state is not supported by a workflow. This is **hypothetical**; no production compromise, false qualification or legal incident is asserted.

## Decision — preserve raw historical data, refuse unsupported read responses

1. **ADR first committed on main before any tests or sources.** Commit xUnit **test-only** RED for each of the four non-pilot enum states against all four registry service boundaries: Page (1), SearchByDocumentSha256 with exact canonical 32-byte imprint (1), DownloadReceipt by owned ID (1), ExportZip with otherwise valid v1 receipt/manifest (1). **16 independent tests**. Every record is owned by the authenticated tenant, inside requested UTC range, contains original nonempty DER and matching SHA256; only enum state differs. Expect **generic `InvalidOperationException`**, no provider ID, tenant UUID, state name, personal imprint or DER. All pre-existing normal `Unverified` tests remain green, and newer #155 ZIP offline tests remain green. Require **actual GitHub Actions .NET backend RED** with precisely 16 missed-denial assertions and unrelated tests PASS, not fixture/compiler errors.
2. **Only after genuine RED** add a minimal private `RequirePilotUnverifiedState(TimestampRecord)` check to `TimestampRegistryService` after the existing `record.Validate()`, called both on `DownloadReceiptAsync` and from existing shared `ValidateReturnedRecords`. This protects Page, Search **including its lookahead**, and ExportZip *before* constructing/returning any manifest, bytes or match data; never relabel data automatically and never mutate a stored row. Preserve tenant/UTC/unique-ID/DER-hash/bounded ZIP and current issue-only `Unverified` behavior. The generic denial is an internal integrity failure, not a user-selected authorization claim or new public endpoint/status-code contract. A future genuinely verified or incident-affected status needs **separate independently approved verification/incident state machine and ADR/TDD** before relaxing this gate.
3. Update this ADR, registry operator and offline verifier runbooks, compliance, threat model and roadmap. Close **only #156** after independently verifying exact **documentation-inclusive main SHA** GitHub Actions 4 core jobs backend/frontend/terraform/docker-smoke SUCCESS, ci-verdict SUCCESS, combined `temporalmark/ci-4-core-jobs=success`, all new .NET Business cases, real PG17 **247/247**, 20 immutable V001–V020 migration checksums, TEST-only full `pg_dump/pg_restore` witness, Keycloak reviewer/registrar browser TOTP+PKCE and signed two-tenant HTTP 401/403, Nginx privacy 413/414/429, stdlib offline ZIP **29/29**.

## Strict security and legal limitations

A read-side fail-closed metadata check is **not** proof that the database is immutable, that all rows are present, that a DER/CMS timestamp has a valid trusted signer or historical EU Trusted List qualification, that `AffectedByIncident` is properly adjudicated, that external signed manifest/custody/WORM or QTSP/AgID status exists, or that Azure production controls are approved. It cannot stop a database owner from rewriting **both** DER and SHA256 while keeping the status `Unverified`. Counts/statistics currently have no status metadata and are not individually validated by this read-side gate. The existing SQL schema's future status values are **not removed**. #17/#15/#13/#61/#64/#38/#50/#18 all remain OPEN.
