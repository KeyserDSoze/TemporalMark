# ADR 0135 — Fail closed before persisting new pilot timestamp records that would be unreadable under registry budgets

**Status:** ACCEPTED for focused direct-main TDD [#177](https://github.com/KeyserDSoze/TemporalMark/issues/177), 2026-11-23 Europe/Rome. Related still-open parent #15 (delegated QTSP) and #17 (legal evidence preservation). This is a pilot persistence/read-compatibility rule, **not** eIDAS qualification, a new credential approval or proof of cryptographic trust.

**Facts:** [Microsoft .NET 10 `Encoding.GetByteCount`](https://learn.microsoft.com/en-us/dotnet/api/system.text.encoding.getbytecount?view=net-10.0) computes encoded bytes, not UTF-16 character length. [PostgreSQL17 `octet_length`](https://www.postgresql.org/docs/17/functions-string.html) computes the source text's database-encoding bytes. The API's pilot registry (ADRs 0127, 0132–0134) now rejects stored receipts with >1,048,576 retained DER bytes, any of four other nonnull `text` metadata fields >16,384 original UTF8 bytes, optional evidence reference >8,388,608 bytes, while batch reads also have separate aggregate limits. However, `TimestampIssueService.IssueAsync` currently hashes/validates and appends all provider results without applying those admission limits. Direct `PostgresTimestampWriter.AppendAsync` also invokes `TimestampRecord.Validate` before writing and never enforces those size budgets. An alternate/broken/compromised provider or internal writer caller can therefore insert a new row that its own authorized download and export must refuse. This is an *architectural self-incompatibility*, **not** a demonstrated real loss, a tenant bypass, or proof of bad RFC3161 signatures. A normal `ExternalRfc3161TimestampProvider` separately caps HTTP DER to 1MiB, but its interface can be implemented elsewhere.

## Decision (ADR first, RED first, exact-head GREEN)

1. **Keep existing pilot acceptance compatible with current registry reads:** on new `TimestampRecord` input, require **DER nonnull/nonempty and length <=1,048,576 raw bytes**, each nonnull `HashAlgorithmOid`, `DigestBase64`, `PolicyOid`, `ProviderId` original UTF8 **<=16,384 bytes inclusive**, optional `EvidenceReference` original UTF8 <=8,388,608 bytes inclusive; require `PolicyOid` and `ProviderId` nonempty/nonwhitespace for new records. Do not impose new ASCII/canonical OID format, pad aliases, provider qualification claims or 4KiB limit. Direct writer does not serialize a period, so no arbitrary 2MiB selected-batch aggregate policy applies at single-row append. The original read-side per-batch limits and separate JSON manifest output cap remain independent. A 16KiB provider ID and exactly 1MiB otherwise valid DER must still succeed.
2. **ADR then tests-only RED on `main`:** Business fake provider tests exercise over-16KiB provider and policy (including multibyte UTF8), original 1MiB+1 DER with otherwise SHA-consistent metadata, null/empty policy and a positive exact inclusive-size case. The denial must occur **after** exactly one provider request but **before** the fake writer is invoked, with existing fixed generic `TimestampProviderResponseException` -> HTTP **502**; no untrusted provider/tenant ID, digest or DER appears in error details. The normal canonical 44-char user SHA256 digest, exact forwarded 32-byte imprint, stored UTC and `Unverified` remain unchanged.
3. Real PostgreSQL17 tests invoke **`PostgresTimestampWriter.AppendAsync` directly** to ensure no bypass of Business. Over-budget provider/policy text, original DER 1MiB+1 with its correct SHA256, optional reference 8MiB+1 or empty mandatory policy must throw a fixed generic `InvalidOperationException` **before opening the SQL connection or attempting INSERT**. Verify no row was inserted, cross-tenant isolation remains, normal short/16KiB original provider ID and NULL optional reference are saved verbatim and remain readable under existing provider `FindByIdAsync`. All test rows are disposable and original, with `Unverified` status; no corruption of existing V001–V020 migrations.
4. Require independently observed genuine missing-admission failures in Business .NET and disposable PostgreSQL17 test-only GitHub Actions before touching implementation. If the backend's deliberate Business RED skips Docker, temporarily isolate only the additional failing Business test block on `main` to allow the independent PostgreSQL RED, **restore it verbatim before source changes**, track exact SHAs and real logs. A compiler/fixture error is not valid RED.
5. **AFTER genuine RED:** implement a reusable internal shared **`TimestampRegistryWriteBudget`** budget check in the Business layer (no network, no allocations of DER copies, no string serialization or hashing of out-of-budget DER). `TimestampIssueService` checks returned provider fields and DER bytes immediately **before** generating SHA256 and building/validating/appending a new record; return a fixed generic `TimestampProviderResponseException` (pre-existing 502, no issuance-created audit or record). `PostgresTimestampWriter.AppendAsync` runs the same read-compatible admission **before** `TimestampRecord.Validate()` and DB connection; invalid input raises a fixed sanitized `InvalidOperationException`. A valid `TimestampRecord` still gets the existing local SHA256 and `Unverified` rules; no new qualification state, reissue/retry or alternate endpoint.
6. Record TDD RED/GREEN, data-contract limits and operator implications in this ADR, docs registry operator guide, TSA HTTP transport guidance, threat model and roadmap. ## Alternatives and residual risks

- **Reject bad metadata only on reads:** permits successful `201 Created` for a record that cannot be fetched; contradicts the pilot's API acceptance promise. Prevent new bad appends proactively, retaining the existing independent read-side and DB-restoration guards.
- **Normalize or truncate upstream metadata:** destroys original source identity/policy provenance and changes the raw evidence manifest; fail closed instead.
- **Put every check only in Domain `Validate()` or only in the .NET API:** can force a large DER SHA256 before rejecting, and direct `PostgresTimestampWriter` callers may bypass the API. Use shared admission check at *both* actual trust boundaries.
- **Infer QTSP trust from policy length or DER hash:** a locally self-consistent token is not automatically valid RFC3161 CMS or a historically qualified QTSP service. Independent historical Trusted List, cert and signature validation, WORM, full-period exports and CAB/AgID remain separate release gates.
- **Global DB check/migration:** V001 historic rows and external operator scripts remain beyond this application-layer write admission. The existing read-side filters handle legacy/owner-inserted rows; the DB owner/backup/restore still needs approved controls. The append helper cannot prove successful WORM persistence, legal retention or exactly-once TSA billing.
