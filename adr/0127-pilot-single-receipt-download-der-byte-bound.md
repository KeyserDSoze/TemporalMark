The synchronous ZIP uses **1,048,576 bytes per original retained DER** to avoid building resource-heavy ZIPs from otherwise self-consistent legacy/corrupted database rows. The independent offline v1 verifier has the same 1MiB DER member budget. By contrast, `DownloadReceiptAsync` retrieves and returns an individually identified, tenant-owned `ResponseDer` of **arbitrary length**, as long as `TokenSha256Hex` equals the bytes and pilot verification state is `Unverified`. The API then marks the download `ReceiptDownloadPrepared` and responds with the full bytes. This inconsistency is a resource/interoperability safety gap, not evidence of an actual compromise or a legal requirement on RFC3161 receipt size. Postgres materialization already occurred before Business sees the row.

## Decision — test-first on main

1. Commit this ADR **before tests**. Commit only Business xUnit tests using a valid tenant-owned `Unverified` record with `ResponseDer = new byte[1_048_577]` and SHA-256 computed over those bytes. Verify it is valid under existing `TimestampRecord.Validate`, yet the **single receipt** must be denied with a generic `InvalidOperationException` and no DER return; also accept exactly **1MiB** and preserve bytes; an oversized *foreign-tenant* record must first fail the existing tenant-security guard, and a missing ID stays not-found. The tests intentionally do not name a new exception subtype yet, so **genuine RED** must reflect a missing denial, not source compilation. Confirm via backend CI logs on tests-only SHA.
2. **Only after real RED**, introduce `ReceiptTooLargeException : InvalidOperationException` with a constant, non-sensitive message and reject `record.ResponseDer.Length > ExportReceiptDerLimitBytes` in `DownloadReceiptAsync` **after the authorized tenant equality check, before SHA-256 hashing**. Reuse the 1MiB synchronous-export pilot bound; continue raw DER equality/validation for accepted receipts and `Unverified` state gate. Never truncate, recompress or silently relabel a record. The business method is shared OSS on-prem / Azure.
3. In `GET /api/v1/stamps/{id}/receipt` only, catch that specific subtype and return **409 Conflict**, with generic problem title and **`Cache-Control: no-store`**, rather than delivering bytes. Do **not** map the case to 413 because HTTP 413 refers to excessive **request** content; this is a server-stored receipt that cannot be served under pilot policy. Audit `ReceiptDownloadPrepared` remains **only after the successful bounded read**, so an oversized refusal does not create a misleading prepared-download event. Keep 404 for unknown or foreign-tenant IDs, 401/403 for unauthorized OIDC/SQL membership, existing audit-failure fail-close.
4. Enhance disposable real two-tenant signed-Keycloak/PG17 smoke to seed **one** oversized yet SHA-consistent `Unverified` A-tenant canary *after* existing counts/search tests, using a compact owner-only PostgreSQL `decode(repeat(...))` expression rather than emitting DER or credentials. Require owner A HTTP 409/no-store generic, owner B 404, and **no `ReceiptDownloadPrepared` audit record for rejected oversized ID**; do not persist ZIP/TSR artifacts. This is a pilot CI-only fixture, never an actual QTSP-issued token.
5. Update this ADR, registry runbook, threat model, roadmap, README. Close **only #169** if actual GitHub Actions on the **exact final docs-inclusive `main` SHA** has backend/frontend/terraform/docker-smoke 4/4 success, ci-verdict+combined success, new Business tests, Python offline/bridge, real PG17 247/247 and 20 migrations/restore, signed-Keycloak A/B HTTP 409/404, existing 401/403/ZIP/audit and proxy checks.

## Security/legal stop line

The 1MiB cap applies to **this pilot synchronous GET response**, not any legal RFC3161 size requirement or to all future qualified TSA integrations. It does **not** prevent pre-existing PostgreSQL `bytea` materialization before the business check, limit concurrent authorized download allocations, resolve pagination/search source-row byte budgets, provide indefinite lawful retention, WORM object lock, signed audit/manifest custody, signed RFC3161/CMS validation, historical EU Trusted List qualification, independent four-eyes issuance, CAB/AgID approval or complete arbitrary-period export. All records stay explicitly pilot `Unverified`; #17/#15/#13/#61/#64/#18/#38/#50 remain OPEN.
