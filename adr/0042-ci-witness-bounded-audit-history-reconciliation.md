# ADR 0042 — Reconcile bounded CI witness append audit under the same read-only snapshot

Status: **accepted for test-only, non-authorizing PostgreSQL witness audit hardening**, 2026-11-16. Scoped [#73](https://github.com/KeyserDSoze/TemporalMark/issues/73) is child of still-open [#64](https://github.com/KeyserDSoze/TemporalMark/issues/64) / [#61](https://github.com/KeyserDSoze/TemporalMark/issues/61). Reviewed ADR 0032–0041, V017, `docs/MDS_CRL_SEPARATE_POSTGRES_WITNESS_TEST.md`, `docs/MDS_CRL_THREE_SOURCE_ROLLBACK_TEST.md`, existing `witness-ci` SQL, the actual full logical PostgreSQL restore fixture and .NET 10 two-/three-source preflights. References: [PostgreSQL 17 SECURITY DEFINER + STABLE](https://www.postgresql.org/docs/17/sql-createfunction.html), [role privileges](https://www.postgresql.org/docs/17/ddl-priv.html), [repeatable-read snapshots](https://www.postgresql.org/docs/17/transaction-iso.html).

## Problem

The separate CI witness service already appends to `unapproved_witness_events` in the same SQL transaction as its latest checkpoint UPSERT, but the read-only reconciler queries only `unapproved_witness_checkpoints`. A superuser/owner can downgrade the checkpoint from serial 4 to serial 3 **while leaving audit history at 4**. The existing two-source preflight accepts a correctly signed restored primary at 3 together with that downgraded witness row as `UNAPPROVED` even though its *own still-present events* prove that 4 existed. This is detectably inconsistent, independently of the ordinary signed file journal added under #72. The event table is currently intentionally not accessible via raw `SELECT` to the witness reader.

## Decision

1. In **only** the disposable `tests/integration/mds-witness-postgres-init/001-unapproved-witness.sql` initial transaction, create `public.check_unapproved_witness_history(text,bigint,text)` as **STABLE SECURITY DEFINER**, with fixed `SET search_path=pg_catalog,pg_temp`, fully qualified `public.` object names, no dynamic SQL or data mutation. It must be owned by the existing `temporalmark_witness_data_owner` (NOLOGIN/NOSUPERUSER) and `REVOKE ALL ... FROM PUBLIC` **within its creation transaction**, granting **EXECUTE only to `temporalmark_witness_reader`**. Writer may execute only `record_unapproved_highwater_witness`, cannot execute the audit checker or read either table. Reader retains only SELECT on latest-checkpoint table and cannot directly SELECT events, tables or their owned identity sequence.
2. The audit checker reads at most **129** source-scoped append events in `event_id` order (reject count `>128`), denies empty, negative/malformed serial/hashes, non-increasing serial, decreasing event observation time, and any latest event with serial/hash inconsistent with claimed checkpoint. No allowance for equal-serial equivocation. Missing, invalid/null requested policy, expected version or digest fails closed. The checker must also confirm the actual checkpoint row still matches the supplied serial/hash, with the `STABLE` function observing the same transaction snapshot.
3. The .NET `ReviewerMdsIsolatedPostgresWitnessReader.ReconcileAsync` continues using **READ ONLY REPEATABLE READ** on the separate PostgreSQL server; it verifies the checker is physically owned by the same NOLOGIN `temporalmark_witness_data_owner`, is `SECURITY DEFINER`, `STABLE`, and that the reader alone has EXECUTE (no PUBLIC grant, no writer access; not a caller-provided authority). After reading latest checkpoint but **before** returning the snapshot, call checker with the same derived untrusted policy, latest serial and seal SHA. Deny a false/missing/error result; never grant direct audit SELECT or fall back to a caller's latest SHA. All original signed source-manifest/seal and owner-only V017 snapshot checks remain unchanged; result is **only `UNAPPROVED/SEPARATE_TEST_POSTGRES_WITNESS_NO_IMMUTABLE_CUSTODY`**.
4. TDD: commit this ADR before code and RED real full restore regression against the existing reader: old fully restored primary 3 + witness checkpoint downgraded by superuser to 3 **must deny** if event 4 remains. Show actual fail on current implementation. GREEN SQL bootstrap, reader checks, adversarial event tamper/removal tests and necessary update of #72's deliberately documented residual replay test. To simulate a successful *total* witness-store replay, the privileged owner must ALSO delete/replay the latest event tail; after rewriting the ordinary file journal to signed old bytes, the three-source preflight may still return **only UNAPPROVED** for the consistent old state, explicitly proving lack of immutable custody. Restore disposable audit state in `finally`.
5. Never upgrade source-policy SHA, FIDO MDS/CRL contents, owner-supplied test public key or alleged latest time into independent trust. PostgreSQL superuser/root/backup host can rewrite event table, replace SQL function or restore both DB + journal, so this is **only an internal consistency check**, not an independent event attestation or append-only WORM audit. SQL functions do not supply HSM/CAB governance, atomic cross-store consensus, PITR/region split-brain proof, or certified evidence. Keep #64/#61/#57/#55/#53/#44/#50/#46/#38 OPEN, V015/V016 registrar issuance freeze intact. No V018, no production API/CLI/registrar grant and no mandatory Azure service. All four CI jobs must be GREEN on exact final `main` SHA before closing **only #73**.

## Residual limitations

An authenticated witness SQL reader is not an independently governed witness *operator*. The bounded history could be truncated by a witness superuser along with its latest row, then replayed as a fully consistent old state; `STABLE` and `SECURITY DEFINER` protect ordinary login paths only, not superusers/host root. This adds no FIDO Alliance R46/JWS/x5c signing-chain revocation verification, physical immutable custody or eIDAS/WORM/QTSP qualification. Separately administered append-only signed provenance, key bootstrap/rotation, legally approved runbooks, offsite operational isolation and equal on-prem open-source/Azure production deployments remain required to address #64.
