# ADR 0060 — Operator-approved RFC3161 policy OID in both request and signed timestamp response

Status: Accepted for limited delegated-pilot TSA policy binding (2026-11-16). Child [#91](https://github.com/KeyserDSoze/TemporalMark/issues/91) of still-open [#15](https://github.com/KeyserDSoze/TemporalMark/issues/15). **An OID match does not make a mark qualified.**

## Reviewed context and authoritative protocol

Reviewed ADR [0002](0002-qualified-vs-delegated-timestamping.md), [0052](0052-external-tsa-http-no-redirect-policy.md)–[0059](0059-rfc3161-operator-approved-signer-certificate-sha256.md), [operator guide](../docs/TSA_HTTP_TRANSPORT.md), [threat model](../docs/THREAT_MODEL.md), [roadmap](../docs/ROADMAP.md), actual `ExternalRfc3161TimestampProvider`, API `Program.cs` and endpoint/redirect/response tests. Existing request includes SHA-256 imprint, nonce, certReq; #89 restricts the CMS signer to one critical timeStamping EKU, and #90 demands a pinned SHA-256 DER signer certificate. But the request leaves `reqPolicy` unspecified and the response merely persists `token.TokenInfo.PolicyId`. One pinned TSA signer can potentially sign stamps under **multiple service/product policies**. Software must not infer that any stamped OID indicates qualified status.

[RFC 3161 §2.4.2](https://www.rfc-editor.org/rfc/rfc3161#section-2.4.2) requires the TSTInfo.policy to identify the service policy and, if a TimeStampReq.reqPolicy was supplied, to **match that request exactly**. [.NET 10 Rfc3161TimestampRequest.CreateFromHash](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.pkcs.rfc3161timestamprequest.createfromhash?view=net-10.0) supports `requestedPolicyId`; [Rfc3161TimestampTokenInfo.PolicyId](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.pkcs.rfc3161timestamptokeninfo.policyid?view=net-10.0) exposes the signed OID.

## Decision

1. Add mandatory **server-controlled** `TimestampProvider:PolicyOid` alongside the already required `TimestampProvider:SignerCertificateSha256`, only when external TSA `TimestampProvider:Url` is configured. No tenant-supplied value and no automatic OID discovery/TOFU. The API passes the exact string into the provider. A missing/blank/ambiguous or incorrectly encoded policy fails with `TimestampProviderUnavailableException` **before preparing/sending any HTTP request**. An unconfigured TSA remains disabled without policy. This applies to both Azure and on-prem deployments.
2. Accept only **canonical dotted-decimal numeric OIDs** with at least two arcs; first arc 0, 1 or 2; second 0–39 for first arc 0/1; no leading zeros except the single digit `0`, no plus/minus sign, whitespace, Unicode digits, empty arcs, suffix/prefix/doubled dots or overflow. Limit length and number of arcs to guard costly parser input; reject malformed strings generically without reflecting config. Use ASCII parsing, never `Oid.FriendlyName` (locale-dependent). Full certificate/service policy approval remains manual and must be documented by an operator.
3. Create the actual `Rfc3161TimestampRequest.CreateFromHash` with `requestedPolicyId: new Oid(approvedPolicy)` plus existing 16-byte random nonce, SHA-256 digest and `certReq:true`. After `ProcessResponse`, byte-consumption, nonce/imprint, signed CMS, #89 critical-only EKU and #90 verified signer fingerprint, require `token.TokenInfo.PolicyId.Value` to **equal** the approved policy OID exactly before constructing `ProviderTimestamp`. The `ProcessResponse` implementation may itself enforce policy matching; the explicit check provides a future-resistant application invariant. No fallback to token issuer-selected policy.
4. TDD: commit ADR first on `main`, then RED-first tests for all invalid/valid OIDs, no HTTP pre-send on missing/invalid policy, real captured and decoded RFC3161 TimeStampReq with correct `RequestedPolicyId` and nonce/imprint/certReq. Observe GitHub RED. Implement source, maintain old endpoint/MIME/redirect tests by supplying a syntactically valid dummy policy OID, update docs/threat/roadmap, verify four-job CI success on exact final `main` SHA, and close only child #91.

## Operational, legal and threat limitations

The matched policy OID is *a claim within a cryptographically signed and pinned-signer token*. This check prevents silent acceptance of a token issued under a different OID; it **cannot** establish that a given OID was actually approved as **qualified** under eIDAS, or that the provider met QTSP rules on that date. The operator must independently authenticate the intended TSA service and its published policy, verify that OID is appropriate, and maintain auditable change control. No development OID or test issuer is declared legally valid. Different policies sharing one TSA leaf require explicit deployment change and require their own validation. External QTSP chain/path trust, revocation at signing time, historical EU Trusted List status and qualification, algorithms/time service, WORM preservation (#17) and CAB/AgID controls (#13) remain open in parent #15. Persisted status remains `Unverified`.
