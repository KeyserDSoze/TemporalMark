# ADR 0080 — Tenant-admin registry page navigation and stale-response-safe browser state

Status: Accepted for **pilot admin consultation only**, 2026-11-18. Focused [#111](https://github.com/KeyserDSoze/TemporalMark/issues/111) under open [#14](https://github.com/KeyserDSoze/TemporalMark/issues/14).

## Baseline reviewed

Reviewed ADR [0006](0006-tenant-bootstrap-and-admin-integrity.md) and [0079](0079-tenant-utc-daily-dashboard-counts.md), `TimestampRegistryService.PageAsync`, `ITimestampRegistry.PageAsync`, PostgreSQL `PostgresTimestampRegistry.ReadAsync`, and `Program.cs` authenticated `GET /api/v1/stamps` / `TenantAdminAsync` route, `src/frontend/src/Dashboard.tsx`, IT/EN strings, `tests/frontend/authenticated.spec.ts`, real signed-Keycloak two-tenant `api-tenant-isolation.py` and `docs/CI_API_TENANT_HTTP_ISOLATION.md`, `docs/ROADMAP.md` and THREAT_MODEL. The existing REST backend already accepts `offset` >= 0 and `limit` 1..200, performs parameterized SQL tenant filtering, and orders by `issued_utc,id`. The UI currently requests the first 50 records and shows `50 / total` without any navigation; this blocks retrieval of later entries via the portal. The page is merely a **view of a moving PostgreSQL table**; no immutable snapshot or legal completeness guarantee exists.

## Decision

1. Add user-visible **Previous/Next** actions to the existing registry card, 50 records/page. Use server-owned period (current UTC filters), existing signed-token-selected tenant, and requests `GET /api/v1/stamps?...&offset=N&limit=50`. The UI must never add caller-selected organization IDs. Show the exact displayed range `start–end of count` based on validated summary count and actual received rows; disable Next when reached total (or current page has fewer than 50 rows), disable Previous on first page. Retain per-record raw TSR download and 10,000-row synchronous export as separate actions.
2. Reset offset to 0 when a date filter or current access token changes. Frontend requests for old pages may finish after a new date/token request and must not override the latest view: use a monotonically advancing per-component **request generation** to commit the complete summary/list/daily/audit batch atomically only when most recent. React cleanup invalidates obsolete requests; asynchronous result strings and raw token bytes are never logged.
3. Explicitly mask any previously fetched tenant, registry, daily series, audit and count while the current `accessToken` differs from the token used for the most recent successful result. This is a **visual residual-data guard** complementary to—never a substitute for—server-side signed OIDC and SQL membership checks. No client ID or caller-controlled org selector can change tenant context. Failed loads must not keep an old successful page in view under another session.
4. TDD: commit ADR before tests. Add a signed-Keycloak authenticated browser regression using **test-only route mocks for list and summary after genuine signed login** to show 51 synthetic rows on page 1/page 2; ensure the real existing tenant/export/OIDC scenario executes unmocked first. Add real two-tenant signed-Keycloak PostgreSQL API `offset=1`, invalid `offset=-1`, `limit=201` and spoofing tests (same existing 1-row canaries, never a production DB). Implement React state/controls and IT/EN translations, update operator/security/roadmap, inspect real CI. Close only after exact final documentation-inclusive `main` four-core successful GitHub Actions and test logs.
5. **No** SQL schema changes, new packages, RLS bypass, qualified timestamp claim, WORM/signed export manifest, or admin provisioning permission. The same API and client work on OSS on-prem and Azure. No global cross-page uniqueness or point-in-time snapshot is implied: inserts/deletes during offset navigation can cause repeated or skipped rows; #17 must deliver independently signed high-water/evidence coverage and authenticated streaming export.

## Security/operational residuals

A backend compromise or database owner can forge or omit registry entries. A reused access token could be revoked mid-flight; the existing server rechecks validated JWT and active membership per HTTP request, but frontend generation checks are not independent IdP account liveness. No identity assurance, WebAuthn registrar V015/V016 unblock, legal QTSP qualification, CAB/AgID certification, UTC(k) or signed WORM custody is delivered. Parent #14/#17/#20/#13 remain OPEN; pilot receipts remain `Unverified`.
