# ADR 0035 — Real PostgreSQL full logical pg_dump/pg_restore regression against a test-only signed latest seal

Status: **accepted as a non-authorizing CI regression only** — 2026-11-16. Focused [#66](https://github.com/KeyserDSoze/TemporalMark/issues/66) child of still-open #64/#61/#57, following ADR 0032–0034 and source `docs/MDS_CRL_SEALED_HIGH_WATER_COPY_RESTORE.md`. Reviewed immutable V017, current GitHub Docker CI and official [PostgreSQL 17 pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html) and [pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html).

## Problem and important limits

#65's real `COPY TO/FROM` test proves a **scoped table-data rollback**. It is *not* a full logical database dump/restore. This ADR advances the integration evidence to the entire TemporalMark PostgreSQL database restored from a **pg_dump custom-format archive** into a NEW, uniquely named disposable database on the **same PostgreSQL 17 test server**, using `pg_restore --single-transaction --no-owner --no-acl --exit-on-error`. The original database must remain untouched except for one synthetic V017 candidate scope. SQL migration checksum history, triggers and schema must be verified on the restored copy. No development credentials, backups, production signer or ephemeral private signing keys are checked in.

A logical `pg_dump/pg_restore` on the same server **does not simulate physical volume loss, PITR, WAL timeline forks, cross-region split brain, a different PostgreSQL cluster, encrypted offsite immutable backup, independent identity provider continuity, or a proof of operational disaster recovery readiness**. The latest seal hash and test verification keys are held in temporary **CI process memory**, not by an independent security operator/immutable authority. Old DB + old correctly signed seal + **replaced old latest pin** can still pass as `UNAPPROVED`. Consequently #64/#61 stay OPEN.

## Decision

1. Add a CI-mandatory integration script in `tests/integration/` that stages a fresh `MDS_BLOB` candidate using existing owner-only V017 with synthetic uppercase SHA256 data; dumps the **complete** TemporalMark test database at serial 3 through `pg_dump -Fc` into a runner-private temporary file; then advances the live row to serial 4 and creates a separate uniquely named disposable database. Restore the older full archive via `pg_restore` with atomic transaction and explicit abort on any error. Validate schema_migrations=17, restored candidate serial=3, primary serial=4, and ensure the V015/V016 registrar interlock is still present on the restored copy. Always clean up the test database and archive using a trap even on failure; do not log database passwords or publish the archive. All DB DDL/test data are on ephemeral CI-only Docker stack.
2. In the *same* CI step, run a dedicated .NET 10 xUnit method using `TEMPORALMARK_RESTORE_TEST_DB` plus `TEMPORALMARK_TEST_DB`, exact test scope, serials/digests. It creates **two independent disposable RSA-PSS key pairs** and actual old/new signed witness and seal bytes, retains only latest test SHA and authority SPKI pin in the test process outside either database. Reuse the existing sealed-high-water verifier + PostgreSQL `READ ONLY REPEATABLE READ` code (ADR 0033/0034), do not reimplement signature validation. Must return only `UNAPPROVED` for matching live serial; deny new manifest against the restored serial, and old correctly signed pair with retained newest seal hash; explicitly show the unresolved attack where malicious caller substitutes the old latest hash and gets only an `UNAPPROVED` observation. Also deny same-serial digest tampering and check restored schema/migration history.
3. The test suite must fail **RED before** the runner/fixture is added. Then green, with a separate mandatory Docker CI step immediately after existing PostgreSQL unit tests. The harness remains test-only; no new migration, SQL grant, API, CLI, private key distribution, installed runtime dependency, cloud service, production root or attestation authorization.
4. Work directly on `main`; document full-run evidence and exact final SHA. Close **only #66** when backend, frontend, Terraform and docker-smoke on the **exact final head** all pass. Keep #64 open for **real independent monotonic externally protected latest seal**, CAB-pinned key bootstrapping and rotation, full cluster backup/PITR, corrupt backup, replica split-brain, signed source provenance, trusted time and on-prem/Azure DR parity. Parent #61/#57/#55/#53/#44/#50/#46/#38 remain open, and V015/V016 registrar SQL issuance frozen; no eIDAS/WORM/QTSP claim.

## Operational privacy and safety

Test-only hashes and disposable keys, never production JWTs, real CRLs, manufacturer identifiers or private key material in the archive. The restored database exists only in disposable Docker CI under a unique test name; cleanup is mandatory. A real restore of live multitenant user data would require legally defined retention controls, data protection assessment and CAB authorization, **not provided here**.
