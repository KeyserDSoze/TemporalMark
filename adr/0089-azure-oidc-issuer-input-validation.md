# ADR 0089 — Strict HTTPS OIDC issuer syntax at Azure plan time

Status: **Accepted for scoped pilot #122 only**, 2026-11-20. Parent [#18](https://github.com/KeyserDSoze/TemporalMark/issues/18), identity [#25](https://github.com/KeyserDSoze/TemporalMark/issues/25) and privacy [#115](https://github.com/KeyserDSoze/TemporalMark/issues/115) remain OPEN.

## Context and authoritative requirements

Reviewed [ADR 0001](0001-architecture-and-deployments.md), [ADR 0087](0087-azure-image-oci-sha256-digest-admission.md), [ADR 0088](0088-disposable-mfa-loopback-callback-fallback.md), `infra/azure/main.tf`, `variables.tf`, `terraform.tfvars.example`, existing mocked `tests/image_pins.tftest.hcl`, `infra/azure/README.md`, `docs/THREAT_MODEL.md` and four-core GitHub CI. The API Container App passes `var.oidc_authority` into `Authentication__Authority`, while the frontend image embeds its own separately compiled `VITE_OIDC_AUTHORITY`. Terraform currently validates only `startswith("https://")`. This admits `https://` without a hostname, `https://localhost`, loopback IPv4, query strings/fragment, userinfo, and nonsensical issuer paths. Such invalid input can break authentication or produce unsafe operator assumptions, while the documented real IdP issuer validation still requires a properly managed issuer with trusted JWT keys.

[OpenID Connect Discovery 1.0 (final, incorporating errata)](https://openid.net/specs/openid-connect-discovery-1_0.html) specifies an issuer with HTTPS scheme, host, optional port/path, **no query or fragment**, and a metadata `issuer` string that must exactly match the configured issuer. [Terraform variable validation](https://developer.hashicorp.com/terraform/language/block/variable) rejects invalid inputs during plan; [Terraform mock-provider tests](https://developer.hashicorp.com/terraform/language/tests/mocking) permit offline positive/negative plan tests. This is **syntax validation only**, not a discovered or verified IdP trust anchor.

## Decision

1. Replace the Azure input's `startswith("https://")` guard with a **strict, anchored Terraform regular expression** that admits HTTPS, a DNS-style, lower-case FQDN with at least two labels and an alphabetic final label, optional numeric port and optional nonempty path segments (e.g. `https://login.microsoftonline.com/<tenant>/v2.0` and `https://id.example.org/realms/team`). Do not embed a vendor/tenant-specific hostname in the Terraform template. Reject `http://`, incomplete/localhost/numeric-IP authorities, URL userinfo or credentials, query, fragment, whitespace, empty path segments, `.`/`..` path segments and trailing slash. This deliberately restrictive reference-template policy may exclude some valid but nonstandard OIDC issuers (IDN, IPv6 literals, percent-encoded paths, internal single-label hosts); such deploys require an independent ADR and change-controlled review, **never** a broadening to `startswith` again. Hostname format alone does not establish public reachability or a known issuer.
2. Before editing production validation, add real **mocked Terraform `command=plan` tests** with valid Keycloak, Entra issuer and port+path examples, and `expect_failures=[var.oidc_authority]` for each invalid example. Wire them into the Terraform core CI job after `init`/`validate`. Use imaginary `registry.example.invalid` OCI digest image refs and fake credentials; **no Azure requests, infrastructure changes, user data or real identity secrets**. Independently observe RED before implementation and GREEN after.
3. Update operator docs with approved out-of-band issuer inventory, exact metadata `issuer`, discovery TLS/JWKS audit, minted JWT audience/acr/current account state and PWA build-time OIDC authority alignment as production gates **outside Terraform plan tests**. Do not relax `TokenValidationParameters`, registration/MFA, tenant claims or signed Keycloak checks. The on-prem OSS deployment remains independent of Azure. No database migrations or WebAuthn changes.
4. Keep verified signed OCI digest-only inputs from #120, dual app pattern and existing Terraform state-secrets caveat unchanged. No claims of protection against DNS rebind, provider compromise, TLS trust chain or identity rollout errors; only input-format hardening for Azure reference deployments.
