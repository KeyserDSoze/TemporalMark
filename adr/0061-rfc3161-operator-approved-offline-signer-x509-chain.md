# ADR 0061 — Operator-approved offline X.509 root path for the verified RFC 3161 signer

Status: Accepted for **pilot PKIX path defense-in-depth only** (2026-11-16). Focused child [#92](https://github.com/KeyserDSoze/TemporalMark/issues/92) of open [#15](https://github.com/KeyserDSoze/TemporalMark/issues/15). **This is NOT an assertion of historical revocation, qualified QTSP status or eIDAS legal validity.**

## Context and reviewed material

Reviewed ADR [0002](0002-qualified-vs-delegated-timestamping.md), [0052–0060](0060-rfc3161-operator-approved-request-and-signed-token-policy.md), [TSA operator guide](../docs/TSA_HTTP_TRANSPORT.md), [threat model](../docs/THREAT_MODEL.md), [roadmap](../docs/ROADMAP.md), `ExternalRfc3161TimestampProvider`, API factory/config and current signer EKU, SHA-256 leaf pin, policy OID and HTTP tests. #89 validates the CMS signer has the critical sole timeStamping EKU; #90 matches its whole DER leaf SHA-256 to operator-approved identity; #91 matches a server-approved reqPolicy to signed TSTInfo.policy. **None independently builds or checks an X.509 trust path.** Pinning a mistakenly approved malicious/self-signed leaf is not PKIX trust.

.NET 10 supports [X509ChainPolicy.CustomTrustStore/TrustMode](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.x509certificates.x509chainpolicy?view=net-10.0) to **replace system roots**, `DisableCertificateDownloads` to block automatic AIA issuer retrieval, and `ExtraStore` for explicit intermediates. [Rfc3161TimestampToken.AsSignedCms](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.pkcs.rfc3161timestamptoken.assignedcms?view=net-10.0) exposes the **actual token's embedded certificate collection**. Checking the TLS server chain or merely SHA-256 pinning the leaf is not a substitution.

## Decision

1. A configured delegated TSA requires an explicit operator-controlled `TimestampProvider:TrustAnchorCertificateBase64Der`: **canonical standard Base64 of exactly one DER X.509 CA root certificate** (no PEM envelope, whitespace, multiple certificates, URL, certificate store name or private key). Reject missing, noncanonical/malformed/oversized (>64 KiB DER), syntactically incomplete, non-self-issued, non-CA, missing `KeyCertSign` key usage root. Only the API's trusted configuration supplies the value; no tenant field or silent system-root fallback. Parse and validate it **before RFC3161 request generation / HTTP POST**. The no-URL disabled provider requires neither anchor nor signer identity.
2. After existing RFC3161 response/DER, signature, imprint/nonce, **verified** CMS signer critical EKU (#89), leaf SHA-256 identity (#90) and signed policy (#91), run `X509Chain.Build` on that very signer, with a **fresh** `X509Chain` whose `ChainPolicy` is: `TrustMode=CustomRootTrust`; `CustomTrustStore` contains only the reviewed root; `ExtraStore` contains only **certificates embedded in that signed CMS**; `DisableCertificateDownloads=true`; `VerificationFlags=NoFlag`; `VerificationTime=DateTime.UtcNow`; and **`RevocationMode=NoCheck` explicitly**. Reject false `Build` / partial/untrusted path or non-root-terminated chain with generic `TimestampProviderResponseException`; never log certificate metadata or trust-anchor values.
3. This is a **current-time path/chain sanity and operator-selected anchoring** control, **not evidence that any certificate or the QTSP service was valid or not revoked at the historic TSTInfo.genTime**. We intentionally avoid network CRL/AIA/OCSP auto-fetch, which could introduce SSRF and nondeterministic validation, and do not claim to have performed certificate revocation. Signing-time revocation proof and historical EU Trusted List status require separately authenticated, preserved and auditable evidence before qualification. A compromised operator-selected root could still authorize attacker-issued leaves; trust anchor acquisition and rotation require out-of-band verification and approval.
4. Both on-prem and Azure supply the same environment setting `TimestampProvider__TrustAnchorCertificateBase64Der` or secured configuration value. Operators must independently review/pin a root *certificate*, not a leaf, TLS server cert or arbitrary intermediate; reissuing/rotating a root is a privileged deployment change. The new validation is not a network service dependency. No change to general HTTPS clients, no auto trust-on-first-use, no quiet downgrade on missing data. Existing receipts remain `Unverified`.
5. TDD: ADR first on `main`, then RED-first tests generating disposable root/intermediate/leaf certificates, pre-send no-network tests, missing/incorrect root chain tests, expired/invalid signer and offline policy invariants; observe GitHub Actions RED; implement validator/provider/API plus adapt legacy tests with a syntactically valid disposable root fixture; update docs; close #92 only after all four final SHA CI jobs GREEN. #15/#17/#13 remain open.

## Operational limits and forward actions

- No CAB/AgID qualification, signer revocation at issuance, CRL/OCSP, historical EU Trusted Lists, TSU UTC(k)/HSM evidence, algorithm agility assessment, legal signed evidence WORM or independent QTSP identity is supplied here. Do not label any output qualified on this basis.
- Timestamp policy OID (#91), leaf pin (#90), EKU (#89) and offline certificate path (#92) are **necessary defense-in-depth checks, not sufficient for eIDAS qualification**. Keep #15 and #17/#13 open.
- [Microsoft X509ChainPolicy](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.x509certificates.x509chainpolicy?view=net-10.0), [CustomRootTrust](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.x509certificates.x509chaintrustmode?view=net-10.0), [AsSignedCms](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.pkcs.rfc3161timestamptoken.assignedcms?view=net-10.0).
