# ADR 0048 — Commit real NuGet package graphs and require locked restores in .NET CI/Docker

Status: **accepted for source dependency resolution reproducibility only** (2026-11-16), scoped child [#79](https://github.com/KeyserDSoze/TemporalMark/issues/79) of open [#20](https://github.com/KeyserDSoze/TemporalMark/issues/20).

## Context, prior decisions and sources

Reviewed ADR 0001 and ADR 0043–0047, `docs/ROADMAP.md`, `docs/THREAT_MODEL.md`, `docs/CI_NUGET_CYCLONEDX_SBOM.md`, `docs/CI_NPM_CYCLONEDX_SBOM.md`, nine `.csproj` under `src/backend` and `tests/backend`, .NET SDK Dockerfile and all GitHub Actions CI jobs. #78 exports *restored* NuGet CycloneDX 1.5 from nine temporary `obj/project.assets.json` graphs, but none of the project inputs records the resolved transitive package graph under version control. `setup-dotnet: 10.0.x`, pinned Docker SDK image content and the transient NuGet feed may change the restore result; this creates a mismatch between a source SHA and the versions tested/packaged.

Official authoritative source: [Microsoft NuGet PackageReference: locking dependencies](https://learn.microsoft.com/en-us/nuget/consume-packages/package-references-in-project-files#locking-dependencies). Microsoft documents `dotnet restore --use-lock-file` for creating `packages.lock.json` and `dotnet restore --locked-mode` for fail-closed verification, noting that library lock files do not govern the graph of a consuming project and SDK-injected dependencies may differ by SDK patch. [NuGet warning NU1512](https://learn.microsoft.com/en-us/nuget/reference/errors-and-warnings/nu1512) explains why force-evaluate must not accompany locked-mode.

## Decision and implementation sequence

1. **TDD and provenance:** commit this ADR before changing tests. Introduce `tests/integration/check_nuget_lockfiles.py` and offline unit regressions, run in backend CI immediately after other source policy tests. The repository policy requires one committed `packages.lock.json` for **each of the nine** .NET 10 projects, exact project discovery, a versioned dependency tree including all direct PackageReferences, real SRI-equivalent SHA-512 contentHash for NuGet package entries, fixed resolved versions and project references handled honestly. It also requires the backend CI to perform explicit `dotnet restore --locked-mode` on all nine **before** tests/publishing, and requires locked-mode app Docker publish. First prove a real failing repository source guard on `main` when all nine lockfiles and locked-mode CI steps are absent, while unit regressions pass.
2. **Registry-derived locks:** use a temporary independent GitHub Actions runner with the same .NET 10 SDK selection and a controlled `dotnet restore --use-lock-file` for every project to generate **actual** NuGet source lockfiles. Extract *only* public package name/version/hash lockfile JSON, delimited in CI logs as base64; do not print NuGet package feeds, API keys, environment or `obj/project.assets.json`. Parse, validate all nine against the corresponding `.csproj` files and commit the exact generated bytes directly on `main`; **remove** temporary CI seed and log emissions immediately afterward. Never invent hashes, and stop/record a blocker if any package graph cannot be resolved.
3. **Locked GREEN:** in the backend job restore all nine projects with `dotnet restore "$project" --locked-mode` **before** tests/publish; run existing `dotnet test`/`dotnet publish` with `--no-restore` to avoid mutable implicit graph updates. For the pinned `mcr.microsoft.com/dotnet/sdk:10.0` builder run `dotnet publish -p:RestoreLockedMode=true` (the Dockerfile copies the entire backend tree, including nine `packages.lock.json` files). In the independent PostgreSQL smoke runner use `-p:RestoreLockedMode=true` or an explicit locked restore where tests need it. NuGet lockfile activation is automatic when committed files exist; no need to introduce shared `Directory.Build.props` with unintended production changes. Never combine force-evaluate and locked-mode.
4. **Validation and CI closure:** regression-test manifest drift, invalid and truncated SHA-512, missing/extra lockfiles, wrong version/framework and source CI fallback to mutable restore. Update `docs/ROADMAP.md`, `docs/THREAT_MODEL.md` and a runbook including source provenance; verify all four GitHub Actions jobs and real PostgreSQL full logical restore/witness, Keycloak MFA and PWA on **exact final `main` HEAD** before closing only child #79. Parent #20 remains open.

## Security limitations

NuGet lockfiles bind package *resolution* for a given target/SDK and package sources; they do not prove that packages are safe, publisher-identified or signed, nor ensure bit-for-bit binaries across architectures. The lockfile of a domain/infrastructure **library** is informational for that library's standalone build and does not override a consuming app's own lockfile; hence we also lock **both entry-point applications and all four tests**, with their own transitive closures. NuGet versioned lockfiles can vary with SDK patch, target/RID selection, NuGet pruning and implicit dependencies; perform future updates through separately reviewed versioned commits and test both GitHub Ubuntu runner and Docker SDK selection. Do not silently rewrite a lockfile in CI.

This change does **not** create a publisher-signature root, SCA/SAST/secret scan, complete OCI+OS SBOM, SLSA/attested release, on-prem/Azure production assurance, immutable evidence, CAB/HSM, authentic FIDO MDS root or eIDAS/QTSP qualified timestamp status. #20, #64/#61/#57/#17 remain OPEN; the V015/V016 registrar/reviewer authorization freeze is unchanged.
