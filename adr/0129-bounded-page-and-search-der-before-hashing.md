Existing synchronous ZIP export has **one DER <= 1,048,576 B**, **all source DER <= 67,108,864 B**, checked **before** any SHA256; single GET receipt has per-DER <=1MiB with tenant/ID priority. However, `PageAsync` and `SearchByDocumentSha256Async` load retained `ResponseDer` even though the HTTP API returns **metadata JSON**, and the shared `ValidateReturnedRecords` calls `TimestampRecord.Validate()` to hash every received DER **without** these operational byte budgets. A valid-checksum oversized legacy row can therefore make a page or imprint search serve metadata which synchronous ZIP/receipt refuse, and a page of 200 valid 1MiB receipts can exceed 64MiB hash work in a single request. The real PostgreSQL repository already returns arrays with full `bytea` materialized: this proposed guard does **not** prevent that allocation. It is not cryptographic RFC3161 validity or evidence of real attack.

Both `PageAsync` 1..200 and search 1..50+lookahead retain their existing count/order protections. Check real GitHub Actions backend RED with exactly the new **missing denial failures**, not compilation/fixture errors; positives must pass.
2. **Only after observed RED**, add a two-pass guard before the existing per-record `Validate()` in `ValidateReturnedRecords`: first verify **ALL** returned rows' `OrganizationId` and half-open requested UTC period, rejecting with the prior constant tenant/period message; second sum `ResponseDer.Length` of **ALL** rows in checked long/subtraction (avoid overflow), rejecting any individual receipt > `ExportReceiptDerLimitBytes` and total > `ExportTotalDerLimitBytes` with **one generic constant `InvalidOperationException`** that contains no tenant, hash, provider, size or record ID; third run existing SHA256, `Unverified`, UUID uniqueness, plus caller's ordering and exact document-imprint checks. ## Residual concerns / strict regulatory nonclaims

This is a **post-repository-materialization** application limit: one tenant admin can still cause the Npgsql/Postgres materialization of many large legacy bytea rows **before** the guard. It does not prove bounded concurrent memory, SQL query byte limits, long-term complete period export, stable multi-page snapshots, independent WORM/legal hold, signed receipt/manifest, independent audit custody, true RFC3161 DER/CMS issuer verification, historical QTSP qualification on EUTL, regulated UTC(k) time source or CAB/AgID certification. The 1MiB/64MiB settings are conservative **pilot operational** budgets, not RFC3161 size constraints or a regulated retention mandate. Keep #17/#15/#13/#61/#64/#18/#38/#50 OPEN and pilot receipt status `Unverified`.
