# ADR 0098 — Isolated dedicated PostgreSQL runtime managed-identity candidate (no assignment/SQL grants)

Status: **Accepted for scoped nondeployed Terraform candidate [#132](https://github.com/KeyserDSoze/TemporalMark/issues/132)**, 2026-11-20. Parent [#128](https://github.com/KeyserDSoze/TemporalMark/issues/128) and [#18](https://github.com/KeyserDSoze/TemporalMark/issues/18) **remain OPEN** for real PostgreSQL Entra authentication, historical state, migration and CAB authorization. No Azure apply authorized.

## Context and reviewed references

Before deciding, reviewed ADR [0001](0001-architecture-and-deployments.md), [0094](0094-azure-api-keyvault-bootstrap-secret-reference.md), [0095](0095-isolated-entra-only-postgres-candidate.md), [0096](0096-detached-npgsql-entra-token-candidate.md), [0097](0097-container-apps-managed-identity-postgres-token-candidate.md), `docs/COMPLIANCE.md`, `docs/ROADMAP.md`, `docs/THREAT_MODEL.md`, `docs/DATABASE_MIGRATIONS.md`, both PostgreSQL/ACA operator candidate runbooks, `infra/azure/main.tf`, existing root `infra/azure/candidates/entra_postgres/{main.tf,variables.tf,versions.tf,tests}`, Python source policy and mandatory CI Terraform workflow, the twenty immutable migration files and separate runtime/DDL/reviewer/registrar PostgreSQL login paths.

The active Azure main reference **still uses `administrator_password=var.postgres_password`**: present and historic Terraform state contain bootstrap credentials. Main API presently uses an externally provisioned Key Vault connection secret and **two different identities** for Blob (system) and Key Vault (UAI); neither proves a PostgreSQL data-plane principal exists. Isolated candidate #129 defines Entra-only **new** PostgreSQL server with a **Group administrator**, not an application identity. Detached .NET Npgsql #130 and Container Apps local token supplier #131 require an explicit independently approved **user-assigned managed identity** client GUID but are **not wired** into the actual API or Azure deployment.

Verified HashiCorp [AzureRM `azurerm_user_assigned_identity`](https://registry.terraform.io/providers/hashicorp/azurerm/latest/docs/resources/user_assigned_identity): requires resource group, location, name; exposes `id` (Azure Resource Manager identity resource ID), `client_id` (Entra application/client ID) and `principal_id` (Entra service-principal/object ID). Microsoft [Container Apps identity assignment](https://learn.microsoft.com/en-us/azure/container-apps/managed-identity) uses identity ARM resource ID for attachment and explicit UAI client ID for local `client_id` token selection. Microsoft [PostgreSQL Entra role configuration](https://learn.microsoft.com/en-us/azure/postgresql/security/security-manage-entra-users) and [managed identity authentication](https://learn.microsoft.com/en-us/azure/postgresql/security/security-connect-with-managed-identity) distinguish creating **an identity** from authorizing a **PostgreSQL SQL role**. SQL role creation requires a separately authenticated approved Entra DB administrator on `postgres` and least-privilege SQL grants; **Azure RBAC `Contributor` etc. is not SQL role mapping.**

## Decision

1. Extend only the **existing separate, non-applied** root `infra/azure/candidates/entra_postgres/` with exactly one `azurerm_user_assigned_identity.postgres_runtime_candidate` resource (NOT `infra/azure/main.tf`), **owned by the approved pre-existing RG**, same approved location, name required as an explicit input `postgres_runtime_identity_name` with strict canonical lowercase pattern ending `-pg-mi-candidate`. Do not add a default identity name that might collide with the active API. Apply only with independent change approval to a disposable new test subscription/resource group, not current Azure registry.
2. Use existing `local.candidate_tags` (`environment=disposable-entra-candidate`, `compliance=NOT_QUALIFIED`, `auto_deploy=DENIED`) and `lifecycle { prevent_destroy=true }`; no identity secret, client assertion, personal credential or tenant data in variables/state/outputs. Explicit resource precondition ensures identity is not named equal to candidate server or approved Entra admin group. A name/ARM GUID regex is **not evidence** of actual tenant ownership, UAI grant assignment or absence of display-name impersonation.
3. Add separate **non-sensitive metadata outputs** `postgres_runtime_identity_resource_id`, `postgres_runtime_identity_client_id`, `postgres_runtime_identity_principal_id`. The first is an ARM resource ID for a *future* approved Container Apps user-assigned identity attachment, the second supplies explicit ACA `client_id` to the #131 callback, the third is the separate Entra service principal object ID for directory/DB-principal verification. Client ID and object ID are **not interchangeable**. Mock plans cannot assert provider-computed identifiers are populated/valid, so test outputs only by source-policy checks. These are identifiers, not authentication tokens. Publishing them does not grant access.
4. **No** `azurerm_container_app`, `azurerm_role_assignment`, `azurerm_postgresql_flexible_server_active_directory_administrator` **for this UAI**, SQL `pgaadauth_create_principal`, DB grants, local `terraform apply`, OCI image, trusted DDL or database-login resource. Existing Entra **group administrator** stays separate. This specific candidate cannot make UAI an SQL admin. A later independently governed DB session must explicitly create and grant minimal SQL privileges, with distinct runtime, approver/reviewer/registrar and migration-owner roles. Do not attach a SQL-capable identity to the active app without review.
5. Test-driven implementation: first commit new mandatory **mocked `terraform test` plans** in the existing candidate test HCL (positive identity name/location/RG/tag, negative bad names/role collision) and Python source-policy checks for exactly one separate UAI resource, safe outputs, fail-closed detachment, no role assignment/SQL login/password. Verify **real GitHub Actions RED** on missing resource/variable before adding Terraform resource/variables/outputs. Then add minimal source and show GREEN on real Terraform provider schema, fmt/validate and all existing Azure plan cases. No new Azure credentials or deployment actions in CI.
6. Document the outcome in `docs/AZURE_POSTGRES_ENTRA_CANDIDATE.md`, `docs/AZURE_CONTAINER_APPS_POSTGRES_IDENTITY_CANDIDATE.md`, `infra/azure/README.md`, ROADMAP/THREAT_MODEL/DATABASE_MIGRATIONS; mention that a Terraform **plan** never validates live Entra identity, DB login/roles, identity attachment or private TLS. No change to on-prem OSS runtime/Keycloak, API/Provisioner and all 20 SQL migration checksums. Production #128/#18 remain open until approved and proven real ACA+Npgsql DB connection, roles/permissions, token expiry, migration/privileged SQL user segregation, credential rotation/state custody and safe rollback, plus WORM/DPIA/QTSP.

## Completion / nonclaims

Only close scoped #132 after the exact **final docs-inclusive main SHA** has 4 GitHub Actions core jobs backend/frontend/terraform/docker-smoke SUCCESS with `temporalmark/ci-4-core-jobs=success`, real Terraform mocked plan positive/negative checks, Python policy, .NET tests and real PostgreSQL dump/restore, Keycloak signed TOTP/PKCE and two-tenant API HTTP isolation. No Terraform `apply`, no live Azure Managed Identity or PostgreSQL logins, no qualified time stamping, no legal WORM/evidence custody and no administrator-secret remediation is implied.
