# ADR 0083 — Atomic PostgreSQL admission of tenant document-imprint searches (pilot)

Status: **Accepted for scoped nonqualified #116 only**, 2026-11-19. Parent [#115](https://github.com/KeyserDSoze/TemporalMark/issues/115) and [#113](https://github.com/KeyserDSoze/TemporalMark/issues/113) remain OPEN.

## Baseline and threat

Reviewed [ADR 0004](0004-evidence-time-and-retention.md) (privacy/retention), [ADR 0005](0005-tenant-audit-mvp.md), [ADR 0081](0081-tenant-document-sha256-imprint-exact-lookup.md), [ADR 0082](0082-search-audit-and-abuse-controls.md), current `TimestampRegistryService`, `TenantAuditService`, V018, `Program.cs` signed-OIDC+SQL active admin guard, CI two-tenant real signed-Keycloak+PostgreSQL smoke, migration-owner and runtime SQL role separation and PostgreSQL's `SECURITY DEFINER`/advisory locks. Existing search does **not** limit enumeration; valid requests can probe known document SHA-256 fingerprints. A single-memory-process `RateLimiter` would reset on redeploy and multiply quotas across API replicas.

Official PostgreSQL 17 references: [transaction-level advisory locks](https://www.postgresql.org/docs/17/explicit-locking.html), [pg_advisory_xact_lock](https://www.postgresql.org/docs/17/functions-admin.html), [SECURITY DEFINER safe search path](https://www.postgresql.org/docs/17/sql-createfunction.html). The one PostgreSQL primary must be shared by *all* API replicas. This gate is **not** a substitute for pre-auth IP/edge protection, independent WORM audit, legal timestamp assurance or privacy-validated operations.

## Decision scoped to #116

1. Add a new forward-only immutable `V019`: two fixed-size row-state tables for tenant and tenant+principal counters, with explicit `CHECK` and foreign-key constraints, no raw imprint, request-body, JWT, match flag or result count. Store the exact authenticated OIDC subject (already used in pilot access audit) solely to enforce **per-principal** quotas; this is personal metadata needing deletion/retention governance. Existing V001–V018 and V015/V016 registrar controls remain untouched. Ordinary runtime SQL role must have **no direct SELECT/INSERT/UPDATE/DELETE** on rate tables.
2. A single SQL `SECURITY DEFINER` function `public.consume_imprint_search_rate(uuid,text)`, executable only by the runtime group, validates nonzero organization and bounded/control-free actor, acquires a **transaction-level PostgreSQL advisory lock keyed to the authenticated tenant**, then reads and changes both counters transactionally. Lock collisions may over-serialize distinct tenants, **never merge their counters**. Use only qualified `public.` objects, with `SET search_path=pg_catalog,pg_temp`. In a multi-replica deployment all requests must reach the same *writable* PostgreSQL primary; fail closed if unavailable, without any local/global fallback.
3. Set conservative, fixed, documented pilot budgets of **12 authorized valid requests per actor and 30 per tenant per 60-second UTC epoch-aligned database-time window**. Both budgets must be below the limit before either counter is incremented; denied attempts do not partially increase counters. If either would exceed, return `allowed=false` and `retryAfterSeconds=1..60` based on the *same PostgreSQL clock* and window end. Client-provided headers, remote IP, claims not already validated, raw SHA-256 and request body must never be rate keys. SQL clock rollback to an earlier window or corrupt counters denies through error, without resetting to permit additional requests.
4. API order: signed JWT and active tenant-admin SQL membership first; strict request imprint/paging/period preflight before quota; **atomic rate admission before reading matching registry rows**; if denied, respond HTTP `429` with integer `Retry-After`, `Cache-Control: no-store`, and generic body that reveals neither match/no-match nor the queried imprint. If allowed, run existing tenant-filtered registry search, then #114 audit append before returning any metadata; no audit success if storage fails. Invalid/malformed requests still use `400`, unauthorized/inactive `401/403`. The rate-limit storage is separate from the existing app audit ledger; a 429 is not a successful search.
5. Opportunistically remove old principal/tenant counter rows during admitted function invocation (stale beyond three minutes). PostgreSQL has no built-in guaranteed TTL: idle rows can persist indefinitely until another request triggers cleanup. This is **not** a fully approved retention mechanism; production #115 must provide independently reviewed scheduled deletion, privacy basis/DPIA and operator evidence. Runtime users receive no cleanup ability outside the narrow function.
6. No required Redis, Azure Storage, per-process cache or cloud-only service. Identical .NET/SQL migration applies on-prem OSS PostgreSQL and Azure PostgreSQL, **provided both use one shared writable primary**. Multi-primary, regional partitioning, failover/clock recovery and edge abuse need further design under #115; never silently claim those work.

## Explicit non-claims

This throttling does not attest that a document is authentic, that an RFC3161/CMS token was qualified, that search events are sealed, or that historical EU Trusted List status was validated. All pilot records remain `Unverified`; V015/V016 security freeze remains unchanged. Edge/network quotas, request-body redaction in every deployed proxy, HMAC actor pseudonymization, GDPR retention deadlines, regional consistency and CAB legal review are outstanding for #115/#113/#17.
